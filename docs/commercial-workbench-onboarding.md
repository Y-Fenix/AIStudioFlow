# 游戏版本工作台：从资料到可评审交付

本示例是虚构练习资料，不是已完成的客户项目。复制文字到自己的隔离项目后再运行，不自动向个人数据库插入示例成功记录。每个执行结果都需要专业评审；章节和引用检查只负责结构与追溯，不负责证明事实或商业判断正确。

## 先用五分钟建立工作范围

1. 用个人模式在本机工作，选择工作室、项目和版本。团队公区只接收你明确预览、选择并确认上传的内容。
2. 在“连接与模型”启用本机 Codex 中转配置，或保存自定义兼容 API。模型与推理强度以实际启用设置为准；更换来源并保存后，在隔离项目用最小真实输入试运行。保存配置或读取模型列表不代表远端生成已验证，不在聊天或需求里粘贴密钥。
3. 进入部门节点，补输入资料，核对当前 Skill。Skill 可以选择、导入或导出；导入的是本次节点的方法，不会自动安装脚本或授予工具权限。
4. 保存输入后执行。结果先核对原始引用、假设、能力边界与下一步，再人工确认。修改资料、Skill 或交付后需要重新评审。
5. 下游节点先预览已确认的上游交付，再追加到自己的输入草稿。它是独立副本，来源修改不会静默更新你的工作。

## 可复制的版本需求

```text
【虚构游戏示例】项目：星屿收纳；版本：0.1；平台：Android。
团队：1策划、1美术、2名Unity开发、1测试；MVP两周。
玩家把颜色相同的物品拖入同色收纳箱，每箱容量3；满箱移走并加1分。
错色、满箱时返回原位，不扣分。首版10关，每关最多30个物品。
每关90秒，所有物品收纳完成即胜利，计时归零失败，切后台暂停。
每关可完成一次激励广告加30秒，广告失败/取消不奖励，网络失败可继续游戏。
包含开始、暂停恢复、胜负结算和加时，不含IAP、社交或云存档。
未提供真实市场数据、竞品包体、美术资源、工程代码和安装包。
```

这份资料适合验证规则拆解，不足以证明市场需求或实际实现。不要让模型补造竞品下载量、真实玩家数据、图稿路径或构建结果。

## 四部门交付路线

| 部门 | 推荐输入 | 本轮可以得到 | 负责人应核对 |
| --- | --- | --- | --- |
| 产品 | 目标玩家、预算、原始访谈/调研摘录、竞品文字资料及上述规则 | 市场机会假设、竞品文字拆解、玩法商业化方案、PRD与文字原型规格 | 数据来源、MVP边界、规则状态、需求ID和验收标准 |
| 设计 | 已确认PRD、参考风格的文字说明、画面尺寸和资源约束 | 视觉方向、UX文字线框、资产规格与待生产清单、文本验收意见 | 状态覆盖、尺寸、交互反馈、可读性、待制作图稿 |
| 开发 | 已确认PRD/设计规格、实际代码摘录、接口和存档约束 | 技术方案、未应用代码提案、文本静态审查和自检计划、交测说明草案 | 真实工程适配、边界条件、存档兼容、未运行的检查与包体缺口 |
| 测试 | 原始需求、已确认规则、可读仓库和指定分支 | 精简覆盖用例、逐用例静态证据、根因与内部Bug草稿、回归建议 | 范围缺口、源码引用、静态推导与实测区分、一因一单、发布前复现 |

产品、设计和开发的执行器处理用户提供的文本；填写 URL、路径或截图名称，不代表它已经读取。联网调研、反编译、生图、Figma、工程写入、构建和发布仍需对应真实工具接入。测试继续走专用静态证据链，不启动 Unity。外部飞书发布及状态修改保留人工确认。

## 自定义流程的推荐搭法

新建流程，先引用“产品 PRD → 设计 UX → 开发技术方案”，每个实例保留自己的输入与 Skill。建议在部门交接处关闭自动继续并放入人工审核，核对上游交付后再继续。独立 AI 任务写清目的、已有资料、期望交付和验收项；依据不足应是风险，不能当通过。

运行冻结当时的节点、输入与 Skill。编辑当前配置不会修改历史运行。完成表示执行步骤结束，不表示业务审批通过；飞书、公区和源码写入不随自动执行开关自动获得授权。

## 用业务结果判断是否值得用

先选一个真实版本做试点，人工记录：输入准备耗时、执行等待、返工原因、评审发现的错误、交付采纳项、测试实际发现的缺陷和最终未解决风险。对照原来的同类流程后再判断收益。本轮没有足够数据承诺节约比例、修复概率或付费转化。

飞书/企业微信继续管理消息和团队文档；StudioFlow 的验证重点是 Skill 固化方法、版本快照、可恢复执行、证据与决策追溯。商业试点可先提供工作室部署和部门方法包；支付、订阅、计费及 SLA 没有在本轮实现。
