# 项目 Agent 静态审查与性能验证

## 真实根因

2026-11-10 独立审计与本机记录交叉确认：旧默认路径使用 Responses 单轮文字请求，通过自定义 `read/search/find_files` 协议探索源码；不是持续运行的 Codex 项目 Agent。约每条 7.5～8 次重新发送上下文，三个工作线程并未解决重复调查与逐条长报告成本。

30 条样本的 225 次模型调用中，195 次取证累计约 1824 秒，30 次最终报告累计约 1958 秒。653 份搜索响应重复携带同一组 100 个不可读文件，约 520 万字符，占搜索结果 JSON 的约 79.5%。先前扩大源码复用后，请求平均长度反而从约 23.6 万升至约 32.8 万字符；不能据此宣称提速。

## 新执行路径

运行时存在 Codex CLI、所选连接支持 Responses 时，默认使用 `CodexAgent`：

- 当前用户实际选择的模型与推理强度，真实项目工作目录、只读 sandbox、保留 shell 工具；禁用插件、Apps 和远端插件。不切换 Git、不启动 Unity。
- 按显式 module 或测试点关联的需求来源组织工作包，默认每包最多 20 条、最多三包并发。保持每条用例每个步骤独立结果，不用共享结论代替逐条校验。
- 使用真实源码重新校验引用、步骤覆盖、用例 ID、状态及失败反例字段。模型推导仍可能有误，引用校验不等于逻辑正确性证明。
- 每条校验后写私有检查点；需求、Skill、模型连接或代码变化失效。原有持久化 `code_fingerprint` 语义不变，另外固定 `.bytes/.bin` 辅助数据哈希并在执行末复核；哈希不证明二进制解码正确。
- 原始 Agent JSONL 活动及返回结果保存在工作包证据子目录，文件权限 0600。源码和需求是私有资料，不将原始活动日志写入通知或自动公开上传。
- 工具子进程不继承服务端环境，仅设置 PATH/LANG 及临时私有 HOME/ZDOTDIR，避免 shell 启动文件重新导出凭据。Codex 主进程需要登录/模型凭据；`read-only` 不等于整个项目读取隔离，当前不是不可信多租户代码沙箱。

Chat Completions 配置、未安装 Codex 时继续原文字执行器，不暗换模型。可显式设置 `TESTFLOW_STATIC_ENGINE=legacy` 对照；`TESTFLOW_STATIC_WORKERS=1..3` 调整并发，`TESTFLOW_AGENT_BATCH_SIZE=1..20` 调整工作包。原生 Agent 仅连续无可观察新活动才触发等待超时，心跳不续期；关闭运行详情不会停止任务。

CLI JSONL 通常在工具或整条消息完成时才发布事件，不能把输出安静几分钟直接解释为上游停止生成。原生执行器默认等待上限是连续 1800 秒无新事件，可通过 `TESTFLOW_AGENT_IDLE_TIMEOUT=30..1800` 配置；这不是总时限，也不构成提速优化。未来要准确区分生成中与断流，应接入提供文本增量的 Agent 事件协议。

逐用例校验后立即保存有效检查点。一处引用错误只触发该用例的一次文字校正，向模型提供实际读取的行号片段；校正仍须完整步骤和逐字引用门禁。已通过的其他用例不重跑，校正再次失败则明确停止且保留有效检查点，不降格伪造通过。

## 已验证与尚待验证

真实 `gpt-6.1-sol / high` CLI 连通探针约 15.3 秒完成。真实首包 10 条、19 个步骤约 700.1 秒返回，共 55 处引用、26 份文本源码重新核验成功。首包发现全体使用 1-based 步骤编号，旧校验器将其误当格式错误并重做；已补明确 0-based 协议和无歧义完整 `1..N` 的兼容转换，保留原始编号及原文，重复、缺失或混杂编号仍拒绝。

该首包不是完整端到端提速验收，也不是与旧引擎同一固定基线的严格 A/B。独立人工复核还发现其中一条候选缺陷可能混淆正常在途收口与自动收集，不能当作已确认 Bug。

133 条执行器完整试跑已完成：真实 GagaSort 源码、`gpt-6.1-sol / high`、三包并发，**1870.86 秒（31 分 10.86 秒）**，覆盖 255 个步骤断言。报告位于本机私有 `data/native-benchmark/full/report.json`。计数为 passed=23、failed=21、needs_runtime=12、requirement_unclear=3、insufficient_evidence=74，无 runner_error/not_run/skipped。这是执行器真实基准，不是已经入库的工作台队列验收，也不是固定基线下与旧引擎的严格 A/B。

该次加载的版本在一包 20 条中有一条引用错误，导致整包再次调查；后续已改为保存其余有效用例，仅校正错误用例。使用该真实候选和实际源码片段的单条修正耗时 **69.75 秒**，通过独立引用及步骤门禁。该单条测速不构成新版本完整吞吐承诺。完整基准也早于辅助二进制指纹改动，不能声称已验证该增量。

独立人工复核进一步发现：failed 候选仍存在重复根因和反例时序不可达的问题；引用真实不代表缺陷成立，21 条 failed 不能直接报成 21 个确认 Bug。需要保留原始结果，并把复核结论单独记录，不覆盖原证据。见[独立审查记录](testing-native-benchmark-audit.md)。

## 正式工作台队列验收及真实收尾故障

正式任务 `bdfe280d71904934a0fd401ddbc238db` 的真实模型任务 `ebe25f3ced334ddda67da9830617d297` 完成133条、255个步骤的审查，8个工作包均未重试；但在保存大结果和通知出箱时发生数据库自锁，原任务如实保留为失败。首轮从启动到该失败记录约 **1565.36秒（26分5秒）**，不是一次成功入库的耗时。

根因是事务写入大结果触发SQLite缓存页溢出及排他锁，通知随后通过新连接读取项目节点，第二连接等待第一连接释放锁，而第一连接等待通知返回。还导致空闲测试工作线程在领取任务时遇锁退出。新增4.8MB结果的实际SQLite回归先复现同一堆栈，再将通知节点查询复用原事务连接；测试队列仅对SQLite BUSY/LOCKED做等待，不吞掉其他数据库错误。

重启后经正常授权排队恢复任务 `807d0c1326f84feaa139dc538446d559`：逐条重新校验133个检查点及实际源码，复核需求、用例、Skill、文本与二进制基线后成功入库；通知sent。恢复约 **7.77秒**，此数包含缓存复用，绝不能当作133条新审查的速度。从原始启动到修复后成功入库共 **1780.36秒（29分40秒）**，包含中途定位修复时间。

正式保存计数：passed=18、failed=20、needs_runtime=12、requirement_unclear=1、insufficient_evidence=82，runner_error/not_run/skipped均为0。完整覆盖用例ID与步骤并不意味着所有预期闭合；82条证据不足、失败候选可靠性和调查深度仍属质量限制，不能声称与用户Codex应用中的评审深度完全等价。

本机私有验证记录 `data/native-benchmark/workbench-verification.json` 固定两次任务ID、时间、复用数、哈希核对和正式证据路径；原失败记录、原始Agent日志与恢复报告分别保留，未手工导入基准结果冒充正式执行。

完成计数仅包含已校验用例；工作包进行中的工具数不换算为用例进度或成功率。

专项测试：`tests/test_codex_agent.py`、`tests/test_agent_activity.py`、`tests/test_QA_native_review.py`、`tests/test_QA_native_execution.py`。替身测试证明协议、隔离配置、去重计数、引用门禁与检查点行为，不能替代真实性能验收。
