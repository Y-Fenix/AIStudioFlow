# StudioFlow AI 工作流产品化开发需求

日期：2026-10-21。依据：用户认可工作流优化方向，并要求整理需求后落地开发。本文区分本期交付与后续路线，不把路线当作已上线功能。

## 目标与定位

面向游戏工作室的 AI 交付工作台：按项目、版本组织需求、用例、源码证据与缺陷，支持人工决策和可恢复执行。飞书/企业微信承接协作和通知；平台承接执行、证据与规则。首个可用场景为测试静态审查，不启动 Unity、不写游戏代码、不自动发布缺陷、不改远端状态。

现状：测试已有执行器、队列、证据校验、人工门禁与飞书接口；生成已有分批检查点。其他部门为人工工作区与适配器接口。模型配置已区分服务器配置与个人电脑。不要重复建设这些能力。

## 方案选择

1. 本期推荐：复用现有权限、任务和版本协议，增加静态审查检查点、只读关联视图和规则检查。先解决真实任务的浪费与不可追踪问题。
2. 全面重建通用 DAG：需要重做调度、数据协议和部门适配，当前执行能力不足，成本大于本期收益，暂不采用。
3. 仅增加首页和更多节点：不能解决运行质量和中断损失，不采用。

## 本期 P0（本次开发交付）

### WF-01 静态审查断点恢复

- 每条完成的用例原子保存私有检查点；失败后由用户重新点击执行，自动复用仍有效的已完成用例。
- 检查点隔离：批次、重置代次、执行/回归用途；输入签名包含协议、需求、完整单条用例、Skill、请求模型选择、代码提交/分支/指纹及仓库路径。
- 需求、Skill、模型选择、代码变化均不复用旧结论；同一基线下修改某条用例仅该用例失效。
- 复用仍校验断言结构、步骤预期与真实源码引用。损坏、缺失、格式错误的检查点视为未命中，重新审查。
- 中断仅保存已完成用例，不将部分结果写成完整报告；最终继续执行原全量覆盖和前后代码指纹校验。
- 运行中显示本次复用数与新审查数；不自动重新运行外部发布和通知。

### WF-02 真实运行状态

- 开始执行时保存请求模型、推理强度、来源与开始时间；不记录 API Key。
- 进度合并保存，防止用例进度覆盖模型诊断，或模型诊断覆盖复用计数。
- 页面区分排队、执行、完成、失败/中断，显示进度更新时间和断点复用；已有取消与无响应超时策略不变。
- 模型配置表示“请求模型”，不声称代理实际提供的底层模型已证实。费用未知时明确未知，不虚构费用或节省比例。

### WF-03 需求至缺陷关联视图

- 测试工作区增加默认折叠的“交付与证据”入口，按来源 → 测试点 → 用例 → 断言/源码引用 → 根因 → Bug 关联 → 回归展示。
- 使用当前已授权任务数据，不额外读取其他节点私有数据，不直接读取磁盘证据文件。
- 可筛选关键未决项、缺陷及未执行项；大列表分页，每页 10/20/50/100。
- 单条关联默认收起，按需展开详情；页面轮询保留展开状态、筛选和页码。同一用例同时有异常依据和待补证据时，同时进入对应筛选，不用总体失败状态掩盖未决断言。
- 缺失关联写“未关联”；无结果写“未审查”；静态支持不能显示成实机通过。显示剩余缺口，不生成修复概率。
- 展示实际统计，不将关联覆盖率当作需求完整覆盖率。

### WF-04 Skill 规则检查

- 提供当前节点 Skill 的只读规则检查，列出输入说明、输出约定、证据要求、边界/失败处理等是否有明确文字声明。
- 检测空规则、未打包的相对依赖及明显缺失说明。不得因文本关键词命中称为“质量达标”。
- 显示实际 Skill 指纹、来源和检查限制：本期是静态规则检查，业务质量仍需真实样本评测。
- 不修改导入内容，不自动恢复或发布 Skill，不改变原权限。

### WF-05 场景入口与部署指引

- 测试首页明确场景：版本需求与代码静态审查，并提供进入测试工作区的入口。
- 保持五部门独立扩展，人工部门继续明确人工交付。
- 测试代码路径不再默认个人机器绝对路径，优先已绑定路径，未配置显示提示而非伪造配置。
- 本期不新增服务器连接探测和个人桥接协议；沿用现有服务器模型配置和本机桥接。

### WF-06 提醒配置降低噪声

- 提供“关键事件（失败、中断、待审核交付）”“全部结果（含人工确认）”事件预设。
- 预设只修改草稿，仍需保存才生效；继承模式不能修改。
- 保留按项目独立目的地与已有逐级覆盖。Webhook 仍仅发送消息和结果链接，不承诺群内审批。

## 后续路线（不属于本期验收）

P1：需求变更差异及人工确认的影响范围、断言级精准重跑、节点产物结构契约、Skill 固定样本评测与版本对比、人工审核差异视图、真实 token/成本记账（服务未返回则未知）、通知摘要合并。

P2：条件分支与受控并行、部门真实工具适配、个人执行桥接完善、企业微信通知适配、多租户飞书身份。所有新增能力保持人工发布门禁。

## 商业验证

以同一真实版本、相同需求/代码范围对比人工、直接 Codex+Skill、平台三种方式。记录人工投入、墙钟耗时、有效缺陷、误报、审核修改、重复项与中断恢复损失。未完成对照前不声称提效百分比或商业效果。商业验证不以替身测试结果代替。

## 架构与兼容

- 新测试业务放 departments/testing/QA_*，前端通过 web/app.js 兼容入口集成；公共任务遥测在 server/core/ 独立模块，队列只接线。
- 检查点为私有本地文件，0600 原子写入，不增加表或改变原字段含义；旧任务无新字段正常显示。
- 新关联与规则检查模块只消费已过滤任务；全部动态文字转义。不增加授权，不展示未授权 Skill 正文。
- 不拉取/提交/推送 Git，不修改 Figma，不把真实需求、密钥或数据库放入代码。仅使用隔离样例进行自动测试。

## 验收

1. 两条用例中第二条中断后，重试只审查第二条；变更需求、Skill、模型或代码时不能复用旧结论。
2. 检查点损坏、伪造引用、取消和基线漂移不产生虚假完成。
3. 遥测合并保留模型与业务进度，不返回任何凭据。
4. 关联视图处理缺失关联、同名用例、未决结论、分页和恶意 HTML；引用真实字段，不推测关联。
5. Skill 检查明确能力边界；无 Skill 查看权限不能从此入口看到正文。
6. 预设切换不会直接保存或发消息；原通知隔离回归通过。
7. 部门边界、测试部门规定的 Python/Node 检查及隔离浏览器流程通过；真实模型与真实飞书发送另列验收状态。
