# 项目迭代版本与旧数据兼容迁移设计

状态：待用户确认；本文是设计，尚未修改程序、数据库或当前预览服务。

## 目标

工作层级变为：工作室 → 项目 → 版本 → 部门 → 节点 → Skill。

成员进入项目后，先选择一个迭代版本，再在其中执行部门工作。一个版本表示一次业务迭代，例如 `1.8.0` 或 `万圣节活动`，不等于 Git 分支、测试批次、节点保存修订号或 Skill 历史版本。

## 当前实现与变更原因

以下结论来自本地实际代码与数据库表结构读取，不代表已实施迁移：

- `server/store.py`：测试任务目前直接按 `project_id` 保存、列举和授权，需求、测试日志、发布台账与回归状态经 `task_id` 关联任务。
- `server/studio_schema.py`：公共节点工作区主键为 `(project_id,node)`，操作日志同样只区分项目和节点。
- `server/core/schema.py`：节点配置主键为 `(project_id,department)`，内容配置按项目唯一；部门队列限制同一项目节点只有一个活动任务；Skill 绑定按项目、节点和测试批次保存。
- `web/studio.js` 与 `web/app.js`：请求、页面上下文、测试 iframe 和消息同步目前没有迭代版本坐标。
- 现有 `revision`、需求的 `version`、`skill_versions.version` 分别表示保存修订、需求文本历史和 Skill 历史，不能拿来充当项目迭代版本。

因此只增加一个下拉框不能满足需求，必须同步调整存储、权限、API、后台队列与界面上下文。

## 方案取舍

| 方案 | 结果 |
| --- | --- |
| 给任务增加版本名称标签 | 无法隔离其他部门工作区、节点配置、日志与队列，不采用。 |
| 项目内建立有稳定 ID 的版本空间 | 推荐。保留项目与节点 ID，在业务记录上增加版本坐标，能独立推进多次迭代。 |
| 每个迭代复制成一个项目 | 会重复成员、授权和连接配置，也不符合项目下多版本的层级，不采用。 |

## 页面与操作

顶部固定展示当前上下文，例如：`我的工作室 / GagaSort / 1.8.0 / 测试部门`。项目和版本各有独立切换入口，版本名称可截断但完整名称可查看，不在左上角堆积多个按钮。

左侧项目区域保留“新增项目 / 选择项目”；当前项目下新增一个紧凑的版本区域：

```text
当前项目  GagaSort                 ▾
当前版本  1.8.0                    ▾
          ＋ 新增版本

部门首页 · 项目总览 · 版本产物 · 待我决策
```

版本选择使用弹窗，支持名称搜索、每页5项、当前版本标记及归档版本筛选；关闭按钮、遮罩、ESC均可退出，并沿用现有防滚动穿透处理。新增版本表单填写名称（必填，项目内唯一）和说明（选填），创建后自动进入。

新项目没有迭代业务数据，进入后提示“先新增版本”。未选择版本时可以管理项目成员、权限和连接设置，不展示混合的工作区，也不能创建测试批次或执行部门节点。

切换版本前检查未保存编辑；切换后清理旧节点、任务、日志滚动缓存、弹窗上下文与轮询。已运行的任务继续属于原版本，不随页面切换改变归属。浏览器不同标签页各自固定 URL 中的版本坐标；个人“上次版本”仅决定首次进入的默认选择，不作为写请求的隐式作用范围。

项目总览、部门首页、产物、待决策和节点管理默认只统计当前版本。顶部和空状态明确显示版本，避免把空版本误认为数据丢失。界面中现有“版本 3”一类保存计数改称“修订 3”；Skill 自身版本保留在 Skill 详情中，与迭代版本分开表达。

## 数据边界与新版本初始状态

| 项目共享 | 版本独立 |
| --- | --- |
| 项目基本信息、成员、部门归属、继承的权限规则 | 版本名称、说明、状态和创建记录 |
| 本地仓库连接、平台模型来源与外部连接配置 | 节点启停/排序/新增/删除配置及版本内内容配置 |
| 部门插件代码、默认 manifest、平台随附 Skill | 版本内节点 Skill 绑定、选择/导入快照、历史与回收站 |
| 项目级授权管理入口 | 需求、用例、测试批次、代码检测、归因、筛选、Bug关联与回归 |
| 平台级安全审计 | 各部门输入、交付物、审批、操作日志及任务队列 |

默认从当前版本复制节点结构和版本级 Skill 配置，保留稳定节点 ID，获得新的配置修订和独立 Skill 记录。存在已删除或未配置的节点/Skill时如实复制，不自动恢复。没有来源版本时使用平台默认模板。

不复制上个版本的需求、测试批次、交付物、批准状态、缺陷发布/状态变更台账或运行中的任务。新版本业务数据从空白开始，防止沿用旧需求和旧审核结果。来源版本和复制配置的操作者记录在创建事件中；原规则的真实上传者/来源不能冒记为复制人。Skill复制为快照，上游后来修改不自动传播。

首期不做“整版本复制全部业务数据”、跨版本自动合并、自动迁移未关闭Bug或与Git分支自动绑定。这些能力需要分别定义证据和外部记录的复用规则，不能简单复制记录。

## 持久化结构

新增 `project_versions`：

- `id`：不可变随机ID；`project_id`：真实父项目外键。
- `name`、`name_key`：名称1至60字，去首尾空白后按现有项目名称策略规范化；同项目内唯一，归档后仍保留名称避免误认历史。
- `description`：选填，最多2000字。
- `archived`：默认0；归档为1，不硬删业务历史。
- `is_legacy`：标记旧数据迁移版本，不表示只读或已完成。
- `based_on_version_id`：可空，只允许同项目来源。
- `created_by`、`created_at`：真实创建者和时间；迁移版本使用明确的迁移来源，不虚构业务创建者。
- 建立 `(project_id,id)` 唯一约束，供业务表组合外键检查归属。

新增个人版本访问偏好表，保存 `(user_id,project_id,version_id)`；只控制默认落点，不参与授权或决定后台任务的写入目的地。

需要直接增加 `version_id` 的表：`tasks`、`jobs`、`studio_workspaces`、`studio_events`、`department_jobs`、`project_node_configs`、`project_content_configs`、`skill_library`、`skill_bindings`、`codex_handoffs`。这些记录必须校验版本属于其原有 `project_id`，不能将 `project_id` 偷换成版本ID。

关键主键/索引变为：

- 工作区：`(project_id,version_id,node)`。
- 节点配置：`(project_id,version_id,department)`。
- 内容配置：`(project_id,version_id)`。
- Skill绑定：`(project_id,version_id,node,task_id)`；`skill_versions` 仍通过不可变 `skill_id` 关联。
- 部门活动队列唯一索引：`(project_id,version_id,node)`，同版本同节点的重复提交仍受限。
- 测试活动队列仍按不可变 `task_id` 去重；任务与队列的版本归属必须一致。

需求、测试事件、节点重置、发布台账、状态变更记录通过原 `task_id` 继承版本，不再增加相互可能矛盾的版本字段；访问前必须先校验任务的项目和版本归属。

## 旧数据迁移与回退

1. 在迁移旧库前检查测试和部门队列。存在排队或运行任务时不进行升级、不通过重启把任务打断；等任务处理完成后再迁移。
2. 使用SQLite备份API生成权限0600的一致性备份，记录迁移编号；备份失败则不迁移。
3. 在维护窗口对每个现有项目建立唯一的“历史版本”，把全部原有业务记录归入该版本；保留项目、节点、任务、Skill、Bug记录的原ID，以及真实上传者、审批、时间、代码证据和修订号。不根据日期猜测原始业务版本号。
4. 重建需要改变组合主键的表，回填新增字段，重建索引并执行外键、记录数量、业务正文/证据哈希一致性检查；迁移步骤保持幂等。
5. `project_id` 始终表示项目；现有 `revision` 和需求/Skill历史计数含义不变。版本隔离的协议变化由新增字段和API路径表达。
6. 失败回滚事务，服务拒绝带着半套结构启动。回退使用迁移前备份及旧程序；不让旧程序继续写已迁移的新库。

迁移后，“历史版本”可继续完成已有测试流程。版本归档才只读，不能因为它是旧数据就擅自归档。

## API与后台任务

新增版本管理路径：

```text
GET/POST /api/studios/{studio}/projects/{project}/versions
GET      /api/studios/{studio}/projects/{project}/versions/{version}
POST     /api/studios/{studio}/projects/{project}/versions/{version}/enter
POST     /api/studios/{studio}/projects/{project}/versions/{version}/archive
POST     /api/studios/{studio}/projects/{project}/versions/{version}/restore
```

业务路径统一在明确版本范围内，例如：

```text
/api/studios/{studio}/projects/{project}/versions/{version}/summary
/api/studios/{studio}/projects/{project}/versions/{version}/workspace?node=product:0
/api/studios/{studio}/projects/{project}/versions/{version}/tasks/{task}
/api/studios/{studio}/projects/{project}/versions/{version}/skills
/api/studios/{studio}/projects/{project}/versions/{version}/nodes?department=testing
```

服务端先验证工作室、项目、版本、归档状态及权限，再构造固定版本的存储访问上下文。即使用户有平台管理权，错误的父项目/版本组合也拒绝。写入同时检查所属范围及原有修订号，不使用可被另一标签页改写的个人偏好来确定版本。

旧无版本路径只允许经明确兼容层访问该项目的迁移历史版本，不自动指向最新版本。新项目没有迁移历史版本时，旧路径返回需要选择版本的错误。生产界面、旧测试页、iframe、导出链接与Skill选择器统一使用显式版本路径。

队列在创建时保存版本ID。Worker领取任务后建立该任务固定的版本上下文，重查真实操作者权限和版本状态；结果、进度、产物和日志只回写原版本。回调消息和Codex交接票据也携带版本ID，版本切换后的迟到结果不能替换当前页面。

归档有活动任务的版本时拒绝操作。已归档版本可查看/导出历史，禁止新建任务、修改Skill、发布Bug、更新远端状态或改写审批。恢复版本后仍需按原有权限和证据门禁继续操作。

## 权限

增加 `version` 资源，复用现有 `view/create/edit/delete` 动作；`delete` 表示归档，不做永久删除按钮。

平台负责人及该项目负责人默认可创建、改名、归档和恢复；其他成员需要显式授权。`version.create` 必须授予项目范围，不能依赖“首页选择负责人身份”获得权限。

在权限规则中增加可选 `version_id` 坐标：空值表示现有项目规则继承到全部版本，指定版本只影响该版本。授权后台可将版本级权限授予指定个人或部门；禁止跨项目拼接版本，明确拒绝优先，授权管理者不得越过自身范围。所有节点、Skill、内容及连接器调用仍检查原有资源动作，获得版本查看权不等于获得子节点访问权。

## 模块边界

- 公共平台维护版本登记、迁移、作用范围、权限、队列、选择器和统一请求路径。
- 部门模块上下文增加只读的 `version: {id,name}`；原有项目、部门、节点ID含义不变，部门负责人无需自己实现数据库隔离。
- 旧测试六节点继续使用原阶段ID和证据依赖，只扩展当前版本上下文；不启动Unity，不改变静态检测定位。
- Skill选择、节点配置、内容管理及Codex桥接复用同一版本范围，不各自用不同的“当前版本”来源。

## 验收标准

1. 同项目创建两个版本，五部门输入、交付、Skill、节点配置、任务、待决策及日志独立；刷新和重启后归属不变。
2. 新版本仅复制节点与Skill配置快照，不继承旧需求、审批、Bug发布与回归结果；新项目必须先创建版本。
3. 旧库迁移后ID、记录数、正文与证据哈希一致；连续启动不重复创建历史版本；模拟失败能完整回滚。
4. 跨项目/跨版本猜任务ID、队列ID、Skill ID或交接票据不能读取或改写其他版本；撤权立即生效。
5. 两个标签页各自工作，切换默认版本不改变另一页请求范围；旧请求/轮询/预览迟到时不串页或误关新弹窗。
6. 版本创建/改名并发与重名冲突受控；版本归档/恢复、活动任务阻止归档、归档只读均有真实API验证。
7. 独立临时库与浏览器跑通选择/搜索/5项分页/创建/切换/刷新/ESC/遮罩及手机布局；原六节点证据门禁与Skill生命周期回归通过。
8. 代码、数据、权限与浏览器验证完成后，确认真实服务无活动任务，备份并更新本机8766预览。

不拉取、提交或推送Git，不修改Figma，不启动Unity。本设计等待用户审核后再开始数据库和程序实现。
