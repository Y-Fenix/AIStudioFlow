## 可审查代码提案

【推导 D5】静态诊断仅针对合成片段：success=false也会执行加时；Rewarded没有作为前置条件，连续调用会连续加时。增加success和Rewarded检查能够处理串行条件下的失败和重复成功，但单独增加两个检查不足以处理跨局回调、并发回调或对象销毁。

【假设 A2】建议将同一请求的第一个终态作为最终结果：失败、取消或本地失效后，迟到成功不再奖励；失败不消耗本局成功领奖额度，可以重新发起新请求。SDK草案没有确认终态顺序和可重试策略，需客户端负责人核对。
【推导 D7｜未应用伪代码】以下为建议接口与处理顺序，省略了尚未提供的SDK调用细节，不是可直接编译的补丁：

状态：sessionToken、alive、phase、pauseReasons、remainingSeconds、rewarded、pendingRequestToken。
约束：所有状态变更、计时和结算均进入同一串行入口；SDK线程只投递事件，不直接访问这些状态或Unity对象。

BeginRound():
  使旧sessionToken失效；创建新的唯一sessionToken
  alive = true；phase = Ready
  remainingSeconds = 90；rewarded = false；pendingRequestToken = 空
  由明确的开始事件进入Running

TryBeginAd():
  若非alive、phase不是Running、仍有暂停原因、remainingSeconds <= 0、rewarded或已有pending，则拒绝
  创建唯一requestToken；先设置pendingRequestToken，再调用广告适配层
  回调闭包捕获当前sessionToken与requestToken
  SDK完成、失败、取消以及启动异常均转换为事件并投递串行入口
  启动异常按失败终态处理；不减少时间、不直接结算失败

HandleAdResult(capturedSession, capturedRequest, success):
  若非alive、局标识不匹配或请求标识不匹配，则忽略
  pendingRequestToken = 空  // 先关闭请求，防止重复及重入
  若success为false，则返回
  若rewarded、phase不在Running或Paused、remainingSeconds <= 0，则返回
  在同一不可重入状态提交中：rewarded = true；remainingSeconds += 30
  完成提交后再通知界面；通知异常不得撤销奖励或重新开放该请求
  不清除任何暂停原因

InvalidatePendingAd():
  在串行入口清空pendingRequestToken；迟到结果自然失效
  若SDK提供取消或退订能力，由适配层执行并处理其异常

EndRoundOrDispose():
  在串行入口将局置为终态或失效，清空pending并使sessionToken失效
  释放本层回调订阅和局引用；后续事件只允许被忽略
