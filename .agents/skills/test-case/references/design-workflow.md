# 用例设计与覆盖工作流

按当前阶段读取对应小节，不默认全文加载。下文 `scripts/` 路径相对于本 Skill 安装目录；§ 编号保留原流程含义。

### 真实账号与数据构造准入

- 先按断言区分本地业务规则与真实外部观察，再标数据准备来源。账号付费历史、活动进度、时间和配置等字段可以用合法本地夹具检查其消费规则；只有必须证明服务器当前值、实际 SDK 接入或设备表现的断言才保留外部验证。不能因为黑盒步骤写了真实账号，就把本地逻辑默认交给测试人员。
- 前置条件显式标注输入准备方式：`【仅内部探针可构造】`、`【需GM/测试包辅助】`、`【需受控SDK/网络环境】`或`【普通操作可执行】`。这些标记用于可选复测路径，不决定验证层级，也不指派人工任务；本地可构造部分由后续执行 Skill 自行完成，外部断言才明确实际所需环境。
- 真实支付历史、订单/补单、排行榜、活动报名、推送授权、广告填充、商店商品、云档、多设备和线上开关均视为真实外部状态。AI 可以根据用例生成账号准备清单、GM/API 参数模板和校验步骤，但不能声称已修改账号，也不能自行改线上后台、正式存档或真实支付记录。
- 用例若必须由测试人员在后台准备数据，主表 `前置条件` 必须写明数据字段、操作人、测试环境、是否需要独立账号/清档，以及完成后的核对方式；`操作步骤` 必须从客户端可执行动作开始。不要把“请后台设置”写成 AI 已完成的步骤。
- SDK 回调处理、通知时间/资格、广告业务状态、支付分层和后台字段消费规则优先静态或本地自动化。实际通知投递、广告素材关闭按钮、商店交易、服务器实时状态、真机渲染/触感等外部独有断言另列；fake/adapter 不得冒充这些真实环境已通过。
- `需GM/测试包辅助`只描述可选复测的输入准备方式。状态机、时间、配置、奖励、存档迁移和事件幂等默认逐项静态代入；只有真实外部观察不可替代时才保留黑盒断言，不能因为未准备账号或测试包就转人工。
- `普通操作可执行`也不自动等于黑盒。先沿代码追踪同一业务路径；能静态判定的直接静态检查，只有必须观察设备、平台或真实服务表现的部分才列黑盒。
- “构造本地状态后验证业务规则”与“修改真实账号后验收”必须分开表述。前者给真实代码入口及夹具/推导证据，后者才要求授权接口、响应与复位日志；没有外部接口不影响本地判断，不能直接写成需人工准备数据。

## 输出约定

默认 Excel 主表 `测试用例` 固定六列：

`测试内容 | 测试目的 | 前置条件 | 操作步骤 | 期望结果 | 需求模块`

- 不生成用例编号、Case ID 或标题序号前缀，除非用户明确要求；关卡数、阈值、档位等真实业务数值不属于编号。
- `需求模块` 填主要来源文件名称，飞书来源填实际需求文档标题而非链接索引文件名，放在六列最后。具体章节、原文、版本、链接索引及跨文件关联放入 `覆盖核对`，不得把所有来源强行归给当前文件。
- `测试内容` 用自然场景名，同一工作簿内应能唯一定位。前置写可建立的账号、配置、时间、存档和状态，步骤说明操作，期望写具体可观察断言，不写“功能正常”或只写“待确认”。
- 能黑盒执行的用例按§2.2把完整准备、操作和可观察预期直接写入上述六列，主表单行复制后即可使用；不为详细步骤另增必读页签或另造一套黑盒用例。
- 默认所有实际用例、耦合回归和必要参数实例整合在一个 `测试用例` 页签，保持六列，直接复制即可使用。`覆盖核对`、`耦合分析`、`验证分层`和变更记录作为机器账本另存 JSON，不要求读者跳辅助页；只有用户指定多页或既有模板要求时才建辅助页。下文这些名称表示分析记录，不强制对应 Excel 页签。分析候选不算已设计用例。
- 用户指定既有导入模板时保留模板，不擅加主表列；追溯和参数明细可用辅助表承接。若下游只识别主表，则展开必要参数实例到主表，不以压缩版式牺牲可执行性。
- 辅助明细用 ID 关联复用证据、公共前置和阻塞原因，不逐实例复制长篇相同说明。小范围任务可合并同义辅助记录，但必须保留覆盖、参数独立预期、耦合决策及层级映射；不能为了显得详尽堆说明表。

## 工作流

### 0. 发现项目资料 → 用户选择 → 读取需求

涉及无参数调用、项目资料发现或飞书来源时，先读 [references/project-sources.md](project-sources.md)。这是进入用例设计前的范围选择，不是重新申请只读权限。

- 只输入 `$test-case` 或未明确本次资料时：在当前已确认项目内发现需求、测试文档及含飞书链接的文件；先完整列出**所有发现的飞书链接文件名称、相对路径和链接数**，另列本地需求/测试资料。让用户通过名称或选择序号指定一个、多个或全部，收到选择前不拉飞书正文、不生成用例。即使只有一个候选也先展示；候选选择序号不是用例编号。
- 已在本次任务明确指定文件、链接、模块对应唯一来源，或要求继续已选资料时，列出采用来源后直接读取，不重复要求选择。历史对话中曾测过某模块不等于本次已选。
- 若项目存在 `文档/测试文档/需求文档`，先递归列出该目录下全部文件名称和相对路径，再把其中包含飞书链接的文件作为候选供用户单选、多选或全选；只有收到选择后才解析所选文件内的链接。该目录不存在时，才回退到全项目发现。
- 优先用 `scripts/discover_sources.py --project <项目绝对路径>` 只读生成资料目录；按项目索引和脚本报告的未解析项补查，不能把辅助脚本结果当全文读取证明。不得用截断列表冒充“所有文件”。
- 选中链接文件默认读取其全部有效需求链接；用户明确点选文件内条目时只读所选条目。同一目标去重读取但保留每个来源映射。选择一个文件不授权递归下载整个飞书 Wiki 或无关引用。
- 选择后通过**飞书 CLI `lark-cli`**读取实际最新需求；先读取与当前 CLI 匹配的 `lark-shared`、`lark-doc` 及 fetch 说明，按引用类型补读相应 skill。这里的 CLI 登录只用于只读获取需求正文，不替代本 Skill 启动时的提单授权；CLI 已登录就直接读取需求，不重复申请需求正文读取授权。缺权限时只处理准确的认证缺口，继续已可读资料。
- 正文、表格、图片、画板、附件及直接承载规则的嵌入资料都要核对；只拿链接、目录或文本摘要不算读完。记录文档标题、URL、revision、获取时间和缺失项，再按§1～§5生成用例。阅读失败的需求不能静默消失或用旧副本冒充最新。
- 本次仅要求修改 skill 时只完成技能更新与验证，不因此启动选择或用例生成。

### 1. 读取完整资料并确定范围

- 开始读取及交付前必须按 [references/media-coverage.md](media-coverage.md) 建立并校验 `source-coverage.json`。从未经裁剪的来源快照枚举媒体，再逐项记录实际读取证据及“来源位置 → 规则 → 用例”的映射；没有媒体也必须显式登记空清单。下载成功、alt、OCR 或只看缩略图均不得冒充已读原图；视频不得只看封面或单帧。读取失败只限制直接受影响规则，继续处理其余明确需求。
- 使用§0已选来源，读取总表及其适用的模块、规则、配置文档；不只读摘要，也不扩展到无关目录。旧测试文档用于需求映射、回归和去重，不能单独证明当前需求预期；若本次只有旧用例则先定位其关联有效需求。
- 对 DOCX 同时核对正文、表格、图片、文本框、内嵌对象和附件关系；图片中的文字、标注和流程也属于需求。仅提取正文不算完整阅读。引用视频、链接或内嵌 Excel 无法读取时，记录具体缺失内容及受影响需求点，不声称已看。
- 区分当前有效条款、明确被替代的历史条款、直接耦合规则、实现配置基线及推测。按用户指定版本和明确变更说明定优先级；没有明确依据的正文/图片/历史冲突交策划确认，不静默选一种。
- 用户已明确本次版本采用的规则优先于相反历史条款；这是旧规则被替代的依据，不应仅因新旧不同就把当前规则再次挂起。只有当前权威不明或同一有效版本自相矛盾时才列冲突。
- 历史资料只按当前变更的直接关系纳入，例如共享入口、奖励库存、失败复活、支付、存档或弹窗顺序。记录耦合依据；不能因为历史对话提过某功能，就自动加入本次回归。
- 缺当前需求时停止该来源及受影响规则的设计并指出缺失；多来源任务继续处理其余明确需求，不因单份读取失败停止整批。缺历史资料只限制相关回归，不阻断已有明确需求；缺配置时保留符号阈值及待补数据，不编造数值、字段、开关或业务限制。

### 1.1 默认反查代码与本地历史耦合

先独立提炼当前需求断言，再反查代码，避免把实现中的错误抄成期望。有项目路径时必须完成本阶段；具体检索与准入规则见 [references/coupling-analysis.md](coupling-analysis.md)。

- 从当前变更的入口、配置、事件、状态、存档和资源出发，追踪调用方、读写方、订阅者及最终消费点；只搜同名功能不算完成。未给比较基线时不猜测修改范围，也不默认读取全仓库历史。
- 自动检索已知项目及资料目录中的旧需求、旧用例、缺陷和本地可用历史；不扫描整个用户目录、不访问未授权远程服务、不拉取 Git。没有找到旧文档也继续做代码耦合分析，不要求用户每次重发。
- `耦合分析` 记录：`耦合项 ID | 当前覆盖项 | 影响模块 | 关联符号与位置 | 传播路径/触发条件 | 历史资料及版本 | 证据类别 | 风险及依据 | 测试决策 | 关联用例/参数/测试 | 排除或待确认原因`。
- 只有行为可能受影响且有可达路径的候选进入回归。共享字段的只读消费者也可能受影响；不能以“只读引用”排除。代码证明影响时，不因缺历史文档或风险较低而删除；仅名字相似、无行为传播关系的引用不扩写成用例。
- 历史规则与当前需求相容时继承；已被明确替代的规则更新。代码只能证明依赖和实现基线，不能单独证明产品意图。缺业务策略才列具体待确认；探索性候选不应批量变成“需求待确认”。

### 2. 先建覆盖模型，再写用例

必须同时遵守 [四维覆盖契约](coverage-contract.md)。下面的覆盖项复用同一账本和 ID；需求、耦合、边界及版本升级分别审计和统计，不能用总用例数替代任何一维的覆盖证明。

在 `覆盖核对` 逐条建立稳定的覆盖项 ID，并记录：

`覆盖项 ID | 来源文件及位置 | 范围类别 | 需求点/规则 | 适用状态与边界 | 关联用例及参数场景 | 覆盖状态 | 缺口或不适用依据`

- ID 使用按类别递增的短码，例如 `REQ-001`（当前需求）、`REG-001`（耦合回归）、`CFG-001`（配置/数据）、`BDY-001`（边界/状态迁移）、`TRN-001`（待确认）。一个覆盖项表达一个可判定规则或风险，不按段落数、字段数机械拆分；同一规则的等价数据行可归为一个数据审计覆盖项，并在审计清单中逐项核对。
- 覆盖状态仅用已设计、部分覆盖、待确认、未覆盖、不适用。只有关联了可执行用例或明确的数据审计记录才算已设计；待确认、未覆盖、不适用不得计入已覆盖分子。不适用必须写出需求逻辑为何不适用，不能只写“本次不测”。
- 生成用例时，每条用例及参数实例都要反向关联一个或多个覆盖项 ID。用例可增加辅助追溯表，不改变用户指定的主表结构。

- 来源位置用章节、段落原文摘录、表格行或图片标注，只有文件名或模块用例数不能证明覆盖。
- 范围类别区分当前需求、相关历史回归、实现配置基线、待确认风险。覆盖状态用已设计、部分覆盖、待确认、未覆盖、不适用，不用测试通过代替。
- 将每个功能的入口、资格、输入、规则、状态变化、输出和禁止行为变成可判断的断言。一个条款可以映射多条用例，一条用例也可承接同一流程中的多个明确断言。
- 对状态型功能建立状态/迁移清单：合法和禁止迁移、首次及重复触发、终止后操作、跨期与恢复。对多条件规则建立决策表，保留条件同时命中、均不命中和优先级冲突。
- 下列维度是审查清单，不是用例生成模板。逐项标记适用/不适用/待确认，并记录覆盖项 ID 或不适用理由；不能机械地对所有模块套全套，也不能只因需求未逐字写出就跳过有直接因果关系的边界。无因果关系的维度不扩写成用例。

| 维度 | 核对重点 |
| --- | --- |
| 阈值与数据 | 最小/最大、阈值前/等于/后、空集合、重复项、排序、去重、溢出、枚举映射、单位与累计/增量语义 |
| 配置 | 默认、缺字段、整个缺省、null、显式值、非法值、实际读取路径、最小配置合并、多个条件优先级、期内变更与冻结 |
| 时间 | 到期前/等于/后、边界前入局与后入局、跨日/周/年、时区与时钟来源、错过窗口、切后台/重登 |
| 流程与中断 | 成功、失败、取消、重试、退出、复活与重开区别、多入口、回调重复/乱序、可达并发、流程中途强杀 |
| 奖励与持久化 | 获取资格、发放、到账、核销和演出分别何时发生；幂等、回退、丢失与补发；状态写入之间的中断 |
| 版本与账号 | 真实旧版本存档、无字段/旧字段、未解锁/进行中/已完成未领奖、配置迁移、重装、切账号、云档/多设备冲突 |
| 表现与交互 | 入口、文案、图标、倒计时、红点、按钮、导航、遮罩、滚动、动画/音效、长文本和适用设备适配 |
| 相关系统 | 同时领奖、弹窗/底栏优先级、共享库存/体力、广告或支付成功/失败/取消/无填充；仅纳入存在关系的系统 |
| 埋点与生成数据 | 文档要求的触发时机、字段和来源；配置逐行、导表、资源映射及运行消费一致性 |

- 非法输入、迁移或恢复没有约定行为时，区分可明确判断的安全不变量与需要策划选择的业务策略。不得自行规定“必须回退1天”“必须清档”或“必须补偿”。
- 将确定断言落为可执行用例，将未定策略单列待确认；主表期望不得混入“结束或循环待确认”等互斥结果。局部缺资料不妨碍其余明确边界的设计，不能把可直接推导的边界一并推给策划。
- 只有权威需求冲突，或关键规则未定义且不同答案会改变验收结论时，才列为需求待确认；缺少无关资料、旧资料或某一参数值不能扩大成整组用例待确认。对仍有明确预期的断言照常生成用例，对缺资料部分写清受影响覆盖项、缺失材料和解除方式。
- 设计阶段不得用“需真机/待确认”代替可完成的需求推导。先从当前有效需求、适用的历史规则、配置定义和流程因果关系判断；只把确实依赖运行观察的表现或时序断言标为运行验证。任何待确认项都要写出不同解释及其对预期的影响，不写空泛问题。
- 升级场景必须注明旧版本及状态如何产生；仅推测可能存在的旧字段或存档列待确认风险。不要因尚未取得旧包就把潜在高风险从覆盖清单删除。

### 2.1 为断言分配最低充分验证层级

| 层级 | 验证范围 |
| --- | --- |
| L0 | 需求与契约一致性检查，仅属设计/静态分析，不冒充执行 |
| L1 | 纯逻辑、边界和单元测试 |
| L2 | 状态迁移、配置全量审计、存档与数据映射测试 |
| L3 | 编辑器、PlayMode、场景或模块集成测试 |
| L4 | 仍依赖真实设备、实际渲染、平台生命周期或真实 SDK/服务的观察 |

- 默认静态模式逐项记录证明路径；上表仅区分实际运行层级，不要求为了填满 L1～L3 额外运行。按断言分流，不按整条用例分流；静态已闭合的本地逻辑不要求人工原样重跑，真实接入与设备表现另列。
- 默认静态模式直接代入时间、关卡、配置、随机范围及网络/SDK 回调参数。动态模式中，时间采用可控时钟/调度器，关卡采用状态构造/测试存档，配置采用测试覆盖，随机数采用种子/可控序列，网络与 SDK 采用依赖替身；先查已有入口和框架支持的替换，不能只因没有显式注入接口就判“需开发补测试接缝”。
- 不能用改阈值、放宽条件、复制业务算法来伪造测试。注入输入后仍调用真实判定及生产消费链；在隔离环境构造状态并清理，不能直接改正式账号、线上配置或系统时间。状态构造不替代产生该状态的关键迁移测试。
- `验证分层` 记录：`覆盖项 ID/断言 | 关联用例/参数 | 层级 | 测试类型 | 目标代码与版本 | 输入构造/替身及隔离恢复 | 所需测试接缝 | 测试文件/测试名 | 执行命令 | 执行状态/证据路径 | 黑盒保留原因 | 未覆盖原因`。设计阶段未知的路径/命令明确写待生成或未核实，不能编造已存在文件。
- 静态代入时间、关卡和状态时不要求真实等待或通关，也不要求注入接口；可另提供按§2.2编写的黑盒复测路径，注明GM或自然等待条件，它不构成人工待办。只有明确要求动态运行时才检查相应接缝和宿主。环境缺失、需求不清、材料缺失分别记录，不混为接缝缺失。
- 分层时先检查已确认项目根目录的 `QA/` 及原生测试，映射已有文件/测试名，区分复用、需修改和待新增。新白盒测试的计划位置为根目录 `QA/`，已有正式原生测试保留并引用；待生成路径不能写成已存在文件。
- 需要生成或执行白盒测试时衔接 `test-whitebox` 的“项目级 QA 测试资产”规则，在 `QA/` 中增量维护可复用的测试脚本、夹具、复跑及报告生成入口，不每轮另起一套，不把编译缓存和临时工程列为长期交付；仅设计用例不创建空 `QA/`、不自动修改业务实现或执行测试。设计状态与执行状态分别统计。

### 2.2 为可黑盒执行的场景写出可照做的步骤

联用 `test-codetest` 默认交付代码初步质量，静态证据充分即可判定，不要求每条必须运行。L1～L4 是验证建议，不能把尚未运行自动变成代码未通过。联用 `test-whitebox` 时实际执行状态仍如实记录，不用静态代替动态。

外部验证设计须指出外部独有变量、为何本地推导/替身不足、实际入口及最小观察值；缺环境、缺账号或未查完代码不是转人工理由。详细黑盒步骤是可选复测路径，不要求使用者重复全部本地检查。

生成或更新用例时，逐条判断是否存在从产品入口可达的黑盒路径；存在就写入主表，不能只留下方法调用或状态描述。编写此类步骤时读取 [references/blackbox-steps.md](blackbox-steps.md)。提供黑盒复测路径不改变最低验证层级，不要求已自动验证的逻辑全部改由人工重复验收。

- 在`前置条件`注明“普通操作可执行”“需GM/测试包辅助”“需受控SDK/网络环境”或“仅内部探针可构造”，并说明已核实的依赖；自然路径可达但难稳定命中时注明偶发及命中条件。不能把代码可注入等同于测试人员能在界面操作。
- 若前置依赖真实账号或线上后台，明确标注“需测试人员准备后台数据”，列出字段和值和准备后核对项；不得写成“AI 设置账号”“自动修改后台”。若只有本地夹具可构造，则标注“仅本地自动化，不代表真实账号验收”。
- 混合场景拆成两层：本地可控状态机/计算断言写入自动化用例；真实账号、线上状态、SDK、设备或平台表现另列黑盒步骤。不要复制同一断言凑数量，也不要把本地 fixture 的通过结果包装成整条真实环境通过。
- 账号准备写清平台/包条件、关卡与解锁状态、历史付费/领奖/活动状态，以及是否需要新账号、清档或保留原档。清档不是默认方案；需要干净历史优先使用独立测试账号，重启补单、升级和恢复链必须保留原账号/原档。设计这些操作不代表已执行，也不授权清除用户数据或真实付费。
- `操作步骤`从实际页面/入口开始，逐步写“在哪里 → 做什么 → 输入什么 → 何时做下一步/观察什么”；单元格内按顺序分行，必要时可用步骤序号（不是用例编号）。涉及开关/GM时核实名称、模式、值、单位及生效方式；不能只写“构造成功回调”“切换状态”“模拟异常”。
- 时间和乱序场景写清时间来源、时区（适用时）、起算事件、动作先后、页面是否保持打开、是否杀进程/重登，以及等待结束或条件已命中的判断依据。需要等待时写已核实的超时判据；只有建议观察时长则标为测试设置，超时未命中前置不能直接判产品失败。重试要区分同一订单/同一期与重新购买/新一期，不能用不同对象代替目标链。
- `期望结果`分开写界面可观察结果及必要的日志/后台断言；同一行可标“界面可验”“需日志确认”。字段值、累计倍率、核销次数或落盘状态若没有可用观察入口，不冒称肉眼可确认；奖励到账不能代替付费身份更新，页面关闭不能代替持久化成功。
- 对依赖耦合结果才能观察的场景，补上重新进入消费者的动作及有区分度的观察点，例如补单后重新打开礼包；先确认所选配置下正常与异常的显示确实不同。广告未播放还可能受缓存、保护期等限制，不能只凭没播就认定间隔规则生效。
- 未找到已存在的GM、SDK模拟或查价控制入口时写具体缺口及最小所需能力，保留可执行部分，不虚构按钮/命令，也不将断网、改手机时间或快速杀进程描述为必然命中特定内部时序。仅内部探针可构造的场景保留白盒步骤，不强造黑盒教程。
- 参数场景和耦合回归采用相同标准；主表单行复制后应能完成关键操作，不以“同上/见另一页”省去账号、动作顺序或预期。已知缺陷的异常表现放既有执行/缺陷记录，与正常期望分开，并标明推导、探针已执行或真机已复现，不能将设计步骤说成实测复现。

### 3. 选择粒度与参数化

- 按风险、状态或判断分支拆分，不按每个名词强制拆行。不同前置状态、触发路径、权限、事务边界、恢复方式或独立失败原因通常独立覆盖。
- 每条用例/参数实例应能说清覆盖了哪个覆盖项，以及相对已有用例新增了哪个断言或风险。语义键为 `覆盖项 + 前置状态 + 动作顺序 + 输入等价类/边界 + 预期状态/输出`；若与已有场景语义相同，不能仅靠改标题、换数据文本或换模块名新增一条。
- 对大批量配置、奖励、枚举或资源映射，分开管理“逻辑用例”和“数据审计”：逻辑用例验证加载、选择、消费等行为；数据审计逐条核对有效记录、字段映射和异常记录。不要为每条静态记录复制完整操作步骤，也不能用抽样逻辑用例冒充全量数据核对。记录总数、核对范围、异常行和映射证据。
- 同一次操作、相同前置条件下能逐项观察的关联断言，可以放同一条用例；各断言写清，失败仍能定位。不要把所有表现混成“页面正确”，也不必将同一个静态页面每个控件机械拆行。
- 逻辑断言与只能运行确认的表现断言可拆分，或在期望中明确分段，便于后续分别判定；不能因为字体需要真机就让文字内容也失去静态结论。
- 同一规则仅输入不同，先参数化设计再按下游消费方式展开。默认把必要实例放在同一主表，各行保留独立前置、输入、步骤和期望，不用“同上”迫使读者跳表；公共规则与来源在机器账本复用。用户指定参数表才单列，每个实例仍可独立执行回填。
- 参数化减少重复描述，不减少必要测试实例。奖励明细、商品价格、枚举映射等逐条数据仍核对全部有效记录，不能以“随机选一档”代替。首项、末项、特殊类型、不同奖励路径和不同边界行为保留独立逻辑场景。
- 等价类需有规则依据：只有行为与风险相同才能抽代表值；边界值和特殊分支不能被普通代表值替代。多条件可用决策表、成对组合或正交法，但有已知依赖的多条件同时命中、顺序冲突及高风险组合必须额外覆盖，不声称成对覆盖等于全组合证明。
- 对互不影响的条件，先分别固定其他条件为满足态，命中本条件前/等于/后；再补确有交互风险的组合。不默认把时间边界×全部等级×全部配置做笛卡尔积；若需要组合，每个实例说明相对已有实例新增的条件交互或风险，不能只靠参数化隐藏冗余。
- 参数实例含状态迁移时，每行说明初始状态或重置方式，防止前一个参数执行后污染下一个。

### 4. 语义去重与历史清理

对主表、参数场景和耦合回归做跨表比较，使用以下语义，而不是只比较标题：

`需求规则 + 前置状态 + 触发动作/顺序 + 输入等价类/边界 + 预期状态/输出`

- 全部相同或一条完全被另一条承接且无独立风险时，合并并保留所有来源映射。只换标题、数字写法或模块位置不产生新用例。
- 部分重叠时抽公共步骤或移除重复断言，保留独特断言；相同 Bug 可影响不同真实路径，不能因根因相同就删掉独立路径回归。
- 删除/合并后反查覆盖矩阵：任何需求点、边界、状态迁移、特殊参数都不能失去承接。拿不准等价时保留并注明差异，不盲目压缩。
- 更新旧表时，按当前来源将每条旧用例归为保留、更新、合并、废弃或待确认，在 `变更核对` 记录原因及替代用例。只有明确版本变化/废弃证据才删除旧规则；历史 Bug 的仍适用回归不因已修复就删掉。

示例：进度1、首箱2未领、失败退出回0，与“首箱前失败回起点”在相同前置下是一条场景。进度3回到已领保护点2、退出与重开、普通箱与末箱则不能只因都涉及失败或领奖就合并。
