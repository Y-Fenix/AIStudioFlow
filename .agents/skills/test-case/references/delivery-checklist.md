# 用例审计与交付核对

按当前阶段读取对应小节，不默认全文加载。下文 `scripts/` 路径相对于本 Skill 安装目录；§ 编号保留原流程含义。

### 5. 反向审计与交付

生成后单独做一次从原需求出发的反向审计，不只复读已生成用例：

- 必须按 [四维覆盖契约](coverage-contract.md) 运行 `scripts/validate_design_coverage.py`，保存 `validated-coverage.json` 及实际命令/退出码；需求、耦合、边界和升级分别有分母、映射及缺口。联用时传递同一账本及输入哈希，不重建另一套。门禁不能发现从未登记的语义遗漏，仍须反向审计原文和媒体。

- 必须运行 `scripts/validate_source_coverage.py check`，将原始快照、媒体清单、读取回执、规则与实际主表行对账，保存本次命令、退出码及摘要。素材缺失、未读、版本漂移或规则未覆盖时，不得交付标称完整覆盖的正式结果；外部取证确实受阻时可明确交付阶段结果并列缺口，不得删来源、删规则、伪造回执或批量改绿绕过。联用 `test-codetest` 时传递同一账本及 SHA256，不能仅传 Excel 丢失图片来源。
- 每个明确条款、图片规则、配置记录是否有承接？各适用维度是否有测试实例或有据可查的不适用理由？
- 检查实际测试输入是否命中所声称的边界。例如仅测“保护点后回退”不能代表“恰在已领保护点失败无损失”；边界标签不等于已设计该场景。
- 每个用例/参数是否有真实来源或明确风险依据？是否夹带旧版废弃规则、实现即预期、不可达前置或未经确认的产品策略？
- 每个待确认项是否写出权威冲突/缺失规则、不同解释导致的验收差异、影响范围和解除方式？待确认项可以登记为风险已识别，但不得算作规则已覆盖或用例已设计；其下可验证的安全不变量及其他明确断言仍应单独设计。
- 覆盖账本是否闭合：每个适用覆盖项有用例/数据审计承接或标为未覆盖；每条用例有覆盖项依据；所有待确认和不适用都有独立依据。覆盖率分子只计已设计项，待确认、未覆盖和不适用单独列示，避免分母口径把缺口藏掉。
- 若用参数化/批量数据审计，是否有实例清单、执行或核对总数及异常明细？不得因用例条数少就宣称覆盖完整，也不得把数据行数量误报为独立用例数。
- 仅设计时分别报告设计实例数与执行数（默认为 0）；尚未执行的数据审计只写核对范围/计划记录数，不能伪造实际核对结果或异常明细。
- 删除/合并后的覆盖关系是否保持？参数表是否可独立执行、定位与回填？是否出现主表和辅助表重复计算？
- 已从代码读写、事件、配置及持久化关系反查历史耦合吗？每个纳入/排除的候选有证据和决策吗？缺历史文档不能伪装为无耦合。
- 每个明确断言是否有静态证明计划，或确需动态/外部观察的具体理由？静态覆盖不等于运行验证。不得因为没跑 L1～L4、缺宿主/账号就把可静态代入的时间、关卡、配置、旧存档或 SDK 回调转人工。
- 逐条核对字段可执行性、标题无编号、语义重复、来源映射和表格显示。缺口能在当前范围内补齐则继续补；需外部信息则明确保留，不用堆行填补。
- 对有黑盒路径的用例做一次“只拿主表这一行能否照做”的审阅：账号/清档要求、真实入口、具体输入、时序命中依据及界面观察点是否齐全？内部断言是否与界面结果分开？需要GM/SDK控制是否已有证据？缺口不得靠“模拟异常/验证正确/同上”掩盖，设计步骤也不得标成已实测复现。

交付报告分别说明需求点、耦合、边界、版本升级四维覆盖及各自待确认/未覆盖项和资料限制。需要报数量时，将公共用例数、参数实例数、相关回归数分开，明确口径，不相加伪装成独立用例数；需求总量包含未明确/未覆盖项，不用缩小分母制造100%。

只在覆盖矩阵证明范围内无缺口时说明“已覆盖本次已明确需求及适用边界”；不能仅凭条数、标题唯一或格式检查宣称绝对不漏。用户未请求执行时，所有结果只表示设计，不填写测试通过。

### 当前对话简报（必须）

每次运行结束，必须在当前对话的最终回复中简短汇总，不能只提供文件链接或让用户自行打开报告。说明本次需求范围、实际设计用例/参数实例数、主要覆盖缺口及结果文件；未执行测试时明确写“仅生成用例，未执行测试”。数量以本次实际产物为准，无可靠统计时如实说明，禁止猜测。

同时列出已选来源数、全部来源已读/总数、各类媒体已读/发现数及未覆盖规则数；媒体按引用位置统计，不与独立用例数混算。图片或视频有未读时直接说明受影响内容，不用“文件已解析”掩盖；已完整读到的重复示意不强行新增用例凑条数。

联用其他测试 Skill 时合并为一份简报，不重复汇报。区分本次新结果与沿用的历史结果，不把未重跑的旧结果说成本次执行结果。
