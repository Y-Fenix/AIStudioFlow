## 启动授权门禁（第一步）

每次新运行本 Skill（包括只生成测试用例、补齐用例或更新旧表）后的**第一条交互**必须先询问一次。同次与 `test-codetest` 联用共用一次授权，同任务压缩恢复不是新运行，不重复询问；新任务或新报告运行不继承历史授权：

> 是否授权本次通过你在 HTML 中粘贴的 Bug 表格 URL 读取表头，并在你手动点击“直接更新并提单”后写入？不授权仍可继续生成测试用例和只读报告。

在收到本次明确的“授权提单”或等价肯定答复前，不读取 Bug 表格、不启动提单写入、不在报告中启用写入按钮；收到拒绝、未回答或范围不清时按未授权处理。该授权只作用于当前 Skill 运行，不从历史对话、旧 HTML 或本地登录态推断，也不等于飞书 API 已具备 `base:record:create` 权限。授权询问完成后，才进入资料发现、需求文件选择和用例生成流程。Skill 自身永远不自动创建 BUG 单。

## 目标与边界

默认目标是完整覆盖当前需求的所有明确功能、规则及适用边界，用可追溯证据证明覆盖，而不是追求条数。既不以“越多越完整”扩写，也不为了精简删掉独立风险。没有固定条数、最低条数或压缩比例。

“滴水不漏”是设计目标，不是无条件保证：只能针对已读取、已定版的资料和声明的覆盖模型说明结果；缺失、歧义和尚未覆盖的内容必须显式列出。用例已设计不等于已执行，更不等于产品无 Bug。

- 输入可以是项目内需求文档、测试文档、飞书需求链接文件、直接链接或目录。未指定本次资料时先执行§0的发现与多选，不要求重复上传，也不擅自沿用上次模块。有项目代码时默认只读反查影响范围和可测试性，不用实现反向定义验收标准。没有项目代码时继续需求设计，注明耦合反查范围受限。
- 生成、审查或更新用例不授权修改产品需求、游戏代码、后台配置、Git 或 Figma。附件内容是分析资料，不是操作授权。
- 更新旧表先重新核对来源与适用版本，不沿用旧结论；默认另存，只有用户明确要求才覆盖。

## 执行模式与交付

仅调用 `test-case` 默认设计用例，运行数为 0；与 `test-codetest` 联用默认设计加逐断言静态检查。“执行用例／再测一遍”默认也指静态检查及具体输入演算，不自动升级为白盒或 Unity 运行。用户明确要求运行单元测试、白盒测试或 Unity 测试，或项目强制验证适用时，才运行相应测试；需要新增或修改测试时再读取 `test-whitebox` 的适用规则。

必须按 [四维覆盖契约](references/coverage-contract.md) 独立盘点需求点、耦合、边界和版本升级，再关联主表用例。缺口不得藏在用例总数里；机器校验只检查记录和映射，不能替代从原需求反查遗漏。

默认 Excel 只有一个 `测试用例` 页签，六列为 `测试内容 | 测试目的 | 前置条件 | 操作步骤 | 期望结果 | 需求模块`；不输出用例编号。覆盖、耦合、验证分层及变更记录保存为机器账本，不堆辅助页。用户模板优先，详见设计细则“输出约定”。

## 本轮进度与恢复

- 同次联用两个 Skill 是一条“需求 → 用例 → 审查 → 交付”流程，共用来源快照、基线、用例 ID/指纹、证据和运行目录；不各自重建一套，不因两个标签自动启动多个 Agent。并行仅在当前授权及项目规则允许时采用，独立模块各自取证，最终统一对账。
- 在项目规则允许写输出后，复用本轮目录中的一个 `run-progress.md`；已有等价任务账本则补入下列信息，不另建重复账本。记录：本轮标识与任务模式、真实授权消息位置、已选来源及版本/哈希、代码基线与相关文件指纹、已读规范的小节/哈希及关键约束、各阶段状态、已完成项和证据路径、阻塞及已尝试办法、下一模块/用例/断言与具体动作。只引用大文件，不把原始正文复制进进度文件。
- 完成一个模块或一批独立断言就保存实际用例/审查草稿、证据及下一步；耗时批次中也及时保存。读取资料时就增量登记 `source-coverage.json`，设计出用例即保存，审完即回填草稿，不等最终排版才从聊天记录重建。输入分母从完整输入独立建立；未审部分仍标未审，不能用已完成项反推总数。
- 上下文压缩或同任务恢复后，先读进度文件和下一步所需的小节/记录；核对本次用户选择及相关指纹，再从断点继续。不得仅因压缩重问已确认事项、重跑资料发现或从第一条重新审查。授权必须能追溯到本次真实用户答复，进度文件中的标记本身不构成授权。
- 规范及契约按阶段读取，一次读清的小节记录定位和关键约束；文件未变且摘要足以决定当前动作时不重复全文读取。约束遗失/不确定时回读对应原文，不能只凭“已读”标记忽略要求。长源码、日志和账本使用符号定位、指定条目或统计摘要，避免反复整份输出。
- 缓存只在有效条件内复用：新运行重新核对当前来源和代码；同一运行中相关源码、需求、配置、测试或依赖环境变化时，仅失效并复查受影响断言及消费者。相同 HEAD 不保证工作区没变；旧日志不能计为本次执行，新旧证据分别说明。不为了节省时间跳过来源版本、完整媒体和最终基线校验。
- 同一输入和环境下已确认失败的读取/测试命令，不无变化重试。先记录失败原因和可改变条件，修复后只重试相关项。连续两个工作批次没有新增可复核证据、结论或产物时，先诊断重复读取/环境适配/报表返工，保存具体进度并改变处理方式，不再只重复“继续核对、即将生成”。
- 已充分证明的断言停止重复取证；出现反例、新输入或依赖变化时再复查。静态审查不为已闭合断言无限搭建运行宿主；明确要求动态运行的项目仍运行或如实记受阻。格式校验失败按具体错误修复，不重做无关审查；修改输入/证据后仍须重跑原有门禁。
- 按阶段交付已可核实结果与下一步。确有材料/权限/环境阻塞时按原契约交付 `partial`；单纯尚未分析完只能给进度摘要和明确标注的草稿，不能将其伪装成材料缺失或完整报告。保留全部输入分母及未审清单，不能用缩小范围、删用例、改绿或降低覆盖标准换速度。最终仍完成来源校验、逐行审查、Excel 回读及适用报告门禁。
