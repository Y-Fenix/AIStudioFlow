# 黑盒复现步骤规范

## 何时保留人工黑盒

先拆分断言。静态可证明的规则和本地可控的状态、时间、配置、随机序列、回调顺序优先静态/自动化验证。真实设备表现、真实平台/SDK行为、真实服务端合同或下发、可信已发布版本差异等本地无法证明的部分，只保留具体外部事实；有明确验收请求或准确玩家路线时，再附人工黑盒步骤。账号、网络、资源处理的客户端逻辑仍须本地完成。

没有显式测试接缝时，先检查现有 adapter、构造器、存档沙盒、假时钟、GM/测试入口和自动化框架。缺接缝写成具体开发缺口，不能伪装成“必须真机”。依赖或许可证问题写成自动化受阻，不转人工黑盒。

覆盖安装和卸载重装场景先执行[升级与重装协议](upgrade-and-reinstall.md)，逐功能区分旧/新版本、账号身份、旧状态、真实卸载与本地数据模拟；本模板承载具体操作和观察点。

## 报告先让测试人员看懂

静态检查默认由 Agent 完成，不要求每功能都造玩家操作。正常项展示已查场景、结果和源码证据；问题项提供“初态 → 输入/调用顺序 → 推导或运行结果 → 异常依据”的白盒步骤。只有确有准确玩家路线时，才按下文生成黑盒复现，作为可选复核资料；不把它列成完成静态检查的前置条件。

区分正向回归方案、条件风险验证、研发/SDK联调与已执行复现。条件风险写明必要触发条件；不能把“断网”“快速点击”等未经证明的动作编成必现步骤。普通点击无法触发时，说明由哪个受控入口准备及谁提供；缺入口就醒目标“尚无完整黑盒步骤”，列具体缺口，不能拿通用套话凑完整用例数。准备步骤仍有缺口的草案也不能记为完整可执行。

写出验证方案不代表已经执行，也不需要为了写步骤真的安装或卸载。升级与重装默认仍是三种数据条件的静态分析。

## 可执行步骤必须具备

步骤应尽可能从已查到的项目资料推导：精确到模块文档中的页面/控件、GM 或受控测试入口、配置键、关卡号、状态变化和观察点。不要用“正常操作”“模拟异常”“同上”代替步骤。若资料只确认了实现路径、没有说明用户可见操作，不要猜页面或按钮；改用已知的受控入口，或标明还缺哪条操作信息。

每个场景都要让没有参与分析的测试人员能够准备、执行、观察和恢复。按实际风险填写：

1. **场景与目的**：唯一 ID、要验证的规则/缺陷、相关来源和断言。
2. **版本与环境**：客户端包/构建号、平台/设备/系统版本、网络/商店/SDK环境、服务端/后台配置版本或快照。未知字段写“需测试负责人提供”，不得猜。
3. **数据前置**：账号类型、等级/关卡、存档/订单/活动状态、配置和资源。标明由谁通过何种受控入口准备，成功后如何核对。不要让 AI 改真实账号或线上配置。
4. **初态与清理**：每例独立起始状态、账号/关卡/存档复位办法、执行后如何清理，以及不可复位的数据风险。
5. **逐步操作**：每一步只写一个动作；具体页面/按钮/输入值/顺序，必要时写定时依据和等待条件。不要用“正常操作”“模拟异常”“同上”替代步骤。
6. **观察点**：每步期望看到的文字、数值、页面/动画/回调/订单状态、服务端或日志字段，以及应保存的截图/录屏/日志。把 UI 观察与业务到账/落档断言分开。
7. **结果栏**：预期、实际结果、执行人、时间、设备/包、证据路径、结论。未执行时实际结果留空，结论写“待人工执行”。

## 输出模板

```text
场景 ID / 标题：
验证规则与来源：
验证边界：真实账号 / 线上状态 / SDK / 商店 / 设备表现（说明具体变量）
版本与设备：
账号与数据准备：
配置/网络/时间前置：
初始状态核对：
清理与恢复：

步骤：
1. 操作：
   等待/触发条件：
   预期观察：
   证据：
2. 操作：
   等待/触发条件：
   预期观察：
   证据：

业务状态预期（到账/存档/资格/幂等）：
实际结果：未执行 / 由执行人填写
结论：待人工执行
异常处理与安全恢复：
```

若关键信息缺失，仍输出已知部分步骤，并在前置列出精确缺失项、受影响断言和解除动作。不得生成看似完整但无法命中目标状态的流程。设计步骤不是实机复现证据。

缺少真实账号、服务端权限、设备型号、测试包或线上配置时，把每项分别列为“需测试负责人提供/准备”，并说明阻塞的断言。不要因此省略本地可执行的预检；也不要把测试准备事项写成已经执行的结果。
