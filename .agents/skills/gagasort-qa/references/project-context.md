# GagaSort QA 项目知识路由

本文件维护的是查找路线，不复制项目的业务规则、完整测试表或历史缺陷库。每次任务读取当前有效来源，不凭记忆复用上次结论。

无参数时从索引和实际入口发现全项目功能，按模块读取，不只按用户提供关键词或当前 diff 定范围；发现与报告协议见[全项目巡检](full-project-audit.md)。配置专项入口见该协议，数据归属、迁移/初始化与逐功能静态影响矩阵见[升级与重装回归](upgrade-and-reinstall.md)。

## 按需读取的权威来源

1. 在仓库根运行 `tools/agent-task preflight`，按输出读取最近的目录 `AGENTS.md` 和精确命中的开发文档章节。
2. 从`文档/开发文档/模块定位索引.md`（模块定位索引）按业务关键词定位模块，再读取模块正文。涉及奖励、权益、支付、存档、时间、进度目标、配置或页面生命周期时，补读索引 §1.1 命中的共用准则；不要把模块特例推广到其它模块。出现测试失败或已报告缺陷时，还必须查模块文档中的“验证／限制／历史结果”等章节及其链接的相关实施记录，不能只读规则章节后就断言历史未知。
3. 需求实施、业务行为边界、Bug 修复和角色分工分别遵循`文档/开发文档/需求实施工作流.md`（需求实施工作流）、`文档/开发文档/Harness工程规范文档.md`（Harness 工程规范 §5.1/§5.3.2/§5.3.3/§5.4/§7）。初次定位已索引 C# 时按 Harness §5.3.2 使用当前会话可用的 CodeGraph；不可用时记录原因后做有界回退。
4. 测试落点有三个不同来源，必须交叉核对：
   - `tools/agent-task-rules.txt`（tools/agent-task-rules.txt）：路径到测试类／方法及验证档位的正式映射，多个命中路径取并集。
   - `文档/开发文档/业务自动化测试运行说明.md`（业务自动化测试运行说明）：成熟脚本的实际覆盖、依赖、替身和人工残留。
   - 当前仓库确有 `QA/README.md`、`QA/run.py` 时，再读其说明并执行 `python3 -B QA/run.py --list`：统一入口已登记的测试套件、结果格式和运行边界。缺少时从正式 tools/原生测试发现入口，不访问不存在的路径或宣称已执行 Runner。该清单只说明已登记内容，不是项目全部测试的穷尽清单。
5. 查具体断言时，沿模块文档中的测试章节进入 `GagaSort/Assets/Tests`、`QA/tests`、`tools/test-*.py` 或 `pub/**/tests`。核心玩法另读 `文档/开发文档/核心玩法/白盒测试/` 的适用文档；回放输入默认使用无表现回放器。
6. 使用 QA Runner 后读取本次 `report.json`，核对选中套件和各自退出码、真实计数、输入哈希、`baseline_changed`、`changed_inputs_during_run` 及证据目录；单看终端摘要或总通过数不足以确认完整结果。

运行 `tools/` 下任何脚本或查看其映射前，先读 `tools/AGENTS.md`（tools/AGENTS.md）；Unity 测试源码命中其他目录约定时，按 `preflight` 继续读取最近的 `AGENTS.md`。路径映射只给最低门禁，业务文档仍需核对本断言的实际边界。

## 常见误判边界

- 小型审查可由当前 Agent 直接完成；根 `AGENTS.md` 或 Harness 明确要求独立测试、Review、UI 复查或核心机制管线时，按可用项目角色和阶段交接执行。没有可用角色时记录主 Agent 代行范围及未完成的独立性；不能虚构 Agent、交接或复核结论。
- 逻辑、配置、时间和可控回调优先用静态或自动化验证。没有测试接缝是开发缺口；缺依赖或许可证是自动化受阻；二者都不能自动转成“必须真机黑盒”。
- 真机、Unity Editor、PlayMode、商店／SDK、线上后台和实际视觉/触感能力不同。按 Harness 和模块文档标出各自层级；源码编译、mock 调用、Editor 通过不能替代另一层的实际结果。
- 奖励到账、资格落档、持久化、动画结束、支付核销和页面回调是不同断言。按适用准则追到业务消费入口与存档入口，不能只看 UI 文案或动画。
- `QA/README.md` 可能记录明确的历史覆盖范围、阻塞项和替身边界。不要把其中某次基线或“最近若干需求”当作当前全量测试状态；每次按本轮分支、HEAD、输入版本重新运行并查实际报告。
- `文档/功能执行/` 保存需求实施或验收记录，适合查决策与历史边界；先核对版本、状态和是否被后续规则替代。历史方案、旧产品预期或旧测试名不能覆盖当前模块规则。

## 查历史问题的口径

- 只在命中的模块开发文档、测试说明、`QA/README.md`、相关实施/验收记录和相应测试中搜索本问题的关键词、入口或稳定断言 ID；不要把全仓搜索无结果当成“从未发生”。
- 若要称为“已知问题”，必须找到同一断言的历史记录，并以当前证据确认仍存在；相似标题不证明根因相同。
- 若要称为“回归”，必须找到同一断言曾修复或通过的可信版本/报告，再在当前基线复现失败。历史报告不替代本轮测试。
- 模块开发文档中的有日期、明确范围/断言和通过结论的正式验证摘要，也是可引用的历史通过证据；若原始报告没有随当前 Worktree 提供，报告中注明“依据模块文档历史摘要，未复核原始报告”。比较失败范围时拆开源数据、打包数据、运行时加载等断言：历史记录只覆盖其中一层，就只给该层回归结论。
- 没找到可核实历史材料时写“本次发现，历史情况未知”。不要宣称“新引入”“以前没有”或给缺陷猜测发生版本。
- 只读取相关且有界的记录；不要为了推断历史状态全量读取 Unity 日志、无关历史提交或用户级 Codex 数据。
