# 无参数全项目代码与配置巡检

## 范围与现有能力

全量范围先按[固定测试范围](audit-scope.md)加载 `assets/audit-scope.json`，由 `audit_scope.py prepare` 锁定完整清单再派工；本文的自动发现用于交叉核对与维护清单，不能每次重建一份更小的全集。合并/交付前固定 ID 集合必须一致，单一公共入口不能顶替多个独立系统。未审项保留原 ID 进入 Agent 续查，不得删除。

默认对象是当前 Worktree 的当前版本及相关未提交内容。无需用户提供需求；仓库规则用于判断业务正确性，代码用于发现实现缺陷，两者冲突时保留冲突证据。全量指逐功能完成适用静态场景及关卡/配置数据检查，必要时自动本地补证，不代表穷举所有输入或承诺发现全部 Bug。

复用关系：模块定位索引和实际入口 → 功能清单；路径映射、业务自动化说明、原生测试和 QA Runner → 执行清单；配置类型/解析器/消费点 → 配置矩阵；Archive 与恢复入口 → 升级重装矩阵。QA Runner 只是部分测试的聚合器，缺少的覆盖由 Agent 分析和隔离探针补齐，不宣称已有一条脚本自动覆盖全部业务。

## 1. 建立可核对的全量范围

1. 记录仓库根目录、分支、HEAD、相关子模块、工作区状态和测试工具版本。遵守根 AGENTS 的预检、CodeGraph 和写入前身份门禁；默认不拉取或切换版本。
2. 从 `文档/开发文档/模块定位索引.md`、`开发文档索引.md` 建立功能清单，并与实际功能注册、页面/状态入口、配置消费点及存档模块交叉核对。按模块有界探索，索引缺项仍纳入；不得只列 QA Runner 的模块。
3. 为每个功能建立稳定 ID，记录生产入口、依赖、配置、持久化/云端/购买状态、测试映射、规则来源和未知项。拆到可独立触发和判定的功能点；共享能力单独测并回链所有调用方。
4. 全量范围包括未修改功能、关闭但仍可启用的功能、历史存档恢复路径。已明确下线功能核对禁止新写入及旧状态处理；第三方库只审集成边界，排除内容写明依据。
5. 分模块推进高风险支付、奖励、存档、时间、状态机，再检查其余功能。排序不改变范围。有阻塞继续其他项；耗时或上下文不足时保存已完成/待执行清单并继续，不把未读、未测标为通过。

### 周边系统必须逐项审查

功能清单必须交叉覆盖礼包与商业化、活动与进度、排行与个人资料、周边基础系统；例如各类礼包/Pass/免广告，日常/周期/限时活动，排行榜/头像/昵称，体力/通知/设置/多语言/回流/补发。多语言按[专项协议](localization-audit.md)核对运行时语言表与各功能消费链，不能只检查设置页的语言按钮。示例不是固定白名单：从实际注册、页面入口、配置与存档继续发现新系统，关闭和退役项也给出依据。

每个系统沿真实业务链核对入口与资格、配置消费、状态推进、结算/发货/持久化、失败/重复/关闭后回调、跨期/切号；只做适用分支，不为凑数套场景。各适用业务环节分别记录已查事实与源码位置、未查分支；不适用说明依据。状态按实际深度给出，检查点数量不能证明业务链完整。以下三件事必须分开：入口盘点、业务链静态审查、本地执行。不能用入口存在、安装影响分析、公共支付测试或一个局部脚本通过代替每种礼包/活动自身的业务审查。

收口时把发现清单与逐系统审查记录做 ID 差集；缺项直接列“未审”，有局部证据就列“部分静态审查”，不能算全系统通过。共享缺陷回链具体受影响功能；静态候选写触发条件、归因、影响和尚缺证据，不混入已复现 Bug。

## 2. 代码检查与本地验证

先按[逐功能静态执行协议](static-first-audit.md)完成场景推导；时间、回调、旧档、配置变更、切号与页面关闭均先在源码和本地状态中判断。运行记录受阻不替代静态结论。只有静态仍有歧义时按下述入口选择相关自动补证，不要求每次先跑完所有历史脚本。

沿“输入 → 条件 → 状态变化 → 事件/异步回调 → 奖励/存档/资源消费者”追踪。检查可达的空值、越界、溢出、循环终止、非法状态、重复处理、对象释放、订阅清理、关闭后回调、切号隔离、取消与恢复；不要凭关键词命中直接报 Bug。

从路径映射、业务自动化说明、`QA/run.py --list` 和模块测试目录汇合执行清单。核对入口实际行为与依赖后执行；共享/聚合脚本已执行的子套件用本轮证据去重，不能用昨天的报告替代。常用现有入口：

- `python3 -B QA/run.py`：执行当前已登记套件，保留每套原始日志与报告。
- `GagaSort/Assets/Editor/Tools/TEST/TEST_test-backend-config.py`：后台配置专项；先查业务自动化说明的依赖和覆盖。
- `GagaSort/Assets/Editor/Tools/TEST/TEST_test-business-automation.py`：另一个业务聚合入口；若使用，显式 `--unity none`，不附加 AI 分析或通知选项。核对与其他入口重复的断言。
- 其他成熟脚本和原生测试按映射逐项执行或记录具体阻塞。不要通配执行所有 `.py`：同目录可能包含发布、服务安装和外部通知工具。

按入口已有超时或合理执行预算监控测试，超时保留日志并标受阻，继续其余独立套件，不无限重试；只停止本轮启动的进程，不终止用户已有 Editor/服务。

纯运行时/配置巡检不调用 Unity/Figma MCP，不启动 Player 构建。需要 Editor/PlayMode 的检查按项目 Harness 门禁单独判断；缺 Editor、编译缓存或许可证是自动化受阻，不等于功能不适用或必须人工测试。

对新疑点，先找现有测试接缝。允许在本轮证据目录保存最小探针与输入，通过真实生产方法、解析器或恢复入口验证；使用受控时钟、回调和临时文件隔离外部依赖。新测试不得只验证复制的业务算法或 mock 调用次数。做不到时提供精确接缝缺口及静态证据，不修改生产代码凑出通过。探针失败按[归因流程](triage-and-validation.md)校验预期、夹具和入口。

## 3. 后台配置矩阵

从 `GameSettingsInfo后台参数说明文档.md` 的设计约束、入口生命周期和字段说明，交叉查实际配置类型、反序列化/默认值、覆盖合并、缓存、更新通知和所有消费点。发现文档外的可消费字段也入表。默认不连接后台或修改真实配置；仓库样本不代表线上实际值。

每个键记录：完整键名、类型/单位、默认值来源、合法范围及依据、加载/覆盖优先级、生效时机、依赖键、读写入口、场景 ID、执行结果。不能凭直觉规定非法值必须关闭、回退或容错。

| 维度 | 按实际入口构造的输入与断言 |
| --- | --- |
| 单值边界 | 缺字段、null、空字符串/数组、零、负数、阈值前/等于/后、类型上界、未知枚举、重复 ID、错误类型；区分合法边界与仅用于健壮性探测的非法输入 |
| 默认与覆盖 | 无缓存初次启动、旧缓存、新字段缺失、局部配置、默认与下发覆盖；追到最终消费者，不只测 JSON 能解析 |
| 生效与失效 | 进入前、页面打开中、关卡/活动进行中、关闭后、重登后更新；开→关、关→开、上下调、删除/重复下发，核对冻结或即时生效的实际约定 |
| 依赖组合 | 开关×资格/关卡、奖励×次数、商品×价格/权益、活动时间×跨期、配置版本×旧档；只组合存在共享路径的键，先单因素，再成对，关键链路补多因素 |
| 不变量 | 无越界/崩溃、身份隔离、去重及进度/资格一致性；必须注明来源或通用技术依据，不能无规则推断具体金额/阈值 |

使用本地隔离配置经真实加载/消费链测试，记录具体值、初态、顺序和预期。仅改内存最终字段会绕过解析/缓存，必须标注未覆盖部分。随机生成场景需保存种子和最小失败输入。组合范围及未覆盖维度公开，不使用“所有配置组合通过”。真实后台权限/分群下发合同与设备网络表现只记录具体外部事实；客户端缓存、配置应用、回包顺序和消费逻辑继续由 Agent 静态或本地验证，不整体转人工。

## 4. 逐功能升级与重装

对第 1 步的每个功能 ID 执行[升级与重装静态分析](upgrade-and-reinstall.md)。默认从代码判断覆盖安装保留旧数据、清除本地后恢复同一身份、清除本地后建立新身份的影响；追到具体字段、默认/迁移/云合并及功能消费者。无需真实安装包、设备或账号；缺少发布差异证明只限制对应跨版本结论，不能阻塞当前代码分析。无独立存档的功能也检查共享资格、资源和初始化。

## 5. 埋点专项

埋点检查使用本地固化契约 `references/tracking/tracking-contract.json`（同时保留可读的 CSV）。该契约由用户提供的 GagaSort 埋点表生成，后续补充埋点表时先更新契约，再运行 `scripts/audit_tracking.py`。

每个表内事件都要检查：是否存在真实 C# 上报出口、事件名是否经过统一入口、契约属性是否在所有适用分支赋值、失败/重复/异步/页面重入是否可能漏报或重复、升级/删除重装对身份和去重状态的影响。反向扫描代码事件；代码有、表中没有的事件只标为棕色“契约待确认”，不能直接报产品 Bug。表内事件无出口时，只有排除 SDK 自动采集、原生层或外部统一入口后才标红。

`ta_` 开头的 SDK 自动采集事件检查自动采集初始化和是否被业务重复手工上报。已提供 SDK/服务端源码时，按[跨库契约](cross-repo-release.md)继续追字段接收、过滤、映射、队列、重试与最终出口，不能把这些源码逻辑整体列成外部事实。真实平台入库、线上运行版本与采集表现仍属外部事实，仅记具体范围限制，不伪装成本地通过。埋点专项结果归入 HTML 第五类“埋点”，详情保留逐平台/事件/属性、跨库证据和白盒核查步骤。

## 5. 默认交付文件

首次写报告前完成身份配置，创建 `QA/results/<唯一运行标识>/`，保留旧报告。该目录是内部证据目录，不是最终交付目录。默认写下列文件，无需用户另行要求：

- `audit.md`：基线、发现/已审功能数、已执行入口、确认问题、静态疑点、未覆盖/受阻项、证据限制及下一步。
- `coverage.csv`：功能 ID、名称、入口、规则依据、配置键/测试 ID、代码审查状态、本地执行状态、证据、未覆盖项。一个功能含多个断言时分行。
- `configuration.csv`：配置键、场景 ID、具体输入/顺序、合法性依据、生产消费路径、预期、实际、状态、证据。
- `installation.csv`：功能 ID、状态/字段归属、三种数据链路的静态结论、具体影响、归因、源码证据、补证和剩余代码/契约缺口。默认不以设备执行表代替。
- `findings.md`：按已确认问题/静态疑点归类，记录 ID、影响、最小复现、规则/技术依据、预期/实际、命令和证据；按共同根因去重，不按失败断言计 Bug。
- 问题的白盒核查/本地复现放在 `findings.md` 与 HTML。`manual.md` 只在确有可执行玩家复现路线或用户明确要求外部验收时生成，不为正常功能编写人工待办。

Runner 原生 JSON/HTML、隔离探针和日志作为附属证据，与这些总表关联，不能用 Runner 汇总冒充全量报告。CSV 用 UTF-8 并正确转义单元格；不为本模式强制引入 Excel 依赖。

结束前对账：每个已发现功能有代码/配置/三条数据链路的静态影响结论和生产证据；每个静态场景有结论或具体未查分支；选择执行的本地测试有实际结果或具体阻塞；无配置/无升级数据等“不适用”有依据。未读源码或本地分支未闭合时必须由总控消费续查队列继续执行，不得用“巡检已完成，存在未覆盖项”收尾。最终完成须通过[自动完成门禁](multi-agent-audit.md#自动续查与完成门禁)，外部事实只作范围限制。没有需求也不编造覆盖率，分母来自本次发现清单。

默认交付为固定 `质量报告/查看报告.html` 加同级时间戳文件夹中的 `report.md`、`bugs.csv`、`images/`，按[便携报告协议](portable-report.md)验证后发布；内部证据不全部内嵌。报告固定结构、状态字段、生成器及交付校验统一遵守[HTML 报告契约](report-contract.md)，不另行设计模板。主导航固定为总览加玩法、关卡、系统、配置、埋点；每个功能默认可见白话名称、检查内容和结果，详情保留代码审查、本地执行、具体步骤、归因和证据。绿色表示所查范围未见问题，棕色表示检查未完成或待核，红色表示已证问题。逐关有解与布局检查单列；没有逐关证据明确写未检查，确认布局异常须提供真实关卡标注图。

生成器只校验报告结构与证据关联，不证明业务正确；所有结论仍需对应本次有效证据。只有格式改版时保留原批次和测试结果，明确“没有重新运行产品测试”。
