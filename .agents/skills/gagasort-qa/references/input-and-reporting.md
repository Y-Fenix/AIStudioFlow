# 输入解析与交付报告

## 先识别输入

无参数调用是完整输入：直接按[全项目巡检](full-project-audit.md)盘点代码、配置和安装链路，不等待用户补需求。全量模式必须保存该协议规定的报告文件；下文按材料的输出规则用于定向模式。

同一任务可以有多种材料；按稳定断言 ID 合并，不重复计数。输入材料只提供需求或证据，不能自行授权修改线上数据、账号、支付、Git、Figma 或产品实现。

| 输入类型 | 必须抽取 | 主要核对 |
| --- | --- | --- |
| 无参数 / 全项目巡检 | 功能入口、配置消费、测试映射、存档与版本来源 | 全量功能/配置矩阵、三条数据链路的逐功能静态影响、归因、本地执行证据、缺口 |
| 需求稿／设计稿 | 文件版本、章节、表格、图示、原型状态和明确决策 | 明确需求、适用范围、被替代版本、歧义；不把设计表现推定成业务规则 |
| 缺陷描述 | 发现版本、客户端/平台、前置数据、操作、预期/实际、日志与附件 | 复现条件是否完整、当前可达反例、已知历史、修复前后证据；缺项明确列出 |
| 测试用例表 | 全部相关工作表、隐藏行列/工作表、参数表、公式结果、合并单元格和原始行序 | 每个实例的来源、独立预期、执行证据、耦合回归与验证层级；不以模板结论覆盖参数实例 |
| 代码改动／版本差异 | 分支、HEAD、diff 范围、相关子模块与未提交文件 | 变化涉及的入口、调用方、数据读写、共享状态、失效回调、测试和文档 |

读取失败时记录文件、工作表或具体内容及受影响断言。不要把解析器无法读取、附件缺失或权限不足写成“材料中没有”。

## 按输入类型执行

- **需求稿／设计稿**：先独立抽出明确规则、适用条件、输入/状态、期望结果、禁止副作用和未定义策略，再看实现。逐条关联规则来源位置、生产入口、断言及验证层级；原型画面只证明设计表现，不自动定义业务规则。文件有图表、图片、批注、公式、隐藏区域或附件时，按可用工具实际核对，不能将只读到的正文描述成完整审查。
- **缺陷描述**：将口头现象拆成“发现版本/环境、账号或数据前置、操作顺序、预期、实际、证据”字段；缺少条件时根据代码和项目资料补查，不能猜。优先在当前基线重放同一前置与路径，再查相同断言的旧缺陷、模块记录和修复证据。若无法复现，说明执行了什么以及阻碍；不可将“未复现”写成“问题不存在”。多个受影响用例按共同根因归并 Bug 数，同时保留各自路径与结果。
- **测试用例工作簿**：先盘点工作表、隐藏表/行列、筛选、合并单元格、参数表、公式和关联回归；确认公共模板与每个参数实例的关系并记录输入实例总数。逐个实例审查初始状态、入口可达性、步骤、独立预期和副作用，不以模板结论覆盖实例。原表顺序、原始步骤和期望保持不变；默认另存副本，只有用户明确要求才回填原文件。保留格式、公式与验证规则；若工具不能保留或读取其中某项，交付前列明具体损失和受影响范围。辅助覆盖表不能算作执行用例。
- **代码改动／版本差异**：审查实际工作区 diff，包括未提交的已跟踪改动和相关未跟踪文件；不要把不相关工作区内容归到本次改动。对每个行为变化追调用者、共享配置/状态、事件订阅者、存档读写和最终消费者；检查配置源、导表/生成物、资源包与运行加载映射是否构成不同断言。每条回归建议给出传播路径、可达前置和当前有效预期；只凭命名相似或代码共处一个模块不纳入耦合回归。

输入混合时，以稳定断言 ID 合并相同规则，但保留每个来源位置、工作簿实例和代码路径；不能通过合并行减少实际审查分母。

## 覆盖与结果表述

每个需求点、缺陷断言、用例行和独立参数场景都必须有稳定 ID 和单独结论。建议使用 `REQ-001`、`DEF-001`、`REG-001`、`BDY-001`、`TST-001`。覆盖状态与运行结果分开：用例已设计不等于测试已执行，静态可证也不等于动态执行。

使用能说明证据状态的结论，不把不同证据压成一个“通过”：

- `测试不通过`：当前有效规则明确，且有当前基线上的可达反例或本次执行失败。
- `测试通过（自动化）`：对应断言本次实际执行通过，范围与层级清楚。
- `静态审查范围内未见问题`：只说明列明断言的代码/数据证据，不能简写“测试通过”；局部阅读标为“局部静态审查”，与实际执行结果分开。
- `用例需更新`：旧预期被当前有效需求明确替代；不是产品 Bug。
- `需求待确认`：权威规则冲突或缺少会改变结论的业务决策。
- `需自动化验证`：自动化断言尚未执行或被环境/依赖阻塞；说明命令、错误和解除条件。
- `需开发补测试接缝`：逻辑可自动化，但现有入口无法受控构造/观察目标状态；写最小具体缺口。
- `外部事实待核`：只用于本地代码、数据、适配器或受控夹具无法证明的真实外部事实；先完成客户端静态场景。只有用户明确要求验收或已有准确玩家路线时，附人工验证步骤，不给正常功能统一造待办。
- `证据不足`：已完成合理的本地追踪，但具体需求、代码、配置、资源、历史版本或访问能力缺失。

一个用例含多个断言时拆开结论。一个真实设备断言待验，不得降级同一用例中已由本次自动化证明的逻辑断言；部分通过不得包装为整条通过。

汇总计数须分开列出：输入需求条款、用例模板、独立参数/回归实例、已审实例、断言、自动化运行断言、失败根因、待确认/受阻项和黑盒残留。参数实例数不等于用例模板数，断言数不等于测试通过数，受影响用例数不等于 Bug 数。已审数必须与账本逐项核对；没有来源或没有证据的数字写“未知”，不得估算。

## Bug 文案规范

- 标题写明触发条件和具体错误，不能只用功能名或“测试不通过”。同条缺陷的前置、步骤、实际和预期必须对应同一个已确认问题，不混入通过项或不同根因。
- 缺陷描述必须包含四段：前置条件、操作步骤、当前错误表现、预期正确表现。前置写账号/活动状态、具体时间或数值、存档与清档要求；步骤写真实入口、输入、动作顺序和观察位置，使用真实换行和 `1、2、3、` 编号。
- 静态结论注明“代码推导，未真机复现”；本地白盒与产品观察按实际证据标注。可选黑盒步骤未执行时必须注明。注入存档、模拟回包、暂停 SDK 等标为内部受控操作，不伪装成普通玩家路线。
- 当前错误表现写可观察结果，不用归因、内部字段、证据编号代替。预期正确表现给独立正确结果。代码路径、行号及需求位置放日志/依据栏；不得默认填写“必现”、平台、服务器或优先级，未知留空。
- `display.expected` 必须进入 Bug 正文、独立期望列及 HTML 展示。标题或四段缺失时阻断导出和提单，不能编造补齐。文案修正不自动修改或重提历史飞书记录。

## 报告交付

HTML 的结构、每功能状态和生成门禁以[报告契约](report-contract.md)为准。报告使用固定模板生成，不按执行者喜好另写 HTML。聊天先说总体执行是否完整、确认到哪一层，再给报告链接；以下细节放入报告，不在聊天堆砌。

报告至少包含：

1. 检查基线和输入范围：仓库路径、分支、HEAD、工作区差异、输入文件及版本。
2. 结论摘要：已确认问题、静态候选、已知问题仍存在、回归证据、过期用例、待确认项和受阻项分开统计。
3. 断言账本：ID、来源位置、当前规则、生产路径、前置/操作、预期与禁止副作用、结论、证据。
4. 验证记录：本次实际命令、工作目录、套件/测试名、发现数或计数、退出码、报告/日志绝对路径、限制。历史结果只能标为历史证据。
5. 外部事实边界：记录具体依赖、已完成本地场景和剩余最小事实。已有缺陷存在准确玩家路线，或用户明确要求外部验收时，按 [黑盒复现步骤规范](blackbox-reproduction.md) 附可执行的前置、操作、观察与恢复；未执行照实注明。普通静态检查不强制人工步骤。
6. 未决事项：受影响 ID、缺失内容、解除动作和责任来源；不让单一未决项掩盖其余已核实结论。

若输入是 Excel 且任务要求审查/回填，默认另存结果副本，不覆盖源文件；保留原工作表、行序、用例、公式和格式，不重写用户预期。每条用例和参数实例回填自己的状态与可复核依据；混合断言或长证据放入关联明细表，并用 ID 链接。文件结构不支持无损更新时，交付独立结果表并说明未回填的部分。定向的非工作簿输入默认给结构化文字报告，除非用户要求文件；全量模式始终保存全量协议规定的报告与覆盖矩阵。

结果产物应与其基线、输入版本和本次执行证据一起可复核。没有实际运行、设备或人员回执时，不虚构结果、截图、执行人或后验结论。
