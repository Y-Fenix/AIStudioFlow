# 缺陷分流与边界验证

## 输入与基线

先确认检查对象是当前工作区还是用户指定版本。记录仓库绝对路径、分支、HEAD、相关子模块版本、工作区差异及需求/用例输入版本。不得拉取来“补齐最新”；远端跟踪信息不能证明线上行为。开始检查后若基线或输入变化，复查受影响结论。

需求稿、设计稿、缺陷描述和用例表都要区分当前有效规则、被替代规则、实现状态、建议和未知项。代码现状不能反向成为验收标准。文档之间冲突时记录来源和影响断言，不自行挑一个更符合当前实现的版本。

项目内的权威规则与测试入口按[项目 QA 知识路由](project-context.md)查找。QA 总入口、路径映射、业务测试说明和模块文档用途不同，交叉核对后再选测试；任何一份清单都不能单独证明覆盖完整。

若输入是工作簿：检查所有相关工作表、隐藏/关联场景、参数表和耦合回归；保留原有行序、预期和参数实例。每个参数实例单独核对，不用公共模板的结论替代。原文件不覆盖；源表无法读取完整时列出受影响工作表和断言。

## 追踪账本

每个需求点或缺陷断言建立稳定 ID，并记录：

| 字段 | 记录内容 |
| --- | --- |
| 来源 | 文件/工作表/章节/单元格、版本或用户提供的现象 |
| 规则 | 当前预期、明确不允许的副作用、版本适用范围 |
| 路径 | 输入/配置、状态前置、调用入口、共享状态/事件、输出或持久化 |
| 实例 | 具体参数、步骤顺序、初态、重置方式 |
| 验证 | 静态证据、测试名、命令、基线、退出码、日志/报告路径 |
| 未决 | 受影响断言、缺少的事实/权限/环境、解除动作和责任来源 |

范围内每条断言和参数实例都要有账本结果。静态判断不能伪装成执行证据。覆盖建议、探索性风险、未确认需求不能混进“已验收”数量。

## 缺陷分类口径

- **测试不通过 / 已确认缺陷**：当前有效规则明确，且当前基线有可达反例或本次实际执行失败。写出前置、输入、触发路径、预期、实际结果和证据。
- **已知缺陷仍存在**：历史 QA/模块记录确实记载同一问题，且当前证据仍可复现。引用历史记录；不能仅凭相似标题认定同根因。
- **回归**：有可核实的先前通过/修复证据或明确的已修复记录，当前相同断言在当前基线失败。没有对照基线时说明证据边界。
- **本次新发现，历史情况未知**：当前首次在本次检查中观察到，且未找到历史记录。不得写成“以前不存在”或“首次引入”。
- **静态候选问题**：源码/数据推导出违反明确规则的路径，但尚未运行或尚未动态复现。说明具体可达条件，不能称为已实机复现。
- **用例需更新 / 需求待确认**：当前权威规则替代了旧预期，或规则冲突会改变结论。分别写出当前来源、原预期和待确认问题。
- **需自动化验证 / 接缝 / 证据不足 / 需黑盒验证**：按实际阻塞原因区分。没有测试环境不等于黑盒；本地可控的时间、状态、随机序列和 SDK 回调优先走自动化。只有真实设备表现、真实平台/SDK行为、服务端合同/下发与可信发布版本差异，才保留具体外部事实；本地仍须按静态执行协议完成客户端分支。

逐功能静态场景及外部事实字段按[静态执行协议](static-first-audit.md)记录；不能只用“待人工验证”代替结果。明确约束和可达反例都能从源码闭合时，允许“静态缺陷已证”，必须附静态推导链并标明未动态运行，不要求必须先有测试日志。

混合断言拆开报告。一个黑盒表现断言不能让同一用例内已由代码或自动化证明的逻辑断言整体降级。

### 自动化失败的逐项归因

失败只表示该执行入口报告了反例，不直接等于产品 Bug。必须按下列顺序对每个失败实例和独立断言归因；先验证 oracle（测试预期）是否仍然有效，再判断产品行为：

1. **校验预期来源。** 回到当前有效需求、模块规则和已确认决策，核实阈值、适用范围、字段语义及例外。代码现状和旧测试不能反向定义规则。规则已经变更的，标为“用例需更新”；权威来源冲突且会改变结论的，标为“需求待确认”。
2. **校验测试实例。** 逐项检查输入数据、账号/存档初态、配置、时钟/随机种子、初始化和清理，确认目标状态可达，参数确实传到被测入口。错误断言、无效夹具、前置缺失、清理串扰和未命中生产路径分别记录为测试问题，不能并入产品缺陷。
3. **校验执行入口。** 检查实际命令、测试发现数、适配器/编译步骤、被调用方法和完整摘要。零测试、错误入口、错误版本、适配器误判或不完整结果标为入口/执行问题；保留未验证范围，不能当作产品通过。
4. **比较生产行为。** 只有预期、实例和入口都有效，并且当前生产路径确实违反有效规则时，才认定产品行为失败。记录同一实例的预期、实际、前置、调用路径和本次证据；缺少其中任一项时用更窄的证据不足分类。

报告时将“规则/预期问题、夹具/用例问题、执行入口问题、环境受阻、产品行为问题”作为不同根因，不用一个套件状态代替归因。每个失败至少保留“预期来源及有效性、夹具和状态核对、生产路径命中证据、实际结果、根因分类、下一步”字段。多个失败断言可归并到一个已证实的共同根因，但仍保留各断言 ID；失败项数量不能直接当成 Bug 数。

以下“修正后重跑”不扩大写入权限：默认巡检只在本轮证据目录构造隔离探针验证问题。修改已登记测试、正式执行入口或持久化新测试需明确授权，遵守单文件写入分配；未获授权时报告根因、修正建议及未验证范围。

常见证据分类：

- **产品行为违反当前规则**：确认输入、初始状态、构建版本和规则来源有效，且测试走到真实生产路径；记录预期、实际、触发条件和日志。能在当前基线上重复的，按缺陷报告。
- **预期已过期或规则有冲突**：对照当前权威规则。明确被替代的预期标记“用例需更新”；规则来源冲突且会影响结论的标记“需求待确认”，不要报产品 Bug。
- **测试或夹具问题**：检查断言、数据、初始化、清理和实际执行路径。错误测试、无效前置或未命中生产入口应标为测试问题，修正后重跑受影响实例；不能据此判产品通过或失败。
- **执行入口问题**：检查 suite 选择、测试发现数、编译/适配命令、退出码和摘要解析。入口未运行目标测试或错误地报告成功/失败时，应修入口并重跑；不能把入口故障归给业务代码。
- **环境或依赖阻塞**：保留实际命令、错误和未执行范围，标记“需自动化验证”并写解除条件。缺少 Editor、许可证或依赖不自动转成黑盒验证。
- **缺少测试接缝**：若逻辑本地可控，只因无法构造或观察所需状态而不能验证，指出最小接缝缺口并标记“需开发补测试接缝”；不要用设备步骤掩盖可自动化断言。
- **结果不稳定**：保留每次运行的基线、输入、随机种子（如有）和结果；先排查时序、共享状态及测试隔离。没有复现证据时写明不稳定现象和次数，不推断为产品缺陷或偶发通过。

工作簿中的失败必须回到具体行、参数实例和独立断言，不能只报套件汇总。修正测试、需求或环境后，只重跑受影响实例及其必要依赖，并保留前后证据；其他未执行实例仍单独标记。

## 边界场景生成

从当前规则和实际分支推导输入，不机械堆全排列。每个补充场景写出它覆盖的断言或独立风险。

- 阈值/范围：适用时测试下界前、下界、上界、上界后；整数门槛按 `T-1 / T / T+1`。浮点、日期、时区按真实精度和单位确定。
- 缺失/异常数据：空、缺字段、默认值、非法枚举、未知配置、稀疏数据、重复记录和 fallback，只覆盖实际接受这些输入的入口。
- 状态与幂等：合法/非法迁移、重复请求、乱序/迟到回调、取消、关闭后回调、重入、跨实例隔离和恢复。
- 生命周期与持久化：新档、适用旧档、重启/重登、前后台切换、页面退出和恢复；只验证产品实际支持的兼容范围。
- 时间与周期：开始前/等于/之后、跨日/跨期、暂停恢复和时间未就绪；遵循模块时间源与时区规则，不修改系统时钟。
- 组合耦合：沿共享配置、状态、奖励/存档消费、页面状态机、事件和回调查到真实消费点。只有新增交互风险时增加组合场景。

不适用项写明规则依据。不要为了“边界覆盖”创造需求、改阈值或强行制造旧版本失败。

## 本地测试选择

1. 从 `tools/agent-task-rules.txt` 找目标路径或行为对应的测试类／方法与验证档位；多路径取测试并集，确认目录级 `AGENTS.md` 和 Harness 适用门禁。
2. 查 `文档/开发文档/业务自动化测试运行说明.md` 获取已存在脚本的覆盖、依赖、替身和证据路径。再读 `QA/README.md` 并运行 `python3 -B QA/run.py --list`；QA 入口适合执行已登记套件，但不保证收录全部成熟测试。必要时直接运行更精确的映射脚本，不为了统一入口重复维护同一套断言。
3. 无参数调用逐功能完成全量静态审查，按歧义与补证需要运行相关本地套件及直接依赖；不以全跑历史脚本作为静态完成前提。用户指定范围时限定到该范围及真实耦合影响。QA Runner 的 `--module` 与 `--suite` 同时使用时取交集；不确定筛选结果时以 `--list` 和实际报告核实。不要将全量模式缩为 QA 列表或当前 diff；未运行入口逐项说明原因。
4. 结果记录真实命令、工作目录、分支/HEAD、工作区状态、测试发现数/断言数、退出码、日志和新结果目录。使用 QA Runner 时读取本次 `report.json`，检查各套件结果、输入哈希及基线/输入变化标志；核实不是旧报告、零测试或跳过。QA 报告的断言计数不等于需求用例覆盖数。运行受阻写清错误与解除条件，不能改写为产品缺陷或人工黑盒通过。
5. 对重要缺陷，修复闭环要求同场景修复前失败、修复后通过；若当前任务仅审查且没有修复前执行证据，标明未执行，不从静态结论推造红灯。
6. 已获明确授权新增或修改稳定测试时，优先复用现有入口；QA 稳定源码放项目 `QA/`，成熟 `tools/test-*.py` 不复制。测试调用真实业务路径，外部依赖才用替身；不测试一份复制的生产算法。测试及映射改动按根 `AGENTS.md` 和 `tools/AGENTS.md` 完成定向验证。

`QA/run.py` 报告中的套件状态和计数口径以当前 README/报告实现为准。测试通过只说明对应层级与范围成立，不说明全部需求、真机或项目整体无缺陷。
