# 多 Agent 全量审查协议

## 目标

`$gagasort-qa` 仍然是唯一入口。总控 Skill 负责盘点、分派、合并、去重和出报告；专项 Agent 只负责自己的领域，不能各自输出最终报告。

全量模式必须把“盘点”和“深度审查”分开统计：发现一个功能不等于已经审查这个功能。没有专项证据的功能只能标为棕色“静态检查未完成”。

## deep-v2 强制账本（不可省略）

派工前必须完成[范围锁定](audit-scope.md)。总控从 `feature-inventory.json` 分配固定 ID、`check_targets` 和候选源码；每个功能独立交付，缺 dossier 时保留未完成行。禁止从 Agent 已交回的 dossier 反推总清单。下面 `checks[]` 每条另需 `scope_targets` 数组，填它真实覆盖的固定 `check_targets` 原文；全部固定目标须有带源码证据、结论闭合的场景回链，否则合并器追加缺口，不能绿灯。该回链不代替七维分支覆盖。

旧版 `checks + gaps` dossier 一律视为浅审输入，不能合并进新报告。每个功能必须同时提供 `branches`、`coverage`、`checks`：

```json
{
  "branches": [{
    "id": "branch-01",
    "dimension": "边界与异常",
    "condition": "具体触发条件",
    "consumer": "最终状态/奖励/资格/存档消费者",
    "evidence": [{"path": "源码路径", "line": 1, "end_line": 2, "note": "该分支作用"}]
  }],
  "coverage": [{
    "dimension": "边界与异常",
    "status": "已闭合",
    "branch_ids": ["branch-01"],
    "case_ids": ["case-01"]
  }],
  "checks": [{
    "case_id": "case-01",
    "dimension": "边界与异常",
    "topic": "具体检查点",
    "scenario": "白话场景和事件顺序",
    "finding": "沿源码分支得到的事实",
    "branch_ids": ["branch-01"],
    "finding_ids": [],
    "evidence": [{"path": "源码路径", "line": 1, "end_line": 2}]
  }]
}
```

硬门禁：

- `branches` 必须列真实条件、最终消费者和准确源码行号；公共管理器不能代替功能分支。
- 七个维度逐项写 `已闭合 / 部分闭合 / 未检查 / 不适用`。部分闭合或未检查必须写清“未读到哪条分支、下一步要查什么”；不适用必须有该功能特定的源码原因。
- 每个 branch 必须同时被 coverage 和至少一个 check 引用；每个 check 必须归属一个 coverage 维度；不能用自由文本 topic 推断维度。
- 每个 check 必须显式写 `finding_ids`，问题只回链到真正覆盖它的检查点，禁止把功能下所有问题泛挂到每条场景。
- 合并器会对所有分支、不适用证据和场景证据做当前源码快照；文件不存在、行号越界、引用孤立或字段缺失直接拒绝合并。
- “深审完成”只由七维 coverage 和 cases 计算；有 dossier 名称、功能数或模板场景都不算完成。


## 分工

| Agent | 负责范围 | 必须追到 |
| --- | --- | --- |
| 玩法 Agent | 关内池、鸭子、机关、道具、失败与残局 | 入口、门禁、数量/容量守恒、状态变化、失败恢复、重入 |
| 关卡 Agent | 关卡枚举、布局、生成、保存、回放、有解性 | 实际关卡数据、逐关判定、异常坐标、求解/回放证据 |
| 系统 Agent | 礼包、支付、活动、排行榜、头像、设置、多语言、广告、Pass | 每个系统自己的入口、状态、异步回调、奖励/资格消费者；多语言按[专项协议](localization-audit.md)追到语言资源、格式化、切换刷新和各功能文本消费者 |
| 配置与存档 Agent | 后台配置、默认值、缓存/hash、通知、升级与重装 | 字段→解析→接纳→消费，三条安装数据链 |
| 埋点 Agent | 固化埋点表、代码事件、属性、统一上报和 SDK 自动采集 | 表内/表外双向覆盖、字段完整性、重复/异步、身份去重和外部 SDK 边界 |
| 总控 Agent | 跨模块影响、问题去重、基线复核、报告 | 证据版本、冲突结论、报告契约 |

## 专项 Agent 输出

每个专项 Agent 输出一个 JSON dossier，不允许只返回自然语言摘要：

dossier 顶层必填 `agent / baseline / features`，`baseline` 包含当前 `head` 和审查结束时的 `source_hashes`（仓库相对依赖路径 → 文件原字节 SHA256）。每功能填稳定 `id`、白话 `summary`、前述完整的 `branches / coverage / checks` 三件套、具体 `gaps`、`related_findings`、实际 `source_paths`，以及 `installation.upgrade / same_identity / new_identity` 三种数据条件的静态影响。不得只参考旧版 `checks` 示例省略分支与七维覆盖。

发现的问题放顶层 `findings[]`，按报告契约填完整证明、步骤、影响和证据；每条 `checks` 只回链其实际证实的问题。动态执行在本轮通过 `record_run.py` 保存回执，按[固定交付](repeatable-delivery.md)输出运行记录及显式功能映射；总控合并本轮真实记录，不在汇总阶段给历史输出补签。

`checks` 必须写真实入口、条件、状态或消费者，并带准确源码行号。一个 Agent 不能用一条公共管理器证据填满所有维度；缺证据的维度写 `未检查` 和原因。

## 合并硬门禁

1. 当前批次不得读取旧报告结论作为当前结果。旧报告最多提供候选功能 ID，所有结论必须来自本轮 dossier 和当前源码快照。
2. 每个功能至少要有一个匹配的专项 dossier；没有匹配 dossier 只能是“仅盘点，未深审”。
3. dossier 的 HEAD 必须匹配，`baseline.source_hashes` 覆盖分支、场景、不适用依据和实际读取的依赖文件。哈希在审查结束时采集；合并时不一致必须续查，不允许只替换哈希/快照。
4. `未检查`、`待核实`、源码变更或专项 Agent 的 `gaps` 会让功能保持棕色。
5. 红色只能来自已有静态证明或本轮真实探针/测试；候选风险不能升级成红色。
6. 绿色必须覆盖适用的入口、边界、重复/异步、状态/持久化、配置、升级/重装和跨模块证据；不能只因为没有 finding 就变绿。
7. 合并后仍要做一次跨模块复核：支付→奖励/资格→存档、活动→时间/配置→页面、玩法→关卡数据→回放、配置→缓存→消费点。

## 报告语义

首屏同时显示：功能盘点数、专项深审数、深审完成数、未完成数、已证问题数和待核实风险数。功能详情先展示专项 Agent 的实际检查点，再展示缺口、归因和复现步骤。没有黑盒入口时展示白盒核查步骤，不能给同事一堆空泛的“请手动测试”。

### 质量快照与固定结论

每轮收尾必须生成 `quality-gate.json`，并把同一份快照嵌入 `report-data.json` 和 HTML。快照只从本轮 `report-data.json`、本轮续查队列和本轮执行记录计算，禁止读取历史报告补数。问题按稳定 ID 去重，展示和导出排序按固定键排序；同一基线、同一输入和同一版本必须得到相同的计数与顺序。

质量快照状态只有 `通过` 和 `部分完成`；报告/证据校验失败由交付回执单独判定为失败。只有 `audit_complete=true` 且报告、证据和 HTML 交互校验均通过，才能写“全量检查完成”或“范围内未见问题”；队列未闭合时只能写“本轮确认问题”，模块必须显示棕色。`report_ready` 只代表报告产物可读，不能覆盖 `audit_complete=false`。历史报告只可作背景，不得进入本轮计数。


## 自动续查与完成门禁

现有能力：`merge_domain_audits.py` 校验 dossier 并合并；以前允许缺 dossier、未闭合分支返回成功，导致半成品被交付。现在复用此入口，在合并后调用 `audit_completion.py` 输出续查队列，缺项返回退出码 **2**，完成且报告证据校验通过才返回 **0**。这是 Agent 的执行门禁，不是新的产品检查器。

合并完成后还必须由 `quality_gate.py` 生成本轮质量快照。快照只接受当前数据和当前续查队列，按稳定 ID 去重并固定排序；它是报告状态的唯一来源。只要队列未闭合，HTML 就必须标记“部分完成”，即使当前已经发现问题或所有已执行用例都通过，也不能写成全量完成。

- 派工按真实功能小批次推进，建议每批 1～3 个；支付等复杂共享链单独一批。最多同时运行项目允许的 4 个子 Agent，总控处理跨模块交接。
- 每批读完分支、消费者和适用规则，保存 dossier。未完成的覆盖和 gaps 如实保留；后续续查**替换该功能的 dossier**，合并命令只传每功能的最新记录，避免重复 ID。
- 公共支付/奖励/存档的证据可共享，但各调用方的实参、回调、状态和最终消费仍需独立检查。不要每批重复跑同一公共测试。当前协议不自动信任跨次缓存；没有完整依赖哈希和影响复核，不得宣称历史结果已复用。
- 当前源码变化由 Agent 续查后，在功能 dossier 写 `source_rechecks: [{"path": "变化路径", "case_ids": ["本轮复核场景ID"], "conclusion": "变化条件及消费者复核结论"}]`；同一 dossier 的 `baseline.source_hashes` 必须包含该文件。合并器只清除有实际场景和证据关联的变化项，不因 HEAD 或快照已更新直接清空待复核标记。
- 总控每轮消费 `*-continuation.json` 中的 `batches` 和 `tasks`，补派未完成部分、自动运行必要的本地探针、重新合并并重算队列。脚本只生成队列，派 Agent 和读取源码由执行 skill 的总控完成。
- 不能把任务数量多、上下文不足、未读源码、缺旧包、没有设备作为结束理由。若相同本地动作连续两次没有新证据，换为源码推导/其他成熟接缝；确实受资源限制无法继续时保存可恢复队列，明确本次执行失败，不能伪装全量完成或转交同事人工验收。

合并各批最新 dossier（未完成会写中间数据及同名 `*-continuation.json` 并返回 2，继续执行）：

```sh
python3 -B <实际skill目录>/scripts/merge_domain_audits.py \
  --base-data <本轮功能清单.json> --root <仓库绝对路径> \
  --evidence-dir <本轮证据目录> --dossier <专项dossier.json> \
  --output <本轮证据目录>/report-data.json
```

多个 dossier 重复使用 `--dossier` 参数。若门禁提示 `validation_error`，由总控修复报告/证据关联后重算，不要求用户补资料。

核查既有中间报告或合并后的数据：

```sh
python3 -B <实际skill目录>/scripts/audit_completion.py \
  --data <本轮report-data.json> --root <仓库绝对路径> \
  --evidence-dir <本轮证据目录> --output <本轮证据目录>/continuation.json
```

外部事实不生成待人工执行的任务，也不阻塞已完成的客户端静态场景。必须先完成本地处理，才能把最小不可判断事实记录为 `external_checks`；不能靠移动到此外部字段隐藏本地缺口。求解预算内未定、非平面几何算法不支持等是自动检查能力限制，不是设备验收任务，也不是 Bug；保留自动阶段结果与明确限制，不删除用户要求的关卡检查。

最终沿用已确认的 HTML。首要内容是已确认 Bug 数、模块结论、影响、原因与复现说明；执行细节和范围限制保留在现有详情。不要给正常功能生成黑盒待办。门禁检查通过不等于发现了所有 Bug，也不代替业务证据审查。
