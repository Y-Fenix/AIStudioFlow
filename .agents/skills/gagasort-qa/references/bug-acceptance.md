# Bug 定向验收与回填

适用于用户明确要求使用本 skill 验收开发修复结果，并检查 `bug-progress.csv` 中“处理状态”为“待验证”的项目。此协议优先于通用巡检和报告交付流程，不启动无参数全量检查，不调用全量派工、关卡扫描、`finalize_report.py` 或 `publish_report.py`。

## 1. 输入与范围锁定

1. 从用户给出的路径定位工作副本 `bug-progress.csv`。未给路径时，先在被测项目质量报告目录中定位；仅有一个符合条件的工作副本时可直接使用并说明路径。多份候选无法判定时先询问目标，不按修改时间猜选，不把原始 `bugs.csv` 当工作副本。
2. 按被测仓库 `AGENTS.md` 完成限定范围预检、写入身份配置。记录绝对路径、分支、HEAD、相关工作区差异和子模块版本；不拉取、切换或提交 Git。源码探索遵循当前项目 CodeGraph 与回退规则。
3. 用 CSV 解析器读取，禁止按逗号或行直接切分。记录原始文件哈希、编码、BOM、换行、表头顺序、行数、ID 与逐格原值。缺少“处理状态”、重复表头、行列错位或无法可靠对应 Bug 时，停止回填并说明具体问题。
4. 仅选择“处理状态”去除首尾空白后等于“待验证”的行，保留原单元格原值。以现有稳定 Bug ID 对应；重复或缺 ID 时结合原行号与内容指纹定位，仍有歧义则不回填该项。既有“验收状态”不代替本轮重新检查。
5. 锁定本轮待验证 ID、数量、原问题、触发条件和原始证据。原始报告只读；记录相关 `bugs.csv`、`report.md` 的哈希用于交付核对。零条待验证时直接如实回复，不生成虚假验收结果、不启动全量或为此新增列。

## 2. 逐条核对修复与关联回归

每条先恢复原问题的触发条件、实际表现、预期与原归因，再核对当前生产入口、条件分支、状态变化和最终消费者。开发描述和修改记录只作定位线索，不能充当修复证据。

- **修复核对**：原触发条件在当前源码中是否仍可达，修复是否覆盖共享入口、失败恢复与重复调用；有可用可信旧基线时对比原失败与现行为，缺少旧基线不得虚构“修复前已复现”。
- **边界检查**：根据实际修改检查阈值、空值、时间、配置优先级、异步回调、生命周期、奖励/资格与存档等适用边界；不适用的有具体依据。
- **关联回归**：沿真实调用者、共享状态/配置、事件订阅者与消费者审查修复影响，检查是否新增丢奖励、重复发放、流程不可达、数据恢复错误等缺陷，不无限扩展为全量审查。
- **自动补证**：静态调用链足以判定时直接给静态结论；有歧义时优先复用定向测试或运行复用真实逻辑的隔离探针，探针和输入留证。不复制算法模拟通过，不改生产代码或既有断言迎合结果。缺少 Unity、SDK、设备或依赖不等于产品 Bug，也不自动转人工；继续完成能做的源码和数据检查。
- **证据**：逐条保存当前基线、检查范围、实际验证方式、源码路径及准确行号、触发输入、推导或执行结果、回归结论和具体限制。源码推导不冒称游戏实测；未执行项不标通过。按项目规则区分自检和独立复核，不冒记 Agent 或人员验收。

证据保存到被测项目本轮独立目录 `QA/results/bug-acceptance-YYYYMMDD-HHMMSS/`，至少有 `acceptance-summary.md`。逐项结构为“Bug ID/标题 → 原问题 → 当前修复证据 → 边界与关联回归 → 实际验证方式和结果 → 验收结论/限制”。确认缺陷附可复核的白盒步骤，有准确玩家路线再补黑盒步骤。

## 3. 结论与回填

开发维护“处理状态”，Codex 维护“验收状态”。用户已要求回填时，可直接更新指定工作副本，不再为这一步索要确认。

| 当前证据支持的结论 | 验收状态 | 记录要求 |
| --- | --- | --- |
| 原问题已消除，适用边界及关联回归完成，未确认修复引入关联缺陷 | 已验证 | 写明实际验证层级和证据，不承诺不存在任何 Bug |
| 原问题仍存在，或确认本次修复引入影响该项验收的关联缺陷 | 重新打开 | 明确是原问题残留还是新增回归，给触发条件、归因和复核步骤 |
| 源码链未查完、关键歧义未消除或必要验证未完成 | 保留原值/空 | 不新增未经约定的状态枚举；证据及总览明确“本轮未完成”，即使原值为已验证也不得计作本轮通过 |

与修复无关的新发现单列到验收证据和总览，说明证据和影响；不自动新增原 CSV 行，不因为无关发现重开已通过的原 Bug。统计时区分原问题未修复、修复引入的新 Bug、其他新发现，避免把同一问题重复计数。

回填写入规则：

1. 写入前备份原文件至本轮证据目录并确认备份哈希一致；再次核对目标文件哈希。若开发或其他进程已改动，重新读取、重新核对受影响行，不能覆盖并发编辑。
2. 只有一次“验收状态”列时复用，并将整列连同原值放在“处理状态”紧右侧；不存在时在该位置新增。重复同名列时停止，不猜列。只更新本轮已形成确定结论的行。
3. 保持所有原列、原单元格值、行序、ID、中文、多行内容、编码/BOM、换行风格。除新增或移动验收列及本轮确定结论的验收单元格外，不修改任何内容，不改变开发的“处理状态”。非本轮行已有验收值保留；新列中非本轮行为空。使用能正确往返的 CSV 读写器，写临时文件、验证后再替换，不写半份文件。
4. 写后重新解析逐格对账：原列原值不变、行数和身份不变、验收列唯一且紧邻处理状态、本轮结论及统计一致、非本轮值不变；再次核对原始存档哈希、源码基线及受查文件是否变化。存在影响结论的源码变化时重查受影响项，不交付过期结论。
5. 原始 `bugs.csv`、`report.md` 和 HTML 不修改、不重新生成。独立工作副本不受原始报告 CSV 哈希绑定限制。正常 CRLF 不算缺陷；如需 Git 空白检查，可仅本次命令使用 `git -c core.whitespace=blank-at-eol,blank-at-eof,space-before-tab,cr-at-eol diff --check`，不改全局配置或强制转换行尾。
6. 不自行修复生产代码，不修改 skill、正式资产或既有测试。暂存、提交、飞书提单等动作须有用户另行授权，不能由 CSV 验收推断授权。

## 4. 固定 Codex 总览回复

最终回复必须直接给数量、结论和入口，不能只发证据链接。按下面顺序回复，数字必须来自本轮实际验收和回填；路径使用真实绝对路径，不能保留占位符。

```markdown
已完成 X 条“待验证”Bug 的定向验收：

- **已验证：X 条**
- **重新打开：X 条**
- 关联回归未发现新 Bug。

已在 [bug-progress.csv](实际绝对路径) 的“处理状态”右侧新增或更新“验收状态”，原有内容保留，其余 X 条保持原样。

本次采用【实际验证方式】。[查看逐项结论与证据](实际绝对路径)。未暂存、未提交。
```

- 有新 Bug 时，把“关联回归未发现新 Bug”改成真实数量及简短影响，区分修复引入和其他新发现；有重新打开项时补 ID 与一句话原因，不能只报数量。
- 有未完成项时，首句改为“本轮共 X 条待验证，已完成 X 条，未完成 X 条”，增加未完成数量与具体原因，说明对应验收值未改；禁止称全部完成或全部通过，不默认要求人工验收。
- “其余 X 条”只计非本轮行；列新增时指其原始内容未变，不表示新增列原已存在。
- 实际方式明确为静态源码审查、定向自动化或两者结合；未执行游戏/设备测试时如实说明，不用“实测通过”代替静态结论。
- 暂存/提交句据实际情况填写；未授权不执行。只有零条待验证时简短报告筛选结果与目标 CSV 链接，不伪造证据或更新记录。

## 5. 交付核对

必须确认：待验证筛选正确；每条确定结论有当前基线证据；关联回归已做或明确未完成；列位置正确；原列与非本轮值保留；备份可回溯；原始存档未改；最终总览数字和 CSV、逐项证据一致。任何检查失败，停止宣称回填或验收完成并如实说明。
