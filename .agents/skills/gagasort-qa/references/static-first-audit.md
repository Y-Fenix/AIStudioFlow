# 逐功能静态检查执行协议

默认目标是“一键得到代码层面的检查结论”，不是生成一份等待测试人员执行的用例表。本协议适用于每个功能及配置点。已有测试可补证，不能决定静态审查是否继续。

## 执行与停止条件

1. 从实际入口出发，追到资格判断、状态变化、异步回调、最终消费者和存档。读取当前适用规则。不能只找类、只读公共管理器或只查安装影响。
2. 将功能拆成可判定场景：写明确初态、具体输入或事件顺序、预期、实际分支、源码位置和结论。沿真实分支逐步推导，不必真的跨天、购买、联网或重新安装。
3. 静态链已闭合就给静态结论。需要观察才能消除歧义时，复用已有接缝，以隔离时钟、回调、内存/临时存档、配置响应运行最小本地探针。探针走真实生产逻辑，不复制算法自证。
4. 缺 Bee/Unity/SDK/许可证只影响相应执行入口。继续源码与数据检查；判断能否用已有独立编译入口或最小依赖替身补证。替身不能实现被测逻辑，不能改正式代码、已登记断言或引入临时 Unity Runner。
5. 只有读取/分析仍有缺口才标“静态检查未完成”，并记录具体未读分支及下一步本地动作。可由本地计算解决的事情由 Agent 完成，不改写成“请人工测试”。

静态结论可为“所列范围未见问题 / 静态已证缺陷 / 条件风险 / 未完成”。确定缺陷不要求先跑游戏：明确有效约束、可达初态、入口与消费链完整、反例确定成立时，可报“静态缺陷已证”；必须写明静态推导，不能声称已动态复现。若入口可达性、输入合同或有效规则未确认，保留为条件风险。

## 每功能要覆盖的维度

`static_audit.cases` 覆盖以下维度；不适用必须给功能特定的理由与来源，不能用七份模板文字凑完成度。同一维度可有多条边界和顺序用例，不能只测一个正常值。

| dimension | 检查内容 |
| --- | --- |
| 入口与正常链路 | UI/状态/事件调用方、启用与资格、初态→处理→消费结果；重验时机 |
| 边界与异常 | 零/负/空/缺项/上限/阈值前等后；返回失败、抛错、取消；数据与锁是否留半状态 |
| 重复与异步 | 连点、重复订单/领取/回包、同步重入、回调乱序、关闭/重开、销毁、切号与跨期后旧响应 |
| 状态与持久化 | 写入先后、失败回滚、防重标记、重启恢复、云合并；是否漏发/多发、资格与进度不一致 |
| 配置变化 | 缺省/显式null/非法组合；进入前、中途、重开和重登变更；冻结值与最新值的选择 |
| 升级与重装 | 保留本地旧数据、清本地恢复原身份、清本地新身份；逐功能字段和最终消费者 |
| 跨模块影响 | 公共支付/奖励/时间/存档/页面/状态机的调用者与订阅者；检查影响向外传播 |

依赖公开技术不变量或已查规则判断。缺少商品跨期政策、线上资格等合同，不能自行发明规则；先完成明确部分，把“业务政策未知”与“代码没读完”分开。

## 功能类型的具体检查

| 功能类型 | 默认由 Agent 检查，不移交人工 |
| --- | --- |
| 关内玩法 | 按命令/帧序追鸭子归属与数量守恒、容量权重、预约占位、状态门禁、机关计数、锁的持有与释放；大步长/多事件同帧、出池失败、重入、稳定残局恢复及道具扣除 |
| 礼包、商城、Pass、支付 | 各商品自身入口、有效SKU/价格/奖励、订单快照、重复交易、关闭后晚成功、跨期/重启后的权益归属、失败时核销与落档；复用项目延迟成功准则，不用公共支付测试代替每个商品 |
| 活动、登录奖励、任务 | 可控时间的阈值前/等于/后、旧日页面跨日、配置开关切换、重复胜利key、阶段/终奖领取、结算后重入、切号及存档合并；不用等到午夜或活动结束 |
| 排行榜、头像、昵称 | UID/地区/期次缓存键，分页重叠/缺页/空页，旧响应和切号隔离，昵称编解码，头像单项/整组缺失、资格回退和保存；本地构造返回数据，不要求真实服务器才读客户端处理 |
| 体力、设置、通知 | 冷缓存与保存值、默认值取反、倒退/跳变时间、满值/上下限调整、无限体力到期、重复暂停和通知偏好回滚；时间与持久化在本地隔离 |
| 多语言 | 按[多语言专项协议](localization-audit.md)检查逐语言资源/key、实参格式、默认与回退、切换刷新、异步旧响应、字体/材质/fallback、资源缓存和语言偏好恢复；覆盖各业务页面接入 |
| 后台配置 | 逐字段从解析、默认、覆盖、缓存/hash、接纳、通知追到最终消费；构造真实可消费边界与有关联的组合，区分客户端处理正确性和服务器是否会下发 |
| 升级与重装 | 用代码和隔离旧档分析保留、清除、迁移、同身份合并、新身份初态；不要求旧包或设备，只有实际发布差异另标限制 |

## 关卡有解与布局

关卡审查是全量巡检的必做项，不能因代码静态检查已很深或普通功能已审完而跳过。执行时按以下顺序完成并保存本轮证据：

### 固定执行入口（不得跳过）

先运行本 skill 的工具，而不是寻找曾经报告里拼写错误的容量脚本：

```sh
python3 -B <实际skill目录>/scripts/scan_levels.py \
  --repo <仓库绝对路径> --output <本轮证据目录>/levels
```

脚本按 `Resources/GagaSort/LevelData` 的 manifest 精确枚举有效关号，快照输入、核对分组与 Hotfix 镜像；从当前游戏配置读取圆角。自动隔离安装 Python 解包/绘图依赖，并按 `packages-lock.json` 下载官方 Mathematics/Splines 包，使用项目指定 Unity 自带的 C# 编译器和 .NET 运行时独立编译生产 `GagaSortPathBuilder`、`GagaSortPoolRelationGeometry` 和几何内核。无需启动 Unity，无需 Library 缓存。编译缓存放系统临时目录，报告仅保留日志、适配差异、源哈希和逐关数据。首次运行需要官方包网络访问和本机已安装项目版本 Unity；失败记录准确缺口，继续能独立完成的源码/数据检查。

入口的默认阶段固定为：

- **打包和范围**：运行时 manifest 精确枚举，分组/ID/指纹头核对，Resources 与 Hotfix 文件逐字节哈希比对；不冒称重新计算生产内容指纹。
- **基础布局**：节点边界/半格、控制柄和真实曲线边界、激活盒/前后池还原、泳池尺寸/方向/锚点/互叠、压水道/出入口距离。池子允许在棋盘外，派生池不可按占位零坐标判错。
- **正式规则与通关**：`build_level_solver.py` 使用完整 MessagePack Key-array 记录、正式 `ValidateLevelRecord` / Factory / LogicRuntime / SolvabilitySolver；从正式 Config.asset 与实际动画取逻辑参数，不偷偷用默认值。默认每关 200ms 搜索，未定时追加正式 `GagaSortDifficultyEvaluator` 的 Novice / Typical 自动走法（固定种子、辅助总预算 300ms、单次 150ms；协作式取消，实际耗时单独记录）。保持原容量、锁定额外槽位、不使用道具。搜索或代理找到的候选均须在全新正式运行时重放至 `HasCompleted`，且正式 Validator 合法，才算有解。保留原搜索与每次辅助记录；预算耗尽或一次自动走法死锁都不是已证无解。主入口可用 `--solver-time-ms` 调搜索预算，辅助预算见 `build_level_solver.py --help`。
- **表现网格**：`build_level_visuals.py` 调用正式 WaterPipeMeshBuilder 的样条、采样及三角形生成，使用真实 Prefab 参数；动态回退和 Resources / Hotfix 配方分别检查，保留来源及指纹。不启动场景；仅以托管容器收集网格，适配差异留证。水面中央带反向、非邻接岸壁正面积相交是**几何风险**，不是 GPU 或实际画面验收。岸壁沿路径距离阈值为显式诊断分组，不能声称复刻历史判定规则；不同高程的投影不可当3D相交。非平面自动补证与预算扩展合并使用[固定交付协议](repeatable-delivery.md)中的通用脚本，保留原始结果，不从某轮报告目录调用临时实现。
- **真实绘图**：基本布局异常和网格风险逐关绘图，棕色三角片及红圈标风险位置，另给普通/激活盒/复杂路径代表图。图来自当前生产数据，不画示意图冒充检查。没有布局异常也不能隐藏网格风险图。

输出 `report-fragment.json` 全部字段（`pipeline_version=2 / inventory_file / layout / solvability / visual / summary_rows / table / anomalies / risks / samples`），三种逐关结果和每关 `details/*.json`、原始输入、源哈希、编译/适配差异及图。`visual-summary.json` 单独计岸壁/水面风险关卡数，同关多来源只算一关；广口径内弯相交只保留诊断证据，不混入非局部风险计数。合并 fragment 不得挑字段遗漏求解或视觉结果。登记真实布局、求解执行日志；未定/阶段失败继续保留具体原因，不用旧产物或手工填数补绿。首次离线环境依赖受阻时继续其余可完成分析，报告相应维度未完成。

### 范围与结果收口

1. **确定真实范围。** 从生产加载入口确认关卡来源、分组/模式、有效 ID 和过滤规则；执行同一加载/枚举路径，输出 `levels/level-inventory.json`。清单逐条记录 `level_id / source / group / mode`，另记发现数量、排除规则及原因。仅扫描某目录、抽样几关或只跑 QA Runner 不算枚举完成。发现源数据与运行时有效关卡有差异时，以运行时入口为准并把差异写入证据。
2. **逐关做布局判定。** 使用真实解析后的布局和已查明的生产规则，逐个关卡记录 `level_id / verdict / checks / evidence`；`checks` 至少覆盖本项目实际适用的坐标边界、占位/重叠、引用、颜色/数量/机关关联、泳道和容量。合法覆盖或表现叠放须按生产规则区分，不能凭坐标接近误报。结果保存为 `levels/layout-results.json`，并保留机器可读的原始数据/日志。每关都要有结果；若某条规则无法从项目规则确认，单列未决，不将该项判通过。
3. **逐关检查有解性。** 优先调用现有无表现求解/回放入口，并确认其输入与生产加载数据一致。逐个关卡记录 `level_id / verdict / solver / budget / evidence` 到 `levels/solvability-results.json`。找到候选解后需按生产规则回放至成功；预算耗尽、工具异常、无入口或结果不确定一律记为 `未定`，不能记无解或通过。静态审查求解器实现不能代替逐关执行结果。
4. **生成异常布局图。** 每个已确认布局异常从对应的真实关卡数据绘制 PNG/JPG/WebP，图上清楚标出关卡 ID、异常对象/坐标、判定规则和必要图例；同时保存对应原始输入及判定证据。禁止用手绘示意图、截图拼贴、示例关卡或仅由源码推测的数据冒充结果。每个 `anomalies[]` 都要回链 `layout-results.json` 中同一关卡的异常项。
5. **对账后才能收口。** 报告中的 `total` 必须等于有效枚举数，`checked` 必须等于有明确结果的唯一关卡数，逐关结果 ID 不得重复或有清单外 ID。只有全部关卡均有结论且无未定项，才可标 `检查完成未见问题` 或 `发现问题`；部分完成标 `检查未完成`，根本没有逐关数据标 `未检查`。任何未定结果都会使该维度保持未完成。完整巡检因此只能标 `执行不完整`，不能用功能源码覆盖率抵消关卡缺项。

推荐每维度结果文件的顶层结构为 `{"schema_version":1,"inventory":"levels/level-inventory.json","total":N,"checked":N,"results":[...]}`。`results` 必须是一关一项，含 `level_id / verdict / checks / evidence`；有解性另含求解入口和预算。具体状态值见[报告契约](report-contract.md)。没有成熟可运行求解入口时仍须做完范围枚举及所有确定可判的布局检查，保存逐关未定原因和下一步可自动执行动作；不能把“逐关玩一遍”交给同事，也不能称关卡全量检查完成。

## 什么才算外部剩余项

本地可控制的时间、状态、随机数、配置、持久化、SDK/网络回调和页面关闭顺序均不属于“必须人工”。缺入口或编译依赖属于本地技术缺口，应自行继续分析或明确局限，不直接转人工。

只有以下外部事实允许进入 `external_checks`：真实设备表现、真实平台/SDK运行行为、线上部署与实际下发、可信已发布版本差异。已提供源码定义的 SDK/服务端字段合同、接收、验单、发货与持久化逻辑属于本地检查，按[跨库契约](cross-repo-release.md)取证。每条外部项写具体断言、依赖事实、为什么源码/本地输入无法确定、已完成的本地场景 ID 和尚需查证的最小事实。外部项只作静态范围限制，默认不执行、不派人工任务、不参与静态未完成计数；仍保留条件风险，不把未知判为安全。

例如“SDK是否可能只发失败不发关闭”可待外部核实；“该回调序列下客户端会不会一直暂停”必须由源码或本地探针回答。不要把整个广告功能丢给人工。

黑盒步骤是已有缺陷供人复核的附属资料，不是给人布置未执行任务。不要求正常功能都造一套人工步骤；无问题给静态检查记录即可，有问题优先提供可复核的白盒推导/本地复现，确有可核定玩家路线时再附黑盒步骤。


## 深度不足时的续查条件

“查到了入口”不等于“查完了功能”。在输出绿色前，执行者必须把入口一路连到门禁、状态写入、异步回调和最终消费者，并将每个可达条件登记为 branch。以下任一情况都必须进入 Agent 自动续查队列；棕色仅用于中间报告，不能据此结束全量执行：

- 只读了公共管理器、事件名或单个正常路径，没有读到本功能的条件分支和消费者；
- 有源码路径但没有准确行号、没有说明该行对当前场景的作用；
- 有 branch 但没有对应的场景、预期/实际结论或 coverage 归属；
- 把本功能的所有问题复制到每条场景，无法说明问题在哪个分支成立；
- 把本地可推导的时间、回调、缓存、旧档、配置组合或页面关闭顺序写成“必须人工”；
- 只因没有设备、后台或旧包就停止客户端代码检查。

报告中的“未完成”必须回答三个问题：还没读哪条真实分支、缺哪份本地证据、下一步可以执行什么动作。不能只写“静态检查未完成”。

## 交付约束

每功能输出 `static_audit`，字段与生成器门禁见[报告契约](report-contract.md)。静态完成度、可选本地执行、外部事实分开。不能只把旧报告的“未完成”改绿；未读分支必须实际检查后才能完成。旧报告保留历史结论，不因升级 skill 自动补造证据。
