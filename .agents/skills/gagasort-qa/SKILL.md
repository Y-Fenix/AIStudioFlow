# GagaSort QA

**跨库发版链路**：检查内购、数数/Adjust/Firebase/BI、插屏/激励和升级/重装时，读取[跨库发版检查契约](references/cross-repo-release.md)。按 `assets/cross-repo-gagasort.json` 定位客户端、Android/iOS SDK、SDK 服务和游戏服务，补齐实际依赖与本轮断言后执行 `scripts/cross_repo.py` 基线/账本校验；结果并入现有功能、埋点和安装详情。它不替代原全量门禁，不因提供服务端源码把真实平台入库或部署版本判为已验证。

**调用边界**：仅接受用户明确调用 `$gagasort-qa`、通过技能选择器手动选择本 skill，或明确要求使用本 skill。普通问答、代码与配置查询、机制 Bug 检查均按当前任务直接处理，不自动启用本流程。询问、评估或修改本 skill 本身不触发 QA 执行。`agents/openai.yaml` 中的 `policy.allow_implicit_invocation: false` 关闭隐式调用。

## 默认离线交付与可选飞书授权

默认交付固定查看器，保留“更新表格”、CSV 导出与提单。查看报告无需服务；更新表格及提单复用本机飞书桥接，读取前校验实时登录。不得把文件拆分误当作删除飞书功能的授权。历史报告不保存或继承授权信息。

用户需要飞书能力时，复用会话已有授权；缺少授权才询问一次：

> 是否授权本次通过你在 HTML 中粘贴的 Bug 表格 URL 读取表头，并在你手动点击“直接更新并提单”后写入？不授权仍可继续只读巡检和生成报告。

只有收到本次明确的“授权提单”或等价肯定答复，才允许启动飞书多维表格读写会话、在 HTML 中启用写入按钮或执行外部提单。拒绝、未回答或范围不清均按未授权处理：继续静态检查、自动化执行和报告生成，但不读取 Bug 表格、不发起外部写入。授权不从历史对话、旧报告、旧 HTML、本地登录态或飞书权限推断，也不跨本次运行继承。Skill、报告加载、筛选和表头预览永远不自动创建 Bug 单；真正写入还必须由用户在 HTML 中手动点击“直接更新并提单”。

默认替同事完成代码层面的检查并输出结论，不是给同事生成一份待执行任务表。只报告证据支持的事实，不承诺发现全部缺陷。已提供的原生 SDK 和服务端处理源码纳入本地检查；默认不安排人工验收。真实设备、支付平台、平台入库、线上实际下发与可信旧发布差异仅记静态范围限制，继续检查本地各库的输入、处理及消费链。

## Quick start

**本机维护顺序（用户已确认）**：先修改并验证全局 skill，再同步到 `/Users/yf/Documents/Unity/gagasort/文档/测试文档/` 的对应目录，最后同步到 RuneSkills。全局位置：`gagasort-qa` 为 `/Users/yf/.agents/skills/gagasort-qa`，`test-case`、`test-codetest` 为 `/Users/yf/.codex/skills/` 下同名目录。RuneSkills 对应 `test/gagasort`、`test/common/test-case`、`test/common/test-codetest`，用于最后归档与分发。用户明确指定项目内 skill 时按指定目录加载，不重定向到 RuneSkills。同步前比较差异，保留无关改动；排除缓存、认证与运行产物，不自动 Git 暂存、提交、拉取或推送。

**联动维护**：三个位置均保留独立目录；每轮按上述顺序同步完整有效文件并校验一致性，包括 `agents/openai.yaml`，保持仅手动调用策略。已有冲突不静默覆盖，不用全目录删除镜像。报告功能变更同时维护生成器、模板、契约、版本指纹和交互回归。具体见[本机同步规则](references/repeatable-delivery.md#本机同步规则)。

**固定执行版本**：全量总控先读[固定执行与同事交付](references/repeatable-delivery.md)，按其顺序完成并调用本 skill 目录的 `scripts/finalize_report.py` 收尾。报告模板和版本由 `assets/delivery-profile.json` 固定。只更新 skill 不触发全项目巡检；不得复制上一轮数量、问题和通过结论。

**默认交付固定为通用 HTML 加批次三项**：遵守[便携报告协议](references/portable-report.md)。报告校验通过后调用 `scripts/publish_report.py --run-dir <本轮结果目录> --output-root <工程>/文档/测试文档/质量报告`。根目录复用一个 `查看报告.html`，与它同级的 `YYYYMMDD-HHMMSS/` 每轮仅存 `report.md`、`bugs.csv`、`images/`。查看器读取时间戳文件夹，保留已认可 UI、完整23列表头、步骤、归因及图片。必要文本证据摘录进入 MD，图片按内容去重；不内嵌原始全文，不生成第四个证据目录。内部源码快照、日志、探针与校验回执仍存本轮 `QA/results/`。发布绑定已通过浏览器检查的文件哈希，禁止另写临时导出器、覆盖旧批次或改动旧 HTML/CSV。查看器版本不同则停止覆盖并报告，不擅自升级；发布失败不得声称交付完成。

**Bug 单固定字段**：版本号统一为 `Codex`；不作为游戏真实版本，不改变检查基线。历史格式转换只读原文件且标注未重新巡检，不产生新审计结论。

**质量稳定性门禁**：每轮必须生成 `quality-gate.json`。它只统计本轮基线、当前报告数据、当前执行回执和续查队列，问题按稳定 ID 去重，结果按固定键排序，不读取历史报告补齐。`audit_complete=false` 时只能输出“本轮确认问题”和棕色未完成状态；只有报告、证据、交互校验和续查队列全部通过，才能输出“全量检查完成”或“范围内未见问题”。`report_ready` 只表示 HTML 可读，不代表检查完成。门禁测试见 `scripts/test_quality_gate.py`。

**路径边界**：skill 所在的 RuneSkills 仓库与被测 GagaSort 仓库分别定位。所有 `--root / --repo`、生产源码、开发文档、`tools/agent-task` 和 `QA/results/` 属于本次被测游戏；脚本、references、模板属于实际加载的 skill。文档中的游戏路径均相对被测仓库根目录解析，禁止相对本 skill 目录向上查找或把 RuneSkills 当成待测游戏。当前会话被测项目为 `/Users/yf/Documents/Unity/gagasort`，同事运行时从其项目上下文确定。

只输入 `$gagasort-qa` 即进入**全项目巡检**，无需补需求、用例或选择模式。不要询问“要测哪个功能”，不要自动缩成最近修改或 QA Runner 已登记模块。礼包、活动、排行榜、头像、多语言等周边系统逐项审查并在报告中直接展示；入口盘点、安装影响和局部测试不能代替业务链审查。读取[全项目代码与配置巡检](references/full-project-audit.md)、[升级与重装回归](references/upgrade-and-reinstall.md)、[多 Agent 全量审查协议](references/multi-agent-audit.md)和[项目知识路由](references/project-context.md)，完成发现、分析、执行和报告。

用户明确指定功能、缺陷、需求稿、用例表或代码差异时，进入定向模式；只处理该范围及真实耦合影响。材料解析见[输入解析与交付报告](references/input-and-reporting.md)。询问用法、修改 skill 本身不触发项目全量测试。

**开发修复后的定向验收**：用户要求检查 `bug-progress.csv` 中“处理状态”为“待验证”的 Bug 并回填时，必须先读[Bug 定向验收与回填](references/bug-acceptance.md)，按该专项协议执行。只验收筛选项及真实关联回归，在“处理状态”右侧新增或更新“验收状态”：通过填“已验证”，原问题仍在或确认修复引入关联缺陷填“重新打开”；未完成不得伪造结论。保留开发填写的处理状态、其他原内容和原始报告存档。该分支不套用全量派工、全量范围门禁、关卡扫描、报告生成与发布流水线；交付 CSV 回填、逐项证据及固定 Codex 总览，不自动重生成原 HTML。

全量默认按[多 Agent 全量审查协议](references/multi-agent-audit.md)分发玩法、关卡、系统、配置/存档与埋点专项审查，再按[逐功能静态执行协议](references/static-first-audit.md)合并。 dossier 必须遵守 `deep-v2` 三件套（真实 branches、七维 coverage、逐分支 checks）；旧版只有 checks/gaps 的浅 dossier 会被拒绝，不能用模板场景补齐。埋点专项读取 `references/tracking/tracking-contract.json`，完成表内/表外事件双向覆盖、属性、统一上报出口、重复/异步和 SDK 自动采集边界检查。逐场景记录初态、输入、预期、源码推导、实际结论和证据。能静态判断就直接给结果；有歧义时自动用隔离时钟、回调、配置和存档补证。没有设备、SDK或编译缓存不能成为停止源码检查或转交人工的理由。只完成入口盘点而没有专项 dossier 的功能必须进入 Agent 续查队列，不能以棕色报告作为全量完成交付。

静态完成度、本地运行记录、外部事实分别记录。外部事实仅记录范围限制，默认不生成任何人工待办。正常功能无需填黑盒步骤；已有缺陷附可复核白盒推导/本地复现，有准确玩家路线再补黑盒。升级 skill 不触发全项目重跑，不能把旧报告未查项自动改成通过。

运行测试、生成报告、构造隔离的测试配置/旧档副本，以及为可疑路径编写并运行最小本地探针，属于默认巡检范围。跨库默认先静态闭合；本地运行仅用于本 skill 原有必要补证或用户明确要求执行的范围，先核对测试副作用和实际覆盖，不自动全跑 SDK/服务器测试。探针源码和输入保存到本轮证据目录，临时编译产物放独立临时目录；复用真实生产代码及成熟入口，不复制生产算法，不修改既有断言迎合结果。遵守项目禁止临时 Unity Runner 的约束。生产代码、正式资产/存档、已登记测试、线上配置、真实账号、设备安装/卸载和 Figma 不因巡检获得修改授权；这些外部执行动作不在默认静态范围内，不创建人工验收任务；继续查完已提供各库对可构造输入的处理。

常见请求：

- `$gagasort-qa`：直接执行全项目代码、配置、升级与重装巡检。
- `$gagasort-qa 只检查复活礼包`：执行该功能及关联支付、奖励、存档、配置和升级/重装回归。
- `$gagasort-qa 审查这份用例表`：核对规则、参数实例和覆盖，保留原表。
- `$gagasort-qa 验收这份 bug-progress.csv 中处理状态为待验证的 Bug，并回填验收状态`：定向核对修复与关联回归，按专项协议回填并回复总览。

## 固定范围门禁

无参数全量必须先读[固定测试范围](references/audit-scope.md)，加载 `assets/audit-scope.json` 的全部固定 ID、业务名和必查内容。先执行 `scripts/audit_scope.py prepare` 生成本轮 `scope-lock.json` 与未审查的 `feature-inventory.json`，再建立基础数据、派工和审查。禁止根据已完成 dossier 反推功能清单，禁止把礼包、活动合成一个功能或只填五个类别。缺源码锚点、发现未归属文件时先修正盘点并新建锁，不能跳过再出“全量完成”。

专项 `checks[].scope_targets` 必须回链固定 `check_targets` 原文；每项必查内容都要有结论闭合且带源码证据的场景。合并、续查、质量快照和最终交付再次核对范围。缺功能、重复编号、改名改分类、缺锁或基线变化均失败；功能数从本轮完整明细计算，不相信手填汇总数。定向模式仅限用户明确指定并记录 `scope_control`，不能用它规避无参数全量检查。范围固定不代表业务已审或保证 Bug 数固定。

## Workflow

以下为巡检主流程；开发修复后的 CSV 验收使用[专项协议](references/bug-acceptance.md)，不机械执行下列全量步骤。

1. **确认基线与范围。** 先做初始预检；无参数时随后盘点全项目功能与入口，再按模块分批补齐预检，不能用 Git 改动清单代替全量范围。在仓库根目录按目标路径运行 `tools/agent-task preflight`；有无关改动时使用多个 `--path` 限定范围。再检查 `git status --short` 并保留无关工作区改动。记录绝对路径、分支、HEAD、工作区差异和相关子模块版本。不得拉取、切换分支、提交或覆盖无关改动。
2. **默认离线；飞书仅按需。** 查看和导出不依赖飞书；用户需要表头同步或提单时，复用本次会话已有授权，已明确授权后运行 `python3 scripts/ensure_feishu_auth.py --start-bridge`。已有 `base:block:read`、`base:field:read`、`base:field:update`、`base:view:read`、`base:record:create` 的有效或可刷新用户会话直接复用；不申请不存在的 `base:record:write` 权限。若脚本退出 3，立即向用户展示本次返回的授权 URL 和二维码并结束该轮；用户完成授权后才用本次设备码继续 `ensure_feishu_auth.py --device-code <本次设备码> --start-bridge`，不阻塞等待、不把设备码或 token 写入报告/分发包。未授权或连接失败只暂停飞书，不影响静态检查和 CSV。用户在 HTML 点击“更新表格”或“提单”打开“新建 Bug 单”，粘贴飞书 Base/Wiki URL → 读取表头 → 检查全部内容预览 → 手动点击“直接更新并提单”。打开、读取和预览不创建记录或模块选项。功能模块统一使用 `【Codex-{功能模块名称}】`，去除名称开头的 ✅ 等装饰；不匹配原业务选项。前后端归一化必须一致且幂等。读取表头和预览不得创建选项；仅在用户手动点击提单后，桥接先读取完整字段定义，保留原选项、颜色、说明、默认值和单多选类型，追加缺少的 Codex 选项并读回确认，再创建记录。同名 Codex 选项已存在时复用。动态选项不得改成静态选项。模块为空、不可写、权限不足或创建未确认时必须阻断提单，不能省略模块或使用默认模块。授权预检除读取表头和创建记录权限外，必须检查 `base:field:update`；缺权限先补授权，不得伪报已具备提单权限。已提交记录不自动修改或重提。
3. **读权威来源。** 按 preflight、`文档/开发文档/模块定位索引.md` 和命中模块文档定位规则、调用入口、已知限制与历史回归；对失败断言或已报告缺陷，必须检查模块文档中的验证／限制／历史结果章节及其指向的相关实施记录。涉及奖励、存档、时间、支付、配置或生命周期时补读索引 §1.1 的对应准则。测试落点按[项目 QA 知识路由](references/project-context.md)交叉核对；实现现状不能代替需求预期。按任务复杂度和根 `AGENTS.md` / Harness §5.3.3 执行角色分工；项目要求独立测试或 Review 时，使用可用角色并记录实际交接，不能独立委派则明确未复核。
4. **建立双向覆盖账本。** 全量模式以功能、代码路径、配置键和安装链路为来源，按全量参考文档记录覆盖矩阵；定向模式将需求条款、缺陷主张、用例行/参数实例或代码变更影响拆成稳定 ID；记录来源位置、当前规则、生产路径、前置/输入、预期和禁止副作用、现有测试、验证层级及结论。需求到证据、用例到有效规则两边都要闭合；遗漏单列，不混入已覆盖或已通过数量。输入类型的具体检查见[输入解析与交付报告](references/input-and-reporting.md)。
5. **分发专项 Agent。** 系统专项必须包含多语言，读取[多语言静态检查](references/localization-audit.md)。按[多 Agent 全量审查协议](references/multi-agent-audit.md)分别生成玩法、关卡、系统、配置/存档与埋点 dossier。埋点 dossier 必须引用本地固化契约，并给出事件、属性、统一出口、表外事件和 SDK 边界的源码证据。每个 dossier 必须有当前 HEAD、真实入口、条件分支、最终消费者、准确行号和具体缺口；禁止用一个公共入口或模板句填满七个维度。没有 dossier 的功能只算盘点，不算深审。
6. **逐场景静态执行。** 必须读取[逐功能静态执行协议](references/static-first-audit.md)。对 C# 先用当前会话 CodeGraph，不可用按项目协议回退。逐功能追到真实调用方、门禁、状态、异步、最终奖励/资格/存档消费者；覆盖七个维度，每条场景写具体输入、顺序、依据、预期、推导链与结论。不适用须有功能特定依据；不能只搜关键词、只读入口或复制公共模块结论。
7. **自动补证与归因。** 静态链闭合就判静态结果，不为得到结论强制跑游戏。歧义优先查路径映射、业务自动化说明及现有接缝，按需执行相关局部测试或隔离探针，不先全跑无关脚本。缺依赖时继续源码/数据检查，能独立编译的复用真实逻辑补证；做不到只记录具体技术缺口。失败按[归因协议](references/triage-and-validation.md)核预期、夹具、入口与生产行为，不把测试错误当产品 Bug。
8. **配置与关卡自动检查。** 配置逐键追解析、缺省、覆盖、缓存/hash、通知和消费点；本地构造边界/组合，不以没连后台拒绝判断客户端。关卡必须实际执行 `scripts/scan_levels.py --repo <仓库绝对路径> --output <本轮证据目录>/levels`。这个入口默认全量执行：manifest/打包对账 → 五组基础布局 → 正式 Validator → 无道具正式求解及全新运行时回放 → 动态和正式配方的岸壁/水面网格检查 → 风险位置绘图。无需启动 Unity 或依赖 Library。合并它生成的 `levels/report-fragment.json` 全部字段，登记 `RUN-LEVEL-LAYOUT`、`RUN-LEVEL-SOLVER` 真实执行日志；报告必须使用 `pipeline_version=2`，保留配置合法性、打包一致性、通关、岸壁、水面五项摘要和逐关表，不能退化为只查节点/泳池。预算耗尽是未定，岸壁/水面几何命中是棕色风险，不能当已证无解或实际画面 Bug。每个风险必须有真实数据标位图和复核步骤；布局绿不能代替有解或表现网格结论。细节见[逐关流程](references/static-first-audit.md#关卡有解与布局)。
9. **静态分析升级/重装。** 按[升级重装协议](references/upgrade-and-reinstall.md)，每功能分别推导保留本地、清本地恢复同一身份、清本地建立新身份的状态/迁移/云合并及消费者。默认不要求真实安装。只有确实需要已发布版本差异的断言单列外部事实，其余本地完成。
10. **完成门禁与固定报告。** 先按[自动续查与完成门禁](references/multi-agent-audit.md#自动续查与完成门禁)分小批次合并，执行 `scripts/audit_completion.py`，由总控消费队列继续检查，不能把队列交给用户。门禁返回 2须续查；求解资源或几何风险仍未闭合时，按[固定交付协议](references/repeatable-delivery.md#完成与未完成的明确区分)保留实际补证、剩余限制与未完成状态，不伪造全量完成。之后按[报告契约](references/report-contract.md)调用 `scripts/finalize_report.py`，统一导表、核源码、生成便携批次并真实执行浏览器交互检查，再调用 `scripts/publish_report.py` 发布已验证文件。默认不生成内嵌全文的 `report.html`；用户明确要求旧联机格式才传 `--legacy-html`。新巡检填 v2.1 的逐功能 `static_audit`；生成器缺场景、缺源码证据、缺维度适用性或静态未完成却报通过时拒绝输出。首屏必须同时显示“已盘点”和“已深审”；没有专项证据的功能只能棕色，不能因为没有 finding 自动变绿。保留用户确认的玩法/关卡/系统/配置/埋点五类样式与绿/棕/红规则。静态已证问题标明未动态运行，方法复现与玩家可达性分别说。缺陷修复确认后回写现有 QA/模块文档，不修改产品文档。

## Evidence rules

- 报告默认打开独立“总览”页签；汇总卡片和执行范围只在总览显示，五类模块页签从本模块内容开始。
- 固定查看器保留“更新表格”和提单；加载本地报告不访问飞书。用户点击读取表头后才通过本机桥接读取，检查预览后手动确认才写入。不继承历史授权信息；连接或登录不可用时明确提示，不禁用更新表格入口。
- 总览固定包含 Bug 列表：默认完整保留 `assets/bug-columns.json` 的23列表头及空列，只纳入本轮已确认问题。缺陷描述必须含前置条件、具体操作步骤、当前错误表现、预期正确表现；按[Bug 文案规范](references/input-and-reporting.md#bug-文案规范)生成，缺项阻断导出和提单。飞书 URL 及提单格式参照 `test-case` / `test-codetest`，但不执行它们的用例流程。“新建 Bug 单”弹窗固定为 URL → 读取真实表头（含视图顺序）→ 全部内容预览 → 手动直接提单；不混入 Bearer/备用授权/二维码。按精确名和受控别名分别填标题、步骤、预期、实际、归因；未知列空，系统与附件列保留展示但不普通写入。读取失败或 URL 变化清除旧提单状态；提交前后校验表头、字段类型与全部 record_id_list，连点只发一次，结果不明锁定并提示核对，不自动重试。CSV 总是导出全部问题和当前列，默认配套 `bugs.csv` 不变。
- 各模块固定先给结论和四项可点击指标，再列问题 / 风险，最后检查明细。模块归属与功能引用的问题取并集，禁止漏掉未关联功能的问题；未完成与已确认问题分别计数，不能用零问题冒充查完。筛选、返回、图片直达及计数口径按报告契约固定执行。
- 报告面向接手测试：有对应图片解释时，摘要与逐关表的主入口直接跳到图片和白话核查说明；原始证据收进“开发核对”，不要求先读 JSON 才能理解结果。关卡图的分类和深链规则按报告契约执行。
- 当前运行结果必须来自本次基线和本次日志。历史报告只能说明历史事实，不能替代当前执行。
- 交付前复核 HEAD、相关子模块与已引用源码哈希。发现期间外部更新时保留原证据，报告首屏列出变动与待复审范围；报告可读性/证据完整性与当前源码匹配分别给结论，不改旧哈希冒充新版本已审。
- 环境或依赖阻塞已有测试时标记自动化受阻，不改判为黑盒或产品缺陷。没有完整摘要、零测试、跳过、超时或旧报告均不能算通过。
- 静态推导、自动化执行、Editor/PlayMode、设备和人工验收分开陈述。静态已完成不等于真机验收；没有跑可选动态测试也不等于静态未完成。不得把某一层通过扩大成项目整体无 Bug。
- 缺陷按用户或项目已有严重性标准排序；没有可查标准时，按实际影响范围、触发概率、数据/资金损害和恢复难度说明优先级依据，不自造 P0/P1 标签。每项提供稳定 ID、影响、触发条件、规则依据、预期/实际、复现与证据。
- 区分自检与独立审查。测试编写者或修复者的自检不能写成独立验收；项目流程要求独立测试/Review 且当前没有独立执行者时，明确标为“未独立复核”，不能代填通过。
- 缺陷修复与生产代码修改遵守根 `AGENTS.md` 和 Harness §5.4；需求/用例审查不自行扩展为生产代码修改。用户明确要求修复时，完成同场景修复前失败、根因修复后通过和规定验证；未要求修复时仅输出审查、测试和回归建议。
- 输入为 Excel 时先识别工作表、参数场景和关联回归；保留原文件及其顺序，默认另存结果副本。工具无法完整读取时说明具体缺失，不假称已审完。
- 生成或审查用例时不按数量堆场景：对真实适用的阈值、配置优先级、状态迁移、幂等、失败/恢复、时间边界和共享消费链逐项判断；不适用要给规则依据。每条参数实例独立核对预期，用户原表的步骤和预期不静默改写。
- 对需求至少做一次反向审计：从权威规则重新检查明确条款、参数、例外和不变量是否都进入账本；对代码变更至少检查直接调用者、共享配置/状态、订阅者和消费者是否覆盖或有排除依据。
- 若本轮修改 skill、测试、用例或文档，先核实仓库绝对路径、分支与 role，并按项目要求配置 Worktree 身份；结束时限定任务范围运行 `tools/agent-task verify --path ...` 和适用测试，再检查状态，确认没有带入无关改动。生产代码 Bug 修复另按项目 Bug 闭环和验证门禁执行。
