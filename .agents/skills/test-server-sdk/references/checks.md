# 最低静态检查矩阵

每个平台独立检查以下八组，共至少十六组结果。每组内分别审查子项，存在不适用的子项要解释。Android 与 iOS 证据不能互相代替；服务端共享实现允许引用同一证据，但分别核对平台入口。

| 每平台 ID 后缀 | 必须追踪的内容 |
|---|---|
| purchase | 商品 ID、价格/币种来源、包/环境路由、初始化/连接状态、购买拉起、取消/失败/成功/待处理回调、交易完成/消费/确认时机；失败不发奖 |
| delivery | 收据/签名与交易来源验证、用户/包/商品/订单绑定、项目回调路由、发货确认、数据库唯一约束或等效原子幂等、并发重复/乱序/超时/进程重启/补单、持久化与客户端同步 |
| tracking.thinkingdata | 初始化与同意状态、项目与环境、匿名/登录身份切换、事件/属性/收入单位、过滤条件、线程/队列/持久化、网络失败/重试/去重、实际发送出口 |
| tracking.adjust | 同上，另外核对 token 的配置来源、收入及归因回调；不暴露 token |
| tracking.firebase | 同上，另外核对原生直传与 Measurement Protocol 是否实际使用、参数类型、事件名限制、双路重复；HTTP 成功不等于平台入库 |
| tracking.bi | 同上，另外核对批量确认、WAL/缓存恢复、失败批次是否被提前删除、身份与项目路由、去重是否误丢合法事件 |
| ads | 插屏与激励分别追踪：初始化→加载→展示→奖励/关闭→状态释放→重加载；静态推导至少连续两次。检查加载/展示失败、无填充、前后台、重入、回调重复/过期、一次展示一次奖励、奖励与关闭回调职责及持久化 |
| installation | 覆盖安装版本迁移与默认值、账号/设备身份稳定性、密钥链/备份/本地文件存储差异、卸载重装同身份与新身份恢复、服务端存档冲突/合并、购买恢复、广告与付费资格；客户端存档/奖励实现不可见部分应阻塞 |

## 推理纪律

- 锁、幂等与去重需定位到真正保护写入的层级，不能看到缓存 Set 就认为跨进程幂等，也不能因为某函数没锁就认定全链路没锁。
- 沿调用链核对 payload 字段、时间/金额单位、错误码、超时与重试责任；跨库接口版本不明时给出兼容风险，不能假定四个 HEAD 同时部署。
- 检查项目配置、平台条件编译、依赖锁定与构建选择是否让代码实际可达。示例配置不是接入证明。
- 区分广告收入 S2S、广告播放、游戏道具发奖三条链路；收入上报成功不能证明后两者。
- 卸载是否清理钥匙串/备份及真实第三方行为需要运行环境证据；源码只能支持已看到的策略。
- 没有客户端时可以完成 SDK/服务部分，但购买按钮、最终到账、游戏道具、完整存档迁移不得写成链路闭合。

## 证据边界

每条结论给出已审查的函数/分支及行号，跨库链路至少展示发送端与接收端，缺一端标明缺口。对未发现问题的结论同样需要证据。遇到动态配置缺失时先查配置读取与回退机制，不能编造配置值。

最终待验项写清平台、前置条件、操作、预期、所需日志或后台证据。只提出待验步骤，不在静态审查中执行。
