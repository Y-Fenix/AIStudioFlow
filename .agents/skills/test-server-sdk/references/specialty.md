# 代码专项审查

每次四库审查都读取本文件。与十六组业务矩阵并行记录，不能用一次语法检查替代专项控制流分析。各库分别建立下列领域的断言；未完成追踪写 blocked，缺少触发证据的模式不能写 issue。每条记录实际读取的文件/函数，不承诺全仓没有某类问题。

| 领域 | 必须核对的行为 |
|---|---|
| syntax_types | 用已执行的解析器证明语法范围；类型、符号解析、平台编译及依赖兼容另列结果。动态 JS 不能靠解析证明类型正确。 |
| loop_retry | while/do/for 的退出条件、状态变化与取消；递归每次是否缩小输入；重试上限或可取消性、退避、总超时、异常路径退出；异步回调递归也检查进度。 |
| concurrency | 共享状态读写、锁覆盖范围与顺序、await/回调内锁持有、主线程同步等待、跨进程幂等；检查同一资源上的同步队列重入与锁反向获取。 |
| lifecycle | 定时器与任务是否绑定请求/订单/展示 generation；成功、失败、取消后是否取消旧任务；旧回调能否清理新状态；监听注册/注销、前后台、实例销毁。 |
| null_errors | Kotlin !!、Swift as!/try!、数组索引、缺失字段及默认成功值；沿前置校验与生产端 schema 确认可达性；异常吞掉后是否误报成功或遗漏状态清理。 |
| resources | 文件/连接/游标/监听/协程的释放与 finally/defer；无限增长队列、持有 Activity/闭包、无界并发、UI 线程阻塞。 |
| data_contract | 秒/毫秒、微单位/主币种、舍入、数值溢出与 JS 大整数；字段名/类型/状态码/版本、身份/包名/订单绑定；缺字段是否被当作成功。 |
| persistence | ACK 与删除的先后、事务/唯一约束、持久化前后崩溃、批次部分成功、WAL 写失败传播、重启后队列恢复、迁移失败回退。 |

## 反例与证据要求

- `while(true)` 不等于死循环：核对 break/return/cancel、阻塞等待与循环内进度。常驻 worker 可以持续运行，但需说明调度、取消与故障退避。
- 重试次数无上限不直接等于缺陷：有退避、取消和明确常驻需求可能合理；忙等、无进度反复发送或不可停止才有具体影响。
- 递归日志批处理若索引不变即退出，不报无限递归。反过来，不能因为存在一个 return 就认定所有错误分支可退出。
- 超时回调读取全局 currentOrderId：沿请求 A 结束、B 开始、A 超时的时序检查。仅捕获 productId 而未绑定订单/generation 不能阻止旧任务影响新请求。
- 已发货 status=100 的补单：检查是否再次触发成功回调、是否重置 finish/ack、宿主是否持久化幂等。SDK 重复通知与已实际重复道具是不同结论。
- 验单暂不可用时先发货：先确认协议/业务是否明确允许；若允许则说明补偿与坏账风险，不能把有意策略直接当实现缺陷。
- WAL 返回 false、主接口仍 ACK：核对 WAL 是否必达、是否有第二份持久化与重放。不能仅因一个函数无 throw 就断言全链路数据丢失。
- 死锁必须给出等待关系及可达时序；单处出现 synchronized、NSLock 或 main.sync 只用于定位，不足以定缺陷。

有反例或调用链保护时修正结论；工具告警先核对配置/可达性/排除项，再转为 issue 或 risk。报告里保留工具规则 ID（若有）与人工判断，不将告警条数当缺陷条数。
