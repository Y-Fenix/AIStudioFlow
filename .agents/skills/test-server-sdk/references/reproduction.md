# 黑盒与白盒复现步骤

本文件规定如何把静态发现转成可核验的复现方案。复现步骤、实际执行记录和缺陷结论是三种不同证据，必须分开写。

## 状态

每条 `issue` / `risk` 的黑盒与白盒方案分别标记一种状态：

- `static_inferred`：根据源码推演出的候选触发路径，尚未确认环境或操作可用。
- `ready_to_run`：所有必要前置条件、版本、数据和操作均已明确，尚未执行。此状态只表示步骤信息完整，不代表用户授权或允许突破默认只读边界。
- `executed_reproduced`：实际执行并观察到与预期不同的结果，记录真实环境、操作/命令、结果和证据。
- `not_reproduced`：已按记录执行，但本次未观察到问题；保留执行条件和证据，不自动推翻源码问题。
- `blocked`：缺少完成验证的最小条件，逐项说明缺什么及由谁/何处提供。

未执行的方案必须将实际结果写成“未执行”，不能填入推测结果。`executed_reproduced` 必须有可定位的日志、测试输出、截图或服务端记录；只有 mock 或替身时，明确其边界，不能称真实端到端复现。

状态判定优先级：缺少任何执行必需的环境、版本、身份、数据或安全前置条件时用 `blocked` 并列出阻塞项；必需条件齐全但路径可达性仅由源码推演、尚未核实时用 `static_inferred`；全部已核实且仅待执行时用 `ready_to_run`。所有状态都受主 Skill 的授权及只读约束。

## 黑盒方案

从公开可观察边界触发问题，例如 SDK 公共 API、客户端操作、服务 API 或真实集成环境。每个方案应包含：

1. **目标与状态**：关联断言 ID，写明执行状态及为何选择该入口。
2. **环境**：客户端/SDK/服务版本、设备或运行环境、包名、配置环境、必要依赖。未知值写 `blocked`，不得猜测。
3. **前置条件**：账号/身份状态、初始订单或事件状态、网络/权限/广告填充等条件；使用脱敏测试数据并说明沙盒或隔离环境。
4. **操作步骤**：按序列出精确操作、输入值、次数和等待/重启/切后台等时序。步骤应能由另一位测试人员照做。
5. **观察点与预期**：说明用户可见行为、公开回调/API 返回、后台状态或可查询日志应是什么。
6. **实际结果与证据**：未运行写“未执行”；运行后记录真实观察、时间、版本和证据路径/ID。不得用推断补空。
7. **清理**：说明测试数据清理、订单/奖励回收或恢复初始状态。存在真实扣费、发货、补奖、清档或外部写入时，不执行，除非用户明确授权且测试环境及回滚方案已核实。

缺少客户端、部署版本、沙盒、测试账号或第三方 SDK 时，保留 `blocked` / `static_inferred` 方案并列出最小缺项；不能编造界面、接口、配置、账号或预期服务行为。

## 白盒方案

从被审查的具体函数、分支或持久化边界触发，说明如何构造输入和观察不变量。每个方案应包含：

1. **代码锚点**：仓库、文件、函数/分支及行号；若已有测试入口，记录真实测试文件、用例或命令，先核实其配置与依赖。
2. **执行方式**：写明是现有测试、建议新增的隔离测试、调试器/日志观察，还是静态推演。建议新增测试不可写成已存在。
3. **构造与步骤**：精确输入、初始状态、受控依赖及调用顺序；并发/超时场景写明事件交错顺序。
4. **断言**：状态转换、调用次数、幂等键、持久化记录、回调、错误传播或资源释放等可观察条件。
5. **结果和边界**：未运行写“未执行”；实际运行记录命令、退出码、真实/替身依赖及输出证据。mock 仅证明被替换边界内的逻辑。
6. **清理**：说明临时数据、进程、锁、文件和模拟服务如何还原。

不能仅写“覆盖此分支”或“增加单测”。测试入口不存在时，给出可供开发补充的测试设计，并标明 `static_inferred`；缺少构建/依赖时标 `blocked`。

## 边界用例提示

按领域挑选有代码路径依据的用例，不要机械穷举。至少考虑相关的：

- 字段缺失、null、空串、空集合、零、负数、上下界及溢出/精度转换。
- 成功、取消、拒绝、异常、空响应、超时、断网、部分成功与重试耗尽。
- 重复、乱序、并发、重入、旧请求回调晚到、状态切换与对象销毁。
- 首次启动、升级、恢复、进程重启、卸载重装，以及旧新客户端/服务协议组合。
- ACK、删除、事务、缓存/WAL 和外部回调之间的崩溃窗口。

每个用例都要对应实际字段、状态或调用链证据。无法触达的组合可不测，但说明原因；不能因为清单已逐项列出就声称覆盖完整。

## 报告结构

Markdown 的每个 `issue` / `risk` 使用：

```text
黑盒（状态）：环境与前置条件；步骤；观察点/预期；实际结果；证据；清理。
白盒（状态）：代码锚点与执行方式；输入和步骤；断言；实际结果；证据；清理。
```

`findings.json` 在断言下增加兼容性可选字段：

```json
{
  "reproduction": {
    "black_box": {
      "status": "static_inferred",
      "environment": [],
      "preconditions": [],
      "steps": [],
      "expected": "",
      "observed": "未执行",
      "evidence": [],
      "cleanup": "",
      "blockers": []
    },
    "white_box": {
      "status": "blocked",
      "code_anchors": [],
      "execution_method": "",
      "inputs": [],
      "steps": [],
      "assertions": [],
      "observed": "未执行",
      "evidence": [],
      "cleanup": "",
      "blockers": []
    }
  }
}
```

JSON 和 Markdown 的状态、步骤、执行结果必须一致。`no_issue_found` 可列关键路径的回归步骤；`not_applicable` 写明配置/调用证据与不适用理由；不要求为二者虚构缺陷复现。
