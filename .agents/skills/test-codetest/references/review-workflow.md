# 代码逐断言审查细则

按当前阶段读取对应小节，不默认全文加载。下文 `scripts/` 路径相对于本 Skill 安装目录；§ 编号保留原流程含义。

### 真实账号与外部状态硬门禁

- 自动化执行前先判定数据来源。真实账号付费/订单/排行榜/活动状态、线上后台开关、云档、多设备、广告填充、推送授权、商店支付和真机表现不得由 AI 假设已构造，也不得把本地 fixture 的通过结果写成真实账号通过。
- 以测试用例前置条件的数据来源标记为第一判据，但不能把“准备方式”当成“验证层级”：`【需GM/测试包辅助】`或`【普通操作可执行】`中的确定性配置、状态机、时间、奖励、存档和事件断言，优先进入本地自动化/静态执行；`【需受控SDK/网络环境】`只有涉及真实 SDK、商店、广告填充或真实网络结果的断言才归`需黑盒验证`。同一行若含真实外部断言，必须拆出本地子结论和黑盒残留，不能整行机械降级。
- AI 自行读取代码并静态代入输入，只有明确要求动态测试或项目强制验证适用时才生成隔离夹具并运行。只有必须证明真实后台/账号当前状态时才需要外部入口。没有测试环境 API 不影响本地字段消费规则的判定。已授权外部准备仍须记录入口、环境、参数、响应和复位结果，不自行改线上数据。
- 真实账号/真实 SDK/真机是黑盒边界，不是“需自动化验证”。`需自动化验证`只用于已有自动化入口但尚未执行或因编译、许可证、依赖受阻的本地动态断言；环境问题不能把人工黑盒替换成自动化，也不能反过来。
- 混合用例拆分断言：本地逻辑正常判定，真实账号/平台/设备断言单独保留步骤、观察值和解除动作。code 口径主结果只汇总本地断言，full 口径才汇总全部断言；不能把任一口径的通过冒称全部真机验收通过。
- 禁止按“账号/广告/网络/后台”等关键词机械改判：先读前置条件和操作步骤，确认是否使用本地 fixture、fake adapter 或只读源审计。只有实际依赖真实账号、线上后台、真实 SDK、真机/平台表现的断言才改为黑盒；本地 fixture 仍可自动化，但依据必须写明“不代表真实环境验收”。
- 判定顺序固定为：先静态追踪完整调用链，再代入边界输入及事件顺序；静态已闭合直接给结论。确需动态才能判定时写明具体证明断点，仅在动态模式内补充运行，不在默认模式无限搭建宿主或生成接缝待办。只有外部独有观察才留黑盒。GM/测试包只是输入准备，不是黑盒理由。

## 基线与输入

1. 核实仓库绝对路径、用户指定的本地分支（如有）、HEAD、相关子模块版本及未提交改动。默认在当前 checkout 做只读检查，不切换分支；若用例明确指定了其他分支，先报告当前基线不匹配并等待用户明确授权后再切换。绝不拉取；分支不存在则停止该基线检查，不以其他分支代替。
2. 记录实际检查的是提交快照还是含未提交改动的工作区。已有远端缓存仅作说明，不能宣称它是线上最新；检查结束复核基线，变化时重新检查受影响内容或明确报告失效范围。
   若项目禁止 Git 读取，则以相关文件哈希/快照建立可复核基线，明确提交/分支未核实，不为满足报告格式违反上位限制。
3. 识别所有实际用例表，包括主表、耦合回归及参数场景。读取公共用例与参数的关联、独立预期和初始化条件；辅助覆盖清单不是已执行用例。
4. 保留输入用例的内容、顺序和无编号约定。代码检查不授权删除、合并或改写原期望；发现重复、废弃规则或前置不可达时记录适用性问题，不静默跳过。
5. 需求、旧版规则和实现基线分清。用户明确指定的本期规则优先于被替代的旧规则；当前权威不明或期望不可判定时记录需求待确认，不能按代码现状补一个预期再判通过。只有原用例与已明确的新规则冲突时，原文保留并标 `用例需更新`，给出当前规则及建议期望；这不是产品需求歧义，也不能因代码恰好符合旧用例而判通过。当前规则下已能证明的产品反例另正常登记。
6. 接收 `覆盖核对`、`耦合分析`、`验证分层` 和白盒报告；核对其基线、真实测试文件及覆盖映射，不能只信报告中的通过字样。缺耦合分析时，在相关模块中补查调用、共享配置、状态、事件、存档及本地历史，不改写原用例；发现遗漏另记 `补充回归建议` 和覆盖缺口，不静默加入输入分母或冒充已审。

## 检测方法

先核对 [四维覆盖契约](coverage-contract.md) 的需求、耦合、边界和升级账本；已有用例漏项不能因“全表已审”被隐藏。独立检查不擅改输入，已授权生成/补齐时才补用例并刷新映射。

对每个用例及参数实例执行：

- 把每条用例的期望拆成稳定的断言 ID（例如 `ASRT-001`），分别记录逻辑、数据、表现，并关联来源覆盖项 ID（若输入表没有覆盖项 ID，先在检测辅助表建立映射，不改写原用例）。沿输入/配置 -> 状态前置 -> 调用链 -> 数据变换 -> 资源消费 -> 输出追踪，先证明测试前置及目标路径可达。
- 使用已暴露的符号索引及项目规定入口；不可用时说明原因，再做限定目录的符号、引用和配置搜索。需求名可能与类名、字段名不同，不因同名搜索无结果就停止。
- 检查默认值、范围变换、索引、循环、取模、过滤顺序、fallback、配置覆盖与生成资源。配置 CSV 与实际包内容不能直接等同。
- 尝试现有的只读解析器、导表映射或资源读取链；不要看到 MessagePack、加密或 Addressables 就立即宣告只能黑盒。确实无法取得或核实资源时列具体证据缺口，不输出密钥、令牌或账号敏感信息。
- 对逻辑结论寻找反例：用具体配置、输入和状态证明能到达不符合预期的输出。纯函数的边界输出、固定文案与条件分支应尽量由静态证据给出结论，运行随机输入不必然使所有分支都无法分析。
- UI 文案内容与字体/裁切分开，计时计算与刷新/显隐分开，奖励资格/幂等与真实到账/动画分开。关联逻辑能确认的先确认，只有剩余运行断言交黑盒。
- 多模块耦合继续追到共同状态、回调、存档和奖励消费点；仅定位入口不足以判通过，也不足以将整条直接归为运行限制。
- 对每个静态断言保存“具体输入及固定条件 → 可达入口 → 决定分支和中间值/状态 → 最终消费输出 → 与独立需求预期比较”。多条件检查决定性条件的单独翻转，时间检查实际精度下的前/等于/后，异步检查可达事件排列、队列/锁及迟到/重复回调；升级检查实际旧状态、首启迁移、二启幂等和跨期。不能只证明纯函数而跳过入口接线、持久化或最终消费者。
- 同一原因涉及不同参数或路径时可以复用适用的证明，但逐一检查前置和输出是否相同，不能复制不适用的行号或统一套结论。每个参数实例、回归实例都必须留下独立的断言级审查记录；公共模板的结论只能作为线索，不能直接继承为实例结论。
- 建立逐项审查账本：工作表/用例/参数实例、断言 ID、检查状态、证据 ID、结论和未决原因。先从完整输入独立生成用例/断言清单及原六列指纹，再建立审查账本，不能从已审条目反推输入分母。结束前逐项核对，不以已检查模板数替代实例数。

范围类断言必须核对权威数据中的目标位置及运行映射。例如禁止数据只在源下标0至4，而可达池从下标5开始，不能因无显式类型过滤就判失败。至少检查起点前一项、起点、末项、回绕、空数据和 fallback。

## 自动验证与测试接缝判定

默认静态模式无需动态注入接口；缺 Runner、Unity、账号或现成测试不构成未通过、黑盒或需补接缝的依据。先完成输入代入、调用链和状态顺序推演。用户明确要求运行单元/白盒/Unity 测试或项目强制验证适用时，才查根目录 `QA/`、原生测试、GM/调试入口和框架，优先复用已有测试，不按日期另建源码副本。验证层级沿用 L0 契约检查、L1 单元、L2 状态/数据、L3 编辑器/集成、L4 真实环境观察；L0 不算运行执行。

下表及受控替换、运行证据要求仅用于动态模式，不是默认静态检查的前置条件。

| 对象 | 优先验证办法 | 仍需区分 |
| --- | --- | --- |
| 时间/倒计时 | 固定时钟、受控 patch、推进调度器，覆盖前/等于/后与跨期 | 计算与真实挂起恢复、屏幕刷新不是同一断言 |
| 关卡/解锁/进度 | 构造合法状态、测试存档或已有 GM 输入，调用真实入口 | 可达迁移、旧存档兼容与界面显示分别验证 |
| 配置/随机 | 隔离配置及全量数据审计、固定种子/序列 | 源配置、导出资源、实际包消费不能混同 |
| 网络/广告/支付 | fake/adapter 驱动成功、失败、取消、重复、乱序回调 | 替身证明业务处理，不证明真实 SDK/平台接入 |

- 改输入，不改被测规则；禁止为过测试改阈值、跳过资格检查、直接写最终余额或复制生产算法作被测替身。状态与 patch 每例独立，写明恢复方式；不改系统时钟或正式存档。
- 没有显式注入接口不等于缺测试接缝：先尝试已有 adapter、构造函数、存档导入、框架 patch/假时钟。只有这些均不能在保留真实生产路径的前提下控制目标变量，才列最小接缝改造。
- 环境/许可证/引擎/依赖缺失时，运行状态为 `执行受阻`；代码结论独立保留。只有写清具体静态缺口、且动态执行对判定不可缺少时才标 `需自动化验证`，不能把环境问题直接推给使用者或改成黑盒。可在当前权限内补齐的测试和夹具由 AI 补齐，不列为使用者待办。
- 需要新增或修改测试时衔接 `test-whitebox` 的“项目级 QA 测试资产”规则：稳定源码、夹具、复跑入口和报告生成脚本放项目根目录 `QA/`，必要报告/执行证据独立保存；编译缓存、临时工程和其他过程文件不沉淀到 `QA/`，仅清理本次创建的临时资源且保留失败证据。已有原生测试通过入口与映射复用，不复制源码。该 Skill 不可用时仍遵守这些目录与增量规则，按项目框架实施。检查测试调用真实业务模块、预期来自需求、断言包含关键副作用与隔离清理；只断言 mock 被调用不算证明领奖/存档成功。
- 执行保存实际命令、工作目录、版本/基线、退出码、测试计数、日志和本次结果文件；确认目标测试被发现且结果非旧文件。零测试、跳过、编译失败、超时或缺结果不能算通过；静态推导不替代执行证据。
- 结果表与执行报告必须写入同一份运行时基线：运行开始时读取一次 `branch`、`HEAD` 和工作区摘要，并由结果生成器复用该快照；若 Excel、`report.json` 或日志中的基线不一致，标记“结果记录不一致”，不得继续宣称本轮结果可比。

## 结果分类

保留结果列名称 `测试结果`。它汇总当前声明范围内的断言，code 为本地代码初步结论，full 为全部验收断言，不等于已执行真机。下表的“该行全部断言”均指当前声明范围；纯外部行按外部实际证据归并，未验收则为需黑盒验证，不能空集合判通过。有真实观察的通过可用 `测试通过（真实环境）`或`测试通过（混合证据）`，不能冒称全部自动化通过。

| 测试结果 | 判定条件 | 必须提供 |
| --- | --- | --- |
| 测试通过（静态） | 在明确前置和检查基线内，完整静态证据支持该行全部断言 | 决定行为的文件/行号、输入条件及推导；注明静态结论 |
| 测试通过（自动化） | 该行全部断言及参数均有适用的实际自动化通过证据 | 测试名与输入、命令、基线、退出码、本次日志/结果文件；仍不代表真机验收 |
| 测试不通过 | 对明确需求找到至少一个实际可达反例 | 前置、触发步骤、预期、异常、错误位置及可达链路 |
| 用例需更新 | 权威规则已明确替代原期望或适用范围，原用例不能再作为当前验收依据 | 原期望、当前规则及来源、建议修订；不改原文，不当产品 Bug 或需求歧义 |
| 需黑盒验证 | full 范围仍有真实外部断言，或该行纯外部；账号字段消费逻辑可本地构造，不因真实账号未准备就转人工 | 已确认部分、外部独有变量、不能替代的理由、最小准备/步骤/观察值 |
| 需自动化验证 | 有适用自动化入口，但所需动态断言尚未执行或执行受阻 | 测试入口、未执行/受阻原因、解除动作；不是人工黑盒任务 |
| 需开发补测试接缝 | 所需动态断言可自动化，但当前实现无法受控构造或观察目标状态 | 已尝试的替换方式、最小接缝方案与责任模块；不是业务失败的直接证据 |
| 需求待确认 | 核对权威需求及适用版本后，仍存在会改变预期结论的真实歧义 | 冲突原文/缺项、不同解释分别导致的结果、只需回答的具体问题 |
| 证据不足 | 关键事实依赖当前不可取得的代码、配置、资源或历史数据，且已完成合理的本地追踪仍无法证实 | 已查范围与证据、缺失的具体材料/访问能力、它阻断的断言、可执行的取证动作 |

判定约束：

- 先消除可消除的未决项，再选结果。按“需求条款/版本 -> 输入数据与配置 -> 调用链/状态 -> 资源和映射 -> 输出/断言”逐层追踪；检查项目内等价实现、序列化/导表/资源读取和明确指定的历史资料。不能因为第一轮搜索没命中、工具不熟、代码量大或尚未读完就标证据不足。可在当前资料和权限内继续查时，继续查。
- 按断言判断并先选 code/full 范围。code 口径把外部残留放单独列，不能让一个画面/设备断言覆盖本地结论；full 才将全部未决纳入主结果。原期望不得删减，依据明确已证明部分与未验收部分。
- 每个未决状态都必须通过“必要性检查”：说明已尝试哪些静态/可控判断方式、为何仍不能判定，以及谁/什么动作能解除阻塞。若写不出这三点，说明分析还没完成，应继续检查而不是贴状态标签。已证明的失败和用例过时分别给反例或权威变更，不要求编造阻塞。
- “需黑盒验证”必须指出确需真实环境的变量。SDK 回调处理、生命周期逻辑和服务异常分支先静态代入，不能仅凭这些名字转黑盒；真实 SDK 交互、系统行为及目标设备渲染才可能保留。缺代码/配置/需求材料分别归证据不足/需求待确认；仅在动态对判定不可替代且具体证明断点已记录时，缺可控入口归接缝、缺执行环境归需自动化验证，不得把默认静态模式批量转成动态待办。
- “证据不足”必须是外部材料或访问能力确实缺失，不是分析进度状态。写出确切缺失物（文件、版本、配置快照、旧存档、权限或工具）、已尝试的定位路径和阻断的断言；不要使用“代码没找到”“还需进一步分析”等空话作为最终依据。
- “需求待确认”必须由权威资料之间的冲突，或关键业务决策完全未定义且不同答案会改变验收结论所触发。文案细节等不影响该断言判定的缺项，不要扩大成整条待确认。代码现状不能反向充当需求；已有明确安全不变量及其余明确断言继续判断。
- 一项阻塞只向直接依赖它的断言传播。参数实例如共享同一缺失证据，证据可复用但每个实例仍需逐一说明该证据对其输入和输出适用；不得为减少状态而虚构结论，也不得把同一根因重复包装成多项阻塞。
- 输出未决项时附“解除阻塞动作/责任来源/需要的输入”。例如“提供版本 X 的配置快照后核对字段 Y”，或“在设备 Z 执行步骤 N 并记录回调顺序”；不要只写“待验证/待确认”。

- 未定位到实现只属于证据不足，不等于 Bug。“没有显式过滤”“没有同名函数”“只搜一次未命中”均不是失败依据；应继续查等价实现。能完整证明必需入口未接入且产生可达异常时，才可判测试不通过。
- 需求歧义不能靠真机观察决定。资源未解码、线上配置未知、代码尚未读完也不是天然运行限制：先尝试项目内解析、读取和调用链追踪；确实缺权限/材料才记证据不足，代码仍未读完不得作为最终未决理由。
- 不因“涉及 UI/服务端/Unity 生命周期”自动推迟整条；检测依据不能仅写“需真机”“逻辑正常”“待确认”或复制一串无推导的行号。
- 只对声明范围内的断言归并：可达反例 -> 测试不通过；旧期望明确过时 -> 用例需更新；真实需求冲突 -> 需求待确认；确缺材料 -> 证据不足；必要接缝 -> 需开发补测试接缝；必要执行受阻 -> 需自动化验证；范围内外部残留 -> 需黑盒验证；其余全部实际自动化通过 -> 测试通过（自动化）；其余全部有充分证明（可混合静态/自动化）-> 测试通过（静态）。范围外已知失败必须在残留及摘要醒目标出。纯外部行不能标静态通过。
- 旧版三状态模板只有用户明确要求才兼容；未决原分类和原因仍完整保留，不把占位状态统计为真实人工任务，也不能为了兼容改判失败。

## 回填及证据

默认另存 `原文件名_{分支}_代码检测结果.xlsx`，不覆盖输入。仅用户明确授权覆盖时例外。

- 保留原表列和顺序，默认追加/更新 `测试结果 | 检测依据 | 自动化执行情况 | 真实环境残留`；已有列不重复添加。用户固定两列模板时后两项明确分段写入检测依据，仍保留机器账本。默认所有实际用例和必要参数实例放同一 `测试用例` 页签，不用多个分析页增加阅读负担；用户模板优先。
- `检测依据` 写实际核实的文件名和行号，必要时补工作簿单元格、配置路径和版本。未定位时如实说明，禁止为了填满列编造路径或行号。
- 每个参数实例独立回填。公共模板只作关联或汇总，不能检查一个参数就判全部通过。模板与实例结果不得重复统计。
- 证据和同根因阻塞可集中记录并用 ID 关联，每个实例仍核实适用性，不复制大量相同段落凑分析量。原用例过时与当前产品行为问题分开登记，不能把旧 oracle 测试绿灯当成本期需求通过。
- 完整 `验证明细` 保存为机器账本 JSON，含来源位置/原六列指纹、断言、范围、需求/代码证据、输入、期望、推导/实测输出、运行状态及残留。主表直接可读可复制，机器账本不要求使用者另读；只有用户指定时再增加分析页签。
- 运行验证状态使用未执行、不适用、已执行通过、已执行失败或执行受阻。纯静态审查默认未执行；不适用只用于无需运行的独立检查。只有真实执行并有命令/日志/录屏等证据时填写已执行状态。
- 未定位项列出已查目录、候选符号和断点；需求待确认项列明原文差异；需黑盒项给可操作前置、步骤、观察值。工具不可用、代码未检查完和资源未拿到要与产品行为问题区分。
- 若输出问题汇总，按根因归并 Bug 并关联所有受影响实例；保留黑盒复现步骤和静态证据，不把受影响用例数当成独立 Bug 数，不虚构复现率或真机现象。
- 保持原格式，更新筛选、状态校验、统计公式和图例以容纳全部实际结果。静态通过、自动化通过、真实观察、用例需更新、实际黑盒残留和其他阻塞分别统计，不将新增状态漏出统计或把静态通过率当自动化执行通过率。过时用例仍计为已审输入，但不得计为当前需求通过；列原始总数及适用口径，不能隐藏删分母。
