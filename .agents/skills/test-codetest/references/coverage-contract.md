# 需求、耦合、边界与版本升级覆盖契约

本契约同时用于设计和代码检查。同次联用只维护一个 `design-coverage.json`，复用已有覆盖项 ID、来源账本和主表行 key，不新增必读 Excel 页签。四维完整与代码通过是两件事：用例覆盖一个失败分支也算已设计，但不能算测试通过。

## 先盘点，再生成

从本次已选需求正文、表格和图片逐条提取可判定规则，先建立分母，再写用例。每条规则标明来源位置；正向功能、禁止行为、数值/文案/展示和数据规则都要盘点。缺资料、待确认和未设计项留在分母中。不能从现有用例标题反推“需求全集”。

按下表逐主题判断适用性。适用时必须关联具体覆盖项；不适用时写可核实依据，不能只写“未提及／本次不测”。没有因果关系的组合不造用例；无法确认的旧状态不得编成既定事实。

| 维度及主题 key | 必须检查的内容 |
| --- | --- |
| requirements：rules | 每条明确规则、禁止行为及正反分支；来源账本每个 rule ID 必须有承接 |
| requirements：data_presentation | 表格、图片、数据映射、数值、文案及展示条件；文案逻辑与真机排版分开 |
| coupling：shared_state | 共用资格、互斥开关、进度、计数、存档、账号与活动 ID；影响链追到最终消费者 |
| coupling：event_order | 回调、生命周期、弹窗队列、遮罩/锁；同时触发、A→B 与 B→A、重复和迟到事件；有因果关系的三方组合不能被成对组合替代 |
| coupling：config_reward | 配置合并及多消费者、奖励/支付/广告链、写盘与页面关闭/跨期；每项有实际关联路径 |
| boundary：values | 阈值前/等于/后、最小/最大、空/零、负值/越界；只测试系统允许输入或真实可达异常输入 |
| boundary：conditions | 单条件变化、每个决定性条件翻转、同时满足与互斥；多条件用决策表，不能只测全真和全假 |
| boundary：time_state | 开始/结束的精确时刻与前后、时间源/时区、跨日/周/期；未报名/进行中/失败/待领奖/已领奖/过期及可达转换 |
| boundary：interruptions | 返回、退出、重启、挂起恢复、断网重连；响应成功/失败/超时、重复/乱序及中间持久化点；核对不重复发奖、不串期、不丢进度等适用不变量 |
| upgrade：baseline | 查证已发布旧版字段、默认值、实际配置与状态来源，区分升级和干净安装；未知版本/旧字段记缺口，不虚构迁移 |
| upgrade：migration | 缺字段、旧值与边界进度、旧未结算/未领取/购买资格、旧配置新旧覆盖；字段解析、迁移、入口与最终消费全链核对 |
| upgrade：reentry_isolation | 首次升级启动、二次重启/重复回调的幂等、升级时跨期/离线、换账号/云档覆盖；只纳入项目确有入口及数据依据的场景 |

每个边界项必须写明固定条件及实际输入，例如 `now=end-1秒、end、end+1秒` 各自的独立预期，不能只有“覆盖时间边界”。时间精度按生产使用的秒/毫秒/日期核实，阈值符号按需求核实，不自行补闭区间。连续值使用实际精度，不机械写整数±1。

每个耦合项必须记录至少两个实际节点、共享对象/触发条件、动作顺序和预期副作用。每个升级项必须记录旧版依据、旧状态、新版本启动/迁移步骤及独立预期。不能只测字段能反序列化就宣称升级安全。

## 静态检查优先

默认全部本地断言使用静态追踪和显式输入演算。时间、关卡、随机范围、配置、奖励、存档、队列、网络结果和 SDK 回调均先代入受控值，查入口可达性、调用顺序、状态读写、持久化和最终消费。并发/异步须分析可达的事件顺序、共享锁及失效条件；单看一个方法不能证明整链安全。随机范围要核对可达集合与极值，不能只列一枚种子。

每条结论必须包含：独立需求预期、具体前置与输入、真实调用链和基线定位、关键判断的中间值/状态、最终推导输出。脚本辅助计算只能校验演算，不能复制生产算法后自证正确。没有运行真实测试就写“静态推导”，不得记自动化执行通过。

只有外部独有观察才转人工：目标设备分辨率/裁切、兼容性、实际触感/性能、真实操作系统通知投递、广告素材行为或商店真实交易等。代码里的文案、布局配置、平台分支、通知调度、回调处理及资格仍要静态检查。每个黑盒残留必须写出外部变量、本地不能替代的原因及最小步骤；可选黑盒复测步骤不等于必须人工执行。

缺 Runner、Unity、真实账号或显式注入接口不阻断静态演算。材料确实缺失或规则真有歧义时，只阻断依赖它的断言并说明缺失物，不批量转黑盒、不自动 pass。静态确实不能证明且只有动态观察能解答的复杂行为，必须具体说明证明断点和所需观察，不能伪装成已通过。

## 机器账本与门禁

在已有覆盖账本基础上保存下列字段，不重复生成分析说明。ID 只在机器账本内使用，主表无编号。

```json
{
  "schema_version": 1,
  "selected_source_ids": ["source-a"],
  "checks": [
    {"dimension": "boundary", "topic": "time_state", "status": "applicable", "item_ids": ["BDY-1"], "reason": "需求第2节规定结束时间"}
  ],
  "items": [
    {"id": "BDY-1", "dimension": "boundary", "basis": "需求第2节；活动时钟/截止判定",
     "status": "covered", "case_keys": ["测试用例!2"],
     "scenario": {"input": "固定已报名、未领奖；now=end-1秒/end/end+1秒", "sequence": "逐一代入到期判定", "expected": "分别填写来源规定的三个输出"}}
  ]
}
```

上述是局部结构示意，不是可提交的完整账本。所有主题必须登记；`checks.status` 为 `applicable / not_applicable / unknown`。`items.status` 为 `covered / partial / missing / ambiguous`；covered 只表示已设计，不表示已通过。每条 item 必须有 `basis` 和 `scenario.input / sequence / expected`；未决项允许缺少尚未知的场景字段，但必须有具体 `reason`，不能算已覆盖。requirements 项另有 `rule_ids` 承接来源规则；coupling 项另有 `path` 数组；upgrade 项另有 `from_version` 及 `old_state`。

`input-manifest.json` 的 `cases[].key` 必须来自实际主表回读，设计阶段可只提供 key；联用时直接复用代码报告的完整 manifest。必须带 `selected_source_ids` 和既有 `source_coverage` 的 path/SHA256 绑定。覆盖门禁核对来源规则、所有主题、双向用例映射和四维缺口，并绑定本次输入文件哈希：

```sh
python3 scripts/validate_design_coverage.py \
  --coverage /绝对路径/design-coverage.json \
  --input /绝对路径/input-manifest.json \
  --output /绝对路径/validated-coverage.json
```

来源未完整或确有外部资料/决策缺口时，可用 `--allow-partial` 保存阶段统计；它不允许跳过结构错误、悬空用例或伪造来源。缺口未消除必须在 Excel 同页摘要、HTML 顶部及对话中标明阶段结果。若独立执行代码检查发现原用例漏测，只登记缺口和建议，不擅自改输入；用户已授权补齐/生成时才补用例并更新映射。

交付前必须从原始来源重新反向审计一次，并列四维各自的已设计/总项数、未覆盖/待确认和有依据的不适用主题。需求规则总数不能用四维风险项数代替。门禁只验证显式登记的结构和映射，无法发现模型从未登记的语义遗漏，不能单靠校验通过宣称绝对不漏。
