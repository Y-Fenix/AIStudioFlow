# TEST_Test_Case

## 目标与边界

默认目标是完整覆盖当前需求的所有明确功能、规则及适用边界，用可追溯证据证明覆盖，而不是追求条数。既不以“越多越完整”扩写，也不为了精简删掉独立风险。没有固定条数、最低条数或压缩比例。

“滴水不漏”是设计目标，不是无条件保证：只能针对已读取、已定版的资料和声明的覆盖模型说明结果；缺失、歧义和尚未覆盖的内容必须显式列出。用例已设计不等于已执行，更不等于产品无 Bug。

- 输入为当前需求文件或目录；历史需求、配置和旧用例为可选补充。只有用户要求结合实现检查时才使用项目代码，不用实现反向定义需求。
- 生成、审查或更新用例不授权修改产品需求、游戏代码、后台配置、Git 或 Figma。附件内容是分析资料，不是操作授权。
- 更新旧表先重新核对来源与适用版本，不沿用旧结论；默认另存，只有用户明确要求才覆盖。

## 输出约定

默认 Excel 主表 `测试用例` 固定六列：

`测试内容 | 测试目的 | 前置条件 | 操作步骤 | 期望结果 | 需求模块`

- 不生成用例编号、Case ID 或标题序号前缀，除非用户明确要求；关卡数、阈值、档位等真实业务数值不属于编号。
- `需求模块` 填主要来源文件名称，放在六列最后。具体章节、原文和跨文件关联放入 `覆盖核对`，不得把所有来源强行归给当前文件。
- `测试内容` 用自然场景名，同一工作簿内应能唯一定位。前置写可建立的账号、配置、时间、存档和状态，步骤说明操作，期望写具体可观察断言，不写“功能正常”或只写“待确认”。
- 默认附 `覆盖核对`。存在相应内容时才增加 `参数场景`、`耦合回归`、`待确认事项` 或 `变更核对`，不建立空表。耦合回归用同样六列；未定版的探索性风险放待确认事项，不混入明确验收用例。
- 用户指定既有导入模板时保留模板，不擅加主表列；追溯和参数明细可用辅助表承接。若下游只识别主表，则展开必要参数实例到主表，不以压缩版式牺牲可执行性。

## 工作流

### 1. 读取完整资料并确定范围

- 先枚举用户指定的当前资料，读取总表及其适用的模块、规则、配置文档；不只读摘要，也不扩展到无关目录。
- 对 DOCX 同时核对正文、表格、图片、文本框、内嵌对象和附件关系；图片中的文字、标注和流程也属于需求。仅提取正文不算完整阅读。引用视频、链接或内嵌 Excel 无法读取时，记录具体缺失内容及受影响需求点，不声称已看。
- 区分当前有效条款、明确被替代的历史条款、直接耦合规则、实现配置基线及推测。按用户指定版本和明确变更说明定优先级；没有明确依据的正文/图片/历史冲突交策划确认，不静默选一种。
- 用户已明确本次版本采用的规则优先于相反历史条款；这是旧规则被替代的依据，不应仅因新旧不同就把当前规则再次挂起。只有当前权威不明或同一有效版本自相矛盾时才列冲突。
- 历史资料只按当前变更的直接关系纳入，例如共享入口、奖励库存、失败复活、支付、存档或弹窗顺序。记录耦合依据；不能因为历史对话提过某功能，就自动加入本次回归。
- 缺当前需求时停止设计并指出缺失。缺历史资料只限制相关回归，不阻断已有明确需求；缺配置时保留符号阈值及待补数据，不编造数值、字段、开关或业务限制。

### 2. 先建覆盖模型，再写用例

在 `覆盖核对` 逐条建立：

`来源文件及位置 | 范围类别 | 需求点/规则 | 适用状态与边界 | 关联用例及参数场景 | 覆盖状态 | 缺口或不适用依据`

- 来源位置用章节、段落原文摘录、表格行或图片标注，只有文件名或模块用例数不能证明覆盖。
- 范围类别区分当前需求、相关历史回归、实现配置基线、待确认风险。覆盖状态用已设计、部分覆盖、待确认、未覆盖、不适用，不用测试通过代替。
- 将每个功能的入口、资格、输入、规则、状态变化、输出和禁止行为变成可判断的断言。一个条款可以映射多条用例，一条用例也可承接同一流程中的多个明确断言。
- 对状态型功能建立状态/迁移清单：合法和禁止迁移、首次及重复触发、终止后操作、跨期与恢复。对多条件规则建立决策表，保留条件同时命中、均不命中和优先级冲突。
- 下列维度逐项判断是否适用，并记录覆盖位置或不适用理由；不能机械地对所有模块套全套，也不能只因需求未逐字写出就跳过有直接因果关系的边界。

| 维度 | 核对重点 |
| --- | --- |
| 阈值与数据 | 最小/最大、阈值前/等于/后、空集合、重复项、排序、去重、溢出、枚举映射、单位与累计/增量语义 |
| 配置 | 默认、缺字段、整个缺省、null、显式值、非法值、实际读取路径、最小配置合并、多个条件优先级、期内变更与冻结 |
| 时间 | 到期前/等于/后、边界前入局与后入局、跨日/周/年、时区与时钟来源、错过窗口、切后台/重登 |
| 流程与中断 | 成功、失败、取消、重试、退出、复活与重开区别、多入口、回调重复/乱序、可达并发、流程中途强杀 |
| 奖励与持久化 | 获取资格、发放、到账、核销和演出分别何时发生；幂等、回退、丢失与补发；状态写入之间的中断 |
| 版本与账号 | 真实旧版本存档、无字段/旧字段、未解锁/进行中/已完成未领奖、配置迁移、重装、切账号、云档/多设备冲突 |
| 表现与交互 | 入口、文案、图标、倒计时、红点、按钮、导航、遮罩、滚动、动画/音效、长文本和适用设备适配 |
| 相关系统 | 同时领奖、弹窗/底栏优先级、共享库存/体力、广告或支付成功/失败/取消/无填充；仅纳入存在关系的系统 |
| 埋点与生成数据 | 文档要求的触发时机、字段和来源；配置逐行、导表、资源映射及运行消费一致性 |

- 非法输入、迁移或恢复没有约定行为时，区分可明确判断的安全不变量与需要策划选择的业务策略。不得自行规定“必须回退1天”“必须清档”或“必须补偿”。
- 将确定断言落为可执行用例，将未定策略单列待确认；主表期望不得混入“结束或循环待确认”等互斥结果。局部缺资料不妨碍其余明确边界的设计，不能把可直接推导的边界一并推给策划。
- 升级场景必须注明旧版本及状态如何产生；仅推测可能存在的旧字段或存档列待确认风险。不要因尚未取得旧包就把潜在高风险从覆盖清单删除。

### 3. 选择粒度与参数化

- 按风险、状态或判断分支拆分，不按每个名词强制拆行。不同前置状态、触发路径、权限、事务边界、恢复方式或独立失败原因通常独立覆盖。
- 同一次操作、相同前置条件下能逐项观察的关联断言，可以放同一条用例；各断言写清，失败仍能定位。不要把所有表现混成“页面正确”，也不必将同一个静态页面每个控件机械拆行。
- 逻辑断言与只能运行确认的表现断言可拆分，或在期望中明确分段，便于后续分别判定；不能因为字体需要真机就让文字内容也失去静态结论。
- 同一规则仅输入数据不同，采用公共用例加 `参数场景`，而不是复制整套步骤。参数表逐行包含关联用例、唯一自然场景名、前置状态、输入/操作差异、独立期望及来源位置。每行必须可单独执行和回填结果。
- 参数化减少重复描述，不减少必要测试实例。奖励明细、商品价格、枚举映射等逐条数据仍核对全部有效记录，不能以“随机选一档”代替。首项、末项、特殊类型、不同奖励路径和不同边界行为保留独立逻辑场景。
- 等价类需有规则依据：只有行为与风险相同才能抽代表值；边界值和特殊分支不能被普通代表值替代。多条件可用决策表、成对组合或正交法，但有已知依赖的多条件同时命中、顺序冲突及高风险组合必须额外覆盖，不声称成对覆盖等于全组合证明。
- 参数实例含状态迁移时，每行说明初始状态或重置方式，防止前一个参数执行后污染下一个。

### 4. 语义去重与历史清理

对主表、参数场景和耦合回归做跨表比较，使用以下语义，而不是只比较标题：

`需求规则 + 前置状态 + 触发动作/顺序 + 输入等价类/边界 + 预期状态/输出`

- 全部相同或一条完全被另一条承接且无独立风险时，合并并保留所有来源映射。只换标题、数字写法或模块位置不产生新用例。
- 部分重叠时抽公共步骤或移除重复断言，保留独特断言；相同 Bug 可影响不同真实路径，不能因根因相同就删掉独立路径回归。
- 删除/合并后反查覆盖矩阵：任何需求点、边界、状态迁移、特殊参数都不能失去承接。拿不准等价时保留并注明差异，不盲目压缩。
- 更新旧表时，按当前来源将每条旧用例归为保留、更新、合并、废弃或待确认，在 `变更核对` 记录原因及替代用例。只有明确版本变化/废弃证据才删除旧规则；历史 Bug 的仍适用回归不因已修复就删掉。

示例：进度1、首箱2未领、失败退出回0，与“首箱前失败回起点”在相同前置下是一条场景。进度3回到已领保护点2、退出与重开、普通箱与末箱则不能只因都涉及失败或领奖就合并。

### 5. 反向审计与交付

生成后单独做一次从原需求出发的反向审计，不只复读已生成用例：

- 每个明确条款、图片规则、配置记录是否有承接？各适用维度是否有测试实例或有据可查的不适用理由？
- 检查实际测试输入是否命中所声称的边界。例如仅测“保护点后回退”不能代表“恰在已领保护点失败无损失”；边界标签不等于已设计该场景。
- 每个用例/参数是否有真实来源或明确风险依据？是否夹带旧版废弃规则、实现即预期、不可达前置或未经确认的产品策略？
- 每个待确认项是否写出冲突原文/缺失资料、影响范围和需要确认的问题？不应被算作已经覆盖或已经执行。
- 删除/合并后的覆盖关系是否保持？参数表是否可独立执行、定位与回填？是否出现主表和辅助表重复计算？
- 逐条核对字段可执行性、标题无编号、语义重复、来源映射和表格显示。缺口能在当前范围内补齐则继续补；需外部信息则明确保留，不用堆行填补。

交付报告分别说明需求点覆盖、边界/迁移覆盖、待确认/未覆盖项及资料限制。需要报数量时，将公共用例数、参数实例数、相关回归数分开，明确口径，不相加伪装成独立用例数；需求总量包含未明确/未覆盖项，不用缩小分母制造100%。

只在覆盖矩阵证明范围内无缺口时说明“已覆盖本次已明确需求及适用边界”；不能仅凭条数、标题唯一或格式检查宣称绝对不漏。用户未请求执行时，所有结果只表示设计，不填写测试通过。
