# TEST_Test_Codetest

## 目标与权限

按指定代码基线逐条检查测试用例的可达行为，不以关键字命中代替调用链证明，不以未找到代码推断未实现。默认只做静态分析，不声称执行过游戏或测试。

- 必需输入为 Git 分支和测试用例 Excel；代码目录默认当前仓库。与 TEST_Test_Case 连用时，以本次已生成的用例为输入，不要求用户重复提供路径。
- 遵守项目 AGENTS.md 的探索和验证入口。禁止擅自提交、拉取、推送、修改业务代码或线上状态。需要运行测试时说明适用入口，只有用户授权和环境满足时才执行。
- 缺分支、缺用例或表结构无法识别时，先指出具体缺失，不生成假结果。资料或个别资源缺失只阻塞相关断言，不中止全部已可检查的用例。

## 基线与输入

1. 核实仓库绝对路径、目标本地分支、HEAD、相关子模块版本及未提交改动。当前不在目标分支时，仅在不会破坏现有改动且项目规则允许时切换；否则停止并报告。分支不存在则停止，不自动拉取或以另一分支代替。
2. 记录实际检查的是提交快照还是含未提交改动的工作区。已有远端缓存仅作说明，不能宣称它是线上最新；检查结束复核基线，变化时重新检查受影响内容或明确报告失效范围。
3. 识别所有实际用例表，包括主表、耦合回归及参数场景。读取公共用例与参数的关联、独立预期和初始化条件；辅助覆盖清单不是已执行用例。
4. 保留输入用例的内容、顺序和无编号约定。代码检查不授权删除、合并或改写原期望；发现重复、废弃规则或前置不可达时记录适用性问题，不静默跳过。
5. 需求、旧版规则和实现基线分清。用户明确指定的本期规则优先于被替代的旧规则；当前权威不明或期望不可判定时记录需求待确认，不能按代码现状补一个预期再判通过。

## 检测方法

对每个用例及参数实例执行：

- 把期望拆成可验证断言，分别记录逻辑、数据、表现。沿输入/配置 -> 状态前置 -> 调用链 -> 数据变换 -> 资源消费 -> 输出追踪，先证明测试前置及目标路径可达。
- 使用已暴露的符号索引及项目规定入口；不可用时说明原因，再做限定目录的符号、引用和配置搜索。需求名可能与类名、字段名不同，不因同名搜索无结果就停止。
- 检查默认值、范围变换、索引、循环、取模、过滤顺序、fallback、配置覆盖与生成资源。配置 CSV 与实际包内容不能直接等同。
- 尝试现有的只读解析器、导表映射或资源读取链；不要看到 MessagePack、加密或 Addressables 就立即宣告只能黑盒。确实无法取得或核实资源时列具体证据缺口，不输出密钥、令牌或账号敏感信息。
- 对逻辑结论寻找反例：用具体配置、输入和状态证明能到达不符合预期的输出。纯函数的边界输出、固定文案与条件分支应尽量由静态证据给出结论，运行随机输入不必然使所有分支都无法分析。
- UI 文案内容与字体/裁切分开，计时计算与刷新/显隐分开，奖励资格/幂等与真实到账/动画分开。关联逻辑能确认的先确认，只有剩余运行断言交黑盒。
- 多模块耦合继续追到共同状态、回调、存档和奖励消费点；仅定位入口不足以判通过，也不足以将整条直接归为运行限制。
- 同一原因涉及不同参数或路径时可以复用适用的证明，但逐一检查前置和输出是否相同，不能复制不适用的行号或统一套结论。

范围类断言必须核对权威数据中的目标位置及运行映射。例如禁止数据只在源下标0至4，而可达池从下标5开始，不能因无显式类型过滤就判失败。至少检查起点前一项、起点、末项、回绕、空数据和 fallback。

## 结果分类

保留结果列名称 `测试结果`，但它是静态审查汇总，不是实机执行结果。默认允许五种互斥汇总值：

| 测试结果 | 判定条件 | 必须提供 |
| --- | --- | --- |
| 测试通过 | 在明确前置和检查基线内，完整证据支持该行全部断言 | 决定行为的文件/行号、输入条件及推导；注明静态结论 |
| 测试不通过 | 对明确需求找到至少一个实际可达反例 | 前置、触发步骤、预期、异常、错误位置及可达链路 |
| 需黑盒验证 | 已定位并完成可做的静态检查，剩余断言确实依赖运行观察 | 已确认部分、具体运行因素、验证动作与判定标准 |
| 需求待确认 | 期望、版本适用性或业务规则不明确，无法判定对错 | 冲突/缺失条款、当前已知行为、需要确认的问题 |
| 证据不足 | 调用链未闭合、实现未定位、资源/远端配置/旧档等证据未取得或工作未完成 | 已查范围、已知证据、缺口及下一步获取/定位方式 |

判定约束：

- 未定位到实现只属于证据不足，不等于 Bug。“没有显式过滤”“没有同名函数”“只搜一次未命中”均不是失败依据；应继续查等价实现。能完整证明必需入口未接入且产生可达异常时，才可判测试不通过。
- 需求歧义不能靠真机观察决定。资源未解码、线上配置未知、代码尚未读完也不是天然运行限制，不能统统塞进需黑盒验证。
- 不因“涉及 UI/服务端/Unity 生命周期”自动推迟整条；检测依据不能仅写“需真机”“逻辑正常”“待确认”或复制一串无推导的行号。
- 一行含多个断言时分别记录结论。明确反例优先汇总为测试不通过；无反例但存在未定期望则需求待确认，其次证据不足，其次需黑盒验证；只有全部断言均被静态证明才汇总通过。保留其余断言的状态，不用一个总状态隐藏缺口。
- 如用户明确限定旧版三状态模板，未定或缺证据项兼容放入需黑盒验证，但在依据和统计中分别标明“需求待确认”或“证据不足”，说明它们不是实际黑盒任务。不能为了兼容表格而改判失败。

## 回填及证据

默认另存 `原文件名_{分支}_代码检测结果.xlsx`，不覆盖输入。仅用户明确授权覆盖时例外。

- 保留原表所有列，在各实际用例/参数表末尾追加 `测试结果`、`检测依据`。输入已含这两列时，在新输出中更新而不重复追加；旧结论不能直接沿用。
- `检测依据` 写实际核实的文件名和行号，必要时补工作簿单元格、配置路径和版本。未定位时如实说明，禁止为了填满列编造路径或行号。
- 每个参数实例独立回填。公共模板只作关联或汇总，不能检查一个参数就判全部通过。模板与实例结果不得重复统计。
- 含混合断言、未决项或实际运行证据时，用 `验证明细` 分开记录：关联工作表/用例/参数场景、检测断言、静态结论、运行验证状态、检测依据、缺失证据/下一步。
- 运行验证状态使用未执行、不适用、已执行通过、已执行失败或执行受阻。纯静态审查默认未执行；不适用只用于无需运行的独立检查。只有真实执行并有命令/日志/录屏等证据时填写已执行状态。
- 未定位项列出已查目录、候选符号和断点；需求待确认项列明原文差异；需黑盒项给可操作前置、步骤、观察值。工具不可用、代码未检查完和资源未拿到要与产品行为问题区分。
- 若输出问题汇总，按根因归并 Bug 并关联所有受影响实例；保留黑盒复现步骤和静态证据，不把受影响用例数当成独立 Bug 数，不虚构复现率或真机现象。
- 保持原格式，更新筛选、状态校验、统计公式和图例以容纳五种结果。不要将新增状态漏出统计或沿用旧表的通过率。

## 交付门禁

- 已记录并复核实际基线，未用其他分支、旧报告或记忆代替当前证据。
- 所有范围内用例与参数实例有对应审查记录；公共模板、参数实例、回归场景的计数口径明确且不重复。
- 每条失败有可达反例，每条通过覆盖全部断言；部分静态通过不得包装为整条通过。
- 需求待确认、证据不足、需黑盒验证分别统计，并说明其中哪些可继续静态定位、哪些需要资料、哪些确需运行。
- 可在当前权限和资料内补齐的缺口继续处理；外部依赖或未完成分析如实保留，不为了清空待验证强行下结论。
- 未修改原用例期望、未自动继承旧结论、未重复添加结果列、未擅自覆盖输入；输出字段和统计核对一致。
- 最终简述结果、关键问题、检测基线、未执行项和限制。格式检查通过不等于业务通过，静态检查不等于自动化执行或真机验收。
